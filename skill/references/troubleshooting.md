# Troubleshooting averi output

Find the line or error you see, then act on it. Each entry gives the meaning, then the action.

## Traces and the ladder

- **`✗ <step> — failed — <reason>`**: the step that failed. Steps log only on success, so the line before it is the last step that worked, not the culprit.
- **`✗` followed by `⚠ reach <flow>`** inside an `ensure_state`: that rung failed and the ladder went on to the next one. It is not the headline error. Fix the rung anyway, because it only costs time.
- **`⚠ reach <flow>: this rung is DESTRUCTIVE`**: averi is about to wipe the app's data. **`⚠ clearState` + count**: it did. A count that climbs while you debug means stop re-running.
- **`⛔ reach <flow>` / `Refused to run reach flow …`**: averi refused a destructive rung because the screen was unreadable or still bare after a ~20 s second look. Nothing was wiped. Take a `screenshot` and retry once the screen has rendered. If the screen shows only unlabeled icons, it reads as bare too; `run_flow` the rung yourself if you mean it.
- **`⚠ detect: <condition> treated as not detected — …`**: a probe that read nothing usable (`(second look over 20 s)` on the second look). It is a diagnostic, not the failure.
- **`⚠ swipe <direction> — …`** (the second line of a `swipe` reply, `⚠ <note>`): the swipe was sent, over a box not witnessed as the screen held now. `the UI tree could not be read (…); swiped over the device screen as built, WxH`: averi does not know how the screen is turned; if it is turned, the stroke's centre and length were the upright panel's and may have missed the content — take a `screenshot`, and if it is turned or did not scroll, swipe again once the tree reads. `the device screen size could not be read (…); swiped over the UI tree's window, WxH`: the tree's window stood in for the screen — read again before relying on what the swipe moved.
- **`↻ recovery <state>`**: the earlier safe rungs ran once more because a late screen beat the ladder. **`↻ no recovery`**: the call's one pass was already spent. **`⚠ recovery` / `⚠ salvage`**: the pass reporting its own stumbles, never the cause.
- **`could not be checked`**: a state with no reach flows met an unreadable tree. Take a `screenshot` first.

## The tree is empty, bare or unreadable

- **`ui_snapshot` returns `[]` plus `0 matches for … in a tree of N nodes`**: the tree has content and none of it matches. If the screen may still be loading (a spinner, an overlay), confirm with an `assert` with a `timeout`, or with a `screenshot`.
- **`[]` plus `⚠ … the tree is bare`**: the tree is empty or unrendered. On iOS right after `launch_app` it may hold only the status bar and the app's icon; that is SpringBoard, not the app, and is bare too. Take a `screenshot`. If the screen is rendered, the tree source is stuck; do not read the element as absent.
- **iOS `idb returned an empty accessibility tree …`** (a lone 0×0 `Application`): a stuck idb, or the first second after `launch_app`. If it says `retried once after 1 s`, it is still stuck. Recover in this order:
  1. `terminate_app`, then `launch_app` (only a new process recovers);
  2. the simulator reboot the error names;
  3. or `app.ios.treeSource: wda` as an alternative source.
- **iOS `idb cannot read the UI tree: the simulator's accessibility service named no frontmost application`**: the simulator's accessibility service is wedged, usually by a tree read made too soon after the simulator booted. It lasts until a reboot: relaunching the app, restarting idb_companion and waiting do not cure it, so averi fails the call at once rather than retrying. Recover in this order:
  1. the simulator reboot the error names; wait until the boot completes (`xcrun simctl bootstatus <udid> -b`) and start idb_companion a few seconds after that, before the next call that reads the tree;
  2. or `app.ios.treeSource: wda` as an alternative source.
- **Android `device <id> is not reachable: adb get-state says "device offline"`**: recover the emulator (wait for `adb devices` to show `device`, else `adb kill-server && adb start-server`). Do not call `ensure_state` meanwhile: its probes read nothing.
- **Android `device <id> is not answering: adb get-state timed out`**: adb itself hangs, not the app. Run `adb devices`; if it hangs too, `adb kill-server && adb start-server`, otherwise restart the emulator (or reconnect the USB cable).
- **Android `… is unauthorized` / `… is offline`** (`No usable Android emulator/device found`, `select_device`, or a selected device): adb lists the device but cannot drive it. Unauthorized: unlock the phone and accept the "Allow USB debugging?" prompt; for an emulator, `adb kill-server`, then `adb devices`. Offline: wait for `adb devices` to show `device`, else `adb kill-server && adb start-server`.
- **Android `is still settling`** (uiautomator's null root right after a launch): take a `screenshot` (it waits for stability), then retry.
- **Android `is reachable but SLOW`**: the host is under load. The app is not dead.
- **`scroll_until … failed after 38204ms (timeout 15000ms; no swipe was sent; 1 tree read took 38204ms) — …`**: the scroll ran out of time, and the text after `—` says only where the element was at the last read. The parenthesis says what spent the time: the time taken, the budget (`timeoutMs`), the swipes sent and how long the tree reads took (in all, and the last one). The budget is checked once a round, after its tree read and keyboard queries, so the time taken can pass `timeoutMs` by one swipe, the settle after it and one more round — its tree read and, on Android, its keyboard queries — and includes them. When the reads took most of it, especially with no swipe sent, the tree source was slow or restarting (a WebDriverAgent restart is reported on the averi server's stderr, not in the reply); the content is not at fault. Retry the step, and check the server's stderr if it recurs. When swipes were sent and the reads took little of the time, the swipes did not bring the element into view in time: pass a larger `timeoutMs`, or check the selector and `direction`.
- **`absent` assert fails with "could not verify"**: the tree was bare. Absence is never passed on an empty screen.

## iOS: an `id:` misses an element that is on screen

Under `treeSource: idb` (or the default `auto` when WebDriverAgent did not come up — its replies carry a `⚠ read through idb` line), this is expected:
- React Native `testID` on a static `Text` or a container is invisible, because idb returns only accessibility elements;
- the same applies to a SwiftUI identifier on an `.accessibilityElement(children: .contain)` container;
- idb drops some identifiers the app sets, a UIKit table cell label's among them (WebDriverAgent reads them);
- idb lists nothing beneath the keyboard or a presented sheet, alert or cover.

The reply says so beneath its not-found: `no tree read contained id:"x". Possible reasons: idb lists nothing beneath …`,
or, when the read lists no identifier on any element, `no tree read contained id:"x", and idb's read lists no id on
any element. Possible reasons: …`. If something covers the element (the keyboard, a sheet, an alert), close that
first. If it is showing, ask for it by `text:` or `label:` (read the label from `ui_snapshot`), or switch the tree
source.

Do not restructure app code (a `Pressable` wrapper, blanket `accessible={true}`) to please the tool. Set `app.ios.treeSource: wda` in `averi.yaml`:
- `id:` then resolves on static text and containers, as on Android;
- taps, typing and install stay on idb/simctl;
- tree reads are ~2× slower, and the first WebDriverAgent build per Xcode version takes minutes and needs `xcodebuild`.

WDA comes from `appium-webdriveragent`, an optional dependency of averi. If an install skipped it (`--omit=optional`), the error names the package.

Alternatively, detect on an id idb does list, or by `text:`/`label:`.

## iOS: `⚠ read through idb: WebDriverAgent did not come up …`

Under the default `treeSource: auto` averi reads the tree through WebDriverAgent, and through idb when WebDriverAgent cannot be brought up at the simulator's first tree read (its package missing, a failed build, a WebDriverAgent averi did not start on its port). The choice holds for the simulator for the rest of the server session. Each reply that claims what it read (tap, a fill, scroll_until, assert, flows, ensure_state, verify) then ends with this line: idb lists no presented layer and no scroll clip, so a target under a menu or sheet, or past its scroll view's edge, may be claimed while the app saw nothing. Check such a claim with a `screenshot`. The reason is on averi's stderr. `app.ios.treeSource: wda` makes the same failure an error that names it; fix it and restart the server.

## A tap target off screen

- **`… is off screen at (x,y) on a WxH screen … — scroll_until it first; nothing was tapped`**: the element is in the tree but its centre is outside the screen. iOS keeps a scroll view's content below the fold in the tree with real rects. Nothing was tapped, so focus did not move. Run `scroll_until` for the same selector, then tap again (unless the refusal says a screen is presented over it: see that entry below).
- **`… only N% of it … is on screen … — scroll_until it with fully: true first`**: the element is clipped at an edge with its centre outside. Since 2026-10-09 a plain `scroll_until` also keeps scrolling until the element's centre is on screen (and clear of anything drawn over it), so either works; pass `fully: true` when the next step measures the element.
- **`… is outside its scroll view <scroll view> at (x,y): nothing of it is drawn (rect …) — scroll_until it first; nothing was tapped`** (or `only N% of it (rect …) is drawn, and a tap goes to its centre — scroll_until it with fully: true first`): iOS with `treeSource: wda`. The element's centre is on the screen, but outside the scroll view it is listed in. WebDriverAgent lists a scroll view's content at its laid-out rect even past the scroll view's frame, and the scroll view draws none of it there: what shows at that point is something else, such as the background below a form that ends above a pinned button bar. Nothing was tapped. Run `scroll_until` for the same selector, then tap again. With the keyboard up, the keyboard is hidden first and the element judged again, since a scroll view laid out above the keyboard grows back.
- **`… is cut at its scroll container's bottom edge (container …); only a WxH part of it shows, N deep across that edge, under the M a tap needs — scroll_until it first (if it is whole …, tap a child of it that lies clear of that edge, or tap by coordinates); nothing was tapped`**: the element's centre is on screen, but its scroll container cuts it to a strip too thin to tap (Android; a strip that thin had taken the tap and done nothing). Run `scroll_until` for it, then tap again. A cut at the top or a side names the `direction:` to pass. `scroll_until` does not stop on such a strip either. If it fails with `… cut at its scroll container's … edge … and the content is exhausted`, the list has no room to show the element whole, or the element is whole but its content touches that edge, which averi cannot tell from a cut. Then tap a child of it that lies clear of that edge, or tap by coordinates. averi refuses only when the tree shows the element runs on past the edge, or when the element touches the edge inside something cut there to such a strip: then the message adds `as is the … it lies in` and says to tap something in what it lies in that lies clear of that edge, or by coordinates: a child touching the cut is no better than its parent. A whole small element that merely touches the edge is tapped. A cut element with no children cannot be told from a whole one, and is tapped, unless what it lies in is refused at that edge. A whole thin row at a list's top with a hidden child laid out above it (a swipe-action view) reads as cut and is refused; tap a child of it that lies clear of that edge, or tap by coordinates.
- **`… is cut at its top edge by <node> (x,y WxH), drawn after it — the dump (Compose's, on Android) leaves out of a node's bounds what a later node covers, so the rest of it may lie under that <role>; only a WxH part of it shows (above the soft keyboard), at x,y, N deep across that edge, under the M a tap needs — … scroll_until it out from under that <role> first (only if a screenshot shows it whole — a control that thin laid flush against that <role> — no scroll shows more: tap by coordinates); nothing was tapped`** (Android): the element is a control dumped as a strip too thin to tap, flush against something the app draws after it — typically a field under a submit bar riding on the soft keyboard, whose own surface is not in the tree. A tap on the strip may land on that bar and be reported done while nothing reaches the field. When the refusal starts the remedy with `the soft keyboard is up (its top edge at y …): dismiss it first (press_key back …) — a bar riding on it goes down with it — or …`, hide the keyboard and tap again; otherwise run `scroll_until` for it, then tap again. Only if a `screenshot` shows the element whole and really that thin (a control laid flush against its neighbour, which the tree cannot tell from a cut), no scroll shows more: tap it by coordinates — never on the strip of a field the bar hides. A text (a field's title) is not refused this way. A node with no control role that is no text either (a clickable row, say) is, when it lies in no scroll view and the node after it runs across its whole top or bottom edge and past it at both ends: a button bar pinned over the content's margins.
- **`… is under <cover> (x,y WxH) at its centre (x,y), drawn over it; only a WxH part of it shows … — scroll_until it first; nothing was tapped`**: something the app draws later lies over the target's centre (a pinned button bar, a floating tab bar), and too little of the target shows beside it to move the tap there. Run `scroll_until` for it, then tap again (unless the refusal says a screen is presented over it: the next entry). A wrapper with children (a `container` or an `other`) laid after the content counts as drawn over its whole rect, unless, among others, it is the screen's size (90 % of it or more), or it has no label and no value and holds the target together with the target's whole scroll view, or it has no label, value or identifier and holds only empty frames: the tree cannot tell a host that swallows touches (a tab bar's) from a transparent one that only positions its child. So on Android a target beside or under a floating action button can be refused naming the FAB's full-width host (Clock's `container id:fab_container`), and a `color`/`ocr` assert there fails closed on it. When the wrapper holds one child only, a control of at most a quarter of its area, the refusal ends `… — the wrapper may only position its one child, <child>: tap that child when it is the target; otherwise scroll_until this element out of the wrapper's band first` instead; a wrapper of several children (a tab bar's host) gets no such line.
- **`… is overlapped by <cover> (x,y WxH) at its centre (x,y), the two listed in reading order: which is drawn on top is not told; … — no scroll tells which is on top: see a screenshot — if the other is drawn over it (a menu, a popover), close it first; if it is the one on top, tap it by coordinates; nothing was tapped`** (tap; `color`/`ocr` fails with `<cover> overlaps the element …, the two listed in reading order …` and ends `if the element is the one on top, assert something in it that lies clear of the other`; `scroll_until` says `… stopped before any swipe — element is in the viewport but overlapped by …; no swipe was sent — no scroll tells which is on top: …`): iOS lists a SwiftUI container's elements in reading order (by their tops), not in the order they are drawn, so of two overlapping controls — an in-screen menu's row drawn over the row beneath it — the tree does not say which is on top, whichever is listed first. The target is refused rather than tapped at a point that may press the other. Take a `screenshot`: if the other control is drawn over the target (a menu or popover is open), close it first; if the target is the one on top (the menu's own row, or two controls that merely touch), tap it by coordinates. No swipe is sent or advised: a stroke beside an in-screen menu may land on its backdrop and close it. Under `treeSource: wda` averi reads a container as listed in reading order when its children's tops never decrease in the order listed (`ui_snapshot` marks it `"readingOrder": true`) — most top-to-bottom layouts pass that check, so two controls that genuinely overlap there (a badge over an avatar, a row's accessory poking out of it) read the same way, a refusal rather than a wrong tap. On Android, a classic View lists its children by location (Android's own accessibility sort), so a banner or toast drawn over a button may be listed before it: such a run is marked `"readingOrder": true` too and read the same way (Compose's nodes are not).
- **`… is under <cover> (x,y WxH) at its centre (x,y), drawn over it as a screenshot shows (the two are listed in reading order); … — if it is a menu or a popover, close it first; no scroll moves it out from under it; nothing was tapped`** (tap; `color`/`ocr`: `<cover> is drawn over the element … as a screenshot shows …`; `scroll_until` stops before any swipe with the same words): the case above, after averi looked. For a target covered by a control listed in reading order with it, averi takes one screenshot and compares the two controls' colours in their overlap and beside it: a target seen on top is tapped (asserted, reached) as usual; one seen beneath is refused naming the control drawn over it. Close the menu or popover first. When the screenshot cannot tell — the two look alike (ΔE under 8), a control shows the screen's own colour (it may draw nothing there), the frame was mid-animation — the reply is the one above with `a screenshot could not tell either (<why>)` in place of `see a screenshot`.
- **`… a screen is presented over it (a modal or a sheet) — close it first; no scroll moves it out from under that screen`** (tap or `scroll_until`): the target lies on the screen beneath a modal or sheet that is still up — whatever else keeps it from a tap (its centre under that screen, off the screen or under the status bar — wholly too, since the screen is judged presented over the target itself, wherever it lies — or a cut at its scroll container's edge), a tap says this in place of that remedy (`scroll_until it first`, the status bar's advice); nothing was tapped and no further swipe was sent. `scroll_until` says it as `… a screen is presented over it (a modal or a sheet) — close it first; no scroll moves it out from under that screen, and a swipe on it may dismiss it, so none was sent` (or `so no further swipe was sent`). Close or finish that screen (its close button, Cancel, Done), then repeat the step. On iOS with `treeSource: wda` that screen is a layer WebDriverAgent shows presented — it reports every node of the screen beneath not visible while the layer shows, and `ui_snapshot` marks the layer `"presentation": "screen"` — and the refusal names what of that layer lies at the point (a row, its title, the sheet's container), the layer itself (`container (0,0 402x874)`) where nothing of it draws there. If no modal is visible on the screenshot, WebDriverAgent may have read the screen mid-animation (repeat the step), or — on a tree that carries no such mark (Android) — the app may keep a full-screen dimming view or scroll view laid over the screen after closing it: report the tree with `ui_snapshot`. A full-screen host that only carries a bar or other content of its own (a host with children: Safari's full-screen host of its bottom bar) is no such screen: only what it draws covers. `scroll_until` says the same when the target is in the tree but not in the viewport (below the fold, under the soft keyboard, cut) and the next swipe would touch down on such a screen: `… — element lies below the viewport, and the next swipe would touch down at (x,y) on <that screen's dimming view or scroll view> — a screen is presented over it …`, and no swipe was sent, because that swipe would land on the modal or sheet (closing a popover, moving a sheet to another size) and not on the target's screen. A failure at a bound adds `The next swipe would have touched down at (x,y) on … — a screen is presented over it …` for the same reason. Close that screen first here too. Under a layer WebDriverAgent shows presented (iOS with `treeSource: wda`) no swipe is sent for a target not in the tree either — `scroll_until … stopped before any swipe — element is not in the tree, and the next swipe would touch down at (x,y) on … — a screen is presented over it …` — unless the swipe would touch down on a scroll view of that layer's own (a search inside the sheet's own list), which is swiped as usual. An in-screen menu laid over a dimming backdrop that closes it on a touch (a SwiftUI card over a blurred screen, in the screen's own container) is refused too under `treeSource: wda` when the screen beneath is grouped as one container the screen's size and WebDriverAgent lists the backdrop after it at its origin: `ui_snapshot` marks the backdrop `"presentation": "backdrop"` — though the screen beneath may still read visible (a hidden backdrop leaves its flags as they were) — and the reply names that evidence: `… a menu's backdrop is presented over it (an empty element WDA lists over the whole screen, after the screen's content) — close it first (if a screenshot shows no menu up, the backdrop is an overlay that lets touches through: tap the target by its coordinates (its centre from ui_snapshot)); no scroll moves it out from under that backdrop` (`scroll_until`: `… (… swipe, then tap the target, by coordinates); … and a swipe on it may close the menu, so none was sent`; `color`/`ocr`: `… (… judge the element on that screenshot) …`). An invisible overlay laid over the content that passes touches (a tint or shimmer, `.allowsHitTesting(false)`, RN `pointerEvents="none"`) reads as such a backdrop: take a `screenshot`; with a menu up, close it; with none, tap the target by its x/y (its centre from `ui_snapshot`), which averi does not judge, and report the tree with `ui_snapshot`. Under idb, or when the menu's rows and the screen's are listed together in reading order, nothing in the tree shows the backdrop: a tap beneath it can answer `Tapped` while the backdrop takes the touch and only closes the menu. If a step taps under such a menu, close the menu first; for the app team, the remedy is `.accessibilityAddTraits(.isModal)` on the menu (the screen beneath then leaves the tree, so a tap there finds no target) or a labelled accessibility element on the backdrop, and `treeSource: wda`.
- **`… an alert is presented over it ("…") — close it first`** (tap or `scroll_until`; iOS with `treeSource: wda`): an alert is up (WebDriverAgent's `Alert`: `ui_snapshot` marks its layer `"presentation": "alert"` and the Alert itself `"presentationElement": true`), and it covers the whole screen beneath it, whatever lies around its card — the target is refused wherever it lies, and nothing was tapped. `scroll_until` says it as `… an alert is presented over it ("…") — close it first, and a swipe would land on the alert, so none was sent` (or `so no further swipe was sent`), and under an alert it sends no swipe even for a target not in the tree: `scroll_until … stopped before any swipe — element is not in the tree, and the next swipe would touch down at (x,y) on … — an alert is presented over it ("…") — close it first, and a swipe would land on the alert, so none was sent`. The alert's own buttons and texts are reached as usual: tap the button that closes it, then repeat the step. For a target not in the tree, a swipe that would touch down on a scroll view of the alert's own is sent (a search inside the alert); for a target beneath the alert, no swipe is sent wherever it would touch down. An action sheet or a popover (WebDriverAgent's `Sheet`, `Popover`; `"presentation": "actionSheet"` or `"popover"`) reads the same way, named by its kind and label — `… an action sheet is presented over it ("…") — close it first`, `… a swipe would land on the action sheet …` — and its own buttons and dismiss region are reached.
- **`Timed out after …: element … is not in the tree, which lists only the window presented on top (the tree source lists the active window alone) — a dialog is presented over it — close it first`** (tap, fill; Android): uiautomator dumps only the window that has focus, so with a dialog up (`ui_snapshot`'s root carries `"presentation": "dialog"`: a window floating off the screen's top and left edges, an AlertDialog) or a bottom sheet (`"presentation": "screen"`: its scrim above the sheet; the message then says `a screen is presented over it (a modal or a sheet) — close it first …`) the screen beneath is not in the tree at all, and the target was not found there. An assert's `not found within …` and a flow's `wait:` on an element say the same remedy, in their parenthesis: `(a dialog is presented over it, and the tree lists only that window — close it first)` (a sheet: `a sheet or modal is presented over it, …`). `scroll_until` sends no swipe for it — one would land on the dialog's dim and dismiss it, or drag the sheet: `scroll_until … stopped before any swipe — element is not in the tree, and the next swipe would touch down at (x,y) on … — a dialog is presented over it — close it first, and a swipe would land on the dialog, so none was sent`. When that swipe would touch down beside the dialog, the failure says so: `…, and the next swipe would touch down at (540,1776) on the dim outside container (155,851 770x517) — a dialog is presented over it …` — the dim around the dialog, a touch on which closes it. Close the dialog or the sheet with its own button (they are in the tree), then repeat the step. A fully expanded sheet dumps no scrim and a full-screen dialog looks like the app's screen in the dump; for those, once a wait has found nothing (or before `scroll_until`'s first swipe), averi asks the window manager, and a Dialog's window it names gets the same remedy (`a screen is presented over it (a modal or a sheet) — close it first …`; `scroll_until` still swipes the sheet's own list, where the element may be). When the window manager says nothing usable, every `… to appear`, every `scroll_until` `element never appeared in the tree` (its stop under a keyboard over the whole screen too), every assert's `not found within …`, a flow's `wait:` on an element and an optional step's `(not present)` (a skipped `wait:`'s headline too) carry `(the tree lists only the active window: if a sheet or a dialog is open over the screen, close it first)`: if one is up, close it and repeat the step. When the window manager says the app's screen is shown alone, they carry no such line.
- **`… was not tapped: after back was pressed …` / `after id:"…" was tapped …`**: the keyboard guard hid the keyboard first, and the layout then moved the element off screen. The screen has changed; take a `screenshot`, then `scroll_until` it.
- **`either way up`** in the refusal or a `scroll_until` failure: the tree suggested the screen may be turned but nothing confirmed it, so averi counted both orientations, and the element is outside both.
- **`… to appear` with `(it matched only 0×0 nodes (scrolled off screen, or collapsed) …)`**: the selector matched only zero-area nodes. iOS (idb) reports a node scrolled above the top that way. Run `scroll_until` with `direction: up`, then retry. If it is not in a scroll view, the view is collapsed or not laid out yet.
- **`… to appear` with `(it matched only nodes clipped out above its scroll container (scrolled past it) — scroll_until it with direction: "up" first)`** (or `below` / `"down"`, Android): uiautomator reported the element scrolled wholly past its list (inverted bounds; `ui_snapshot` shows it zero-size with `clippedOut`). Run `scroll_until` with the direction it names, then retry. A plain `scroll_until` (direction down) does not turn back for an element already clipped out above on its first read.
- **`scroll_until … failed … — element was in the tree before the first swipe, clipped out above its scroll container, … — scroll_until it with direction: "up"`** (or `in tree but never intersected … — it lay clipped out above its scroll container …`, or `above the viewport` on iOS): the element lay past the edge the swipes push content out through, so the default direction carried it further away. Run `scroll_until` again with the direction it names. **`… element never appeared in the tree — if it lies above, try direction: "up"`**: the swipes moved the content and then it stopped changing without the element showing — most likely the end of the content in the direction asked, so it is probably above (or, with `direction: "up"`, below — try `"down"`) or not on this screen. A screen that only finished loading between the first two reads also counts as moved, so treat the hint as a guess, not a finding.

## Typing and fields

- **`⚠ fill … typing APPENDS`**: the field already held text and `clear` was off. The length check passed, but the content may be wrong. Add `clear: true`, unless a pre-filled value must survive.
- **`⚠ the field shows N characters for the M typed, and its text after focus was not read`** (Android, a fill without `clear` by a sole id into a field that looked empty): the field holds the value among other text, and averi did not read it before typing. A field that inserts a dial code on focus shows that, and so does one whose inserted text happens to hold the value while it refused every key. Check the value with `ui_snapshot`.
- **`Typed N characters into … — NOT verified: the matched node exposes no value`** (a `⚠ fill … NOT verified` line in a flow): the selector matched a node that is not a `textfield` and shows no text, so averi could not check the typing. (A `textfield` showing no text is empty: a fill whose characters it dropped fails with `typed N characters but the field shows 0`.) If `clear` was set, nothing was deleted either. Check the field with `ui_snapshot`.
- **`Typed N characters into … — NOT verified: the field could not be found again (the screen changed while typing)`**: the text was typed, but the selector stopped matching (typically a `value:` selector, once the value changed) and the screen's identified nodes changed while typing (an inline error went away, a notice or the keyboard appeared), so averi would not guess which node is the field. The field may well hold the text. With `(the selector no longer matches it)` the field moved, has a twin, or nothing was read before typing. Check the field with `ui_snapshot`, or select it by something that does not change as you type (`id:`). A clear alone (empty text) whose field was lost reads `Cleared … (N deletes sent) — NOT verified: …`: the deletes were sent, nobody saw the field empty. `Focused … — NOT verified: clear sent no delete …` means only the focus tap happened.
- **`⚠ … the matched node is role text, not a textfield`**: the selector found a label, not the input. Typical on iOS with `treeSource: idb`, where a floating label is its own `text` node. `clear` deletes nothing there. The line names the nearest input. It is not shown when the matched node's value changed to show the text, because then that node took it. Select it with `role:textfield` plus its `id:`, or its current `value:` when inputs share an id.
- **A fill fails with `typed N characters but the field shows M`** on a field that reformats what is typed (`0.00` becomes `1000.00`): the read-back compares the field with the value exactly when `clear` is set, and looks for it, without, in what was typed after the field's earlier text. A field that only ADDS one kind of separator between groups of what was typed passes (an IBAN grouped in fours, `1234567,89` shown `1 234 567,89`: the reply says `the field shows them reformatted`); an added `.` or `,` passes where it sits as a thousands separator, with a ⚠ line to check it is not a decimal point (`1.234` for `1234` reads alike either way), or as two or more marks grouping digits alone (a dotted date `31.12.2026` for `31122026`, no ⚠ line: two marks cannot be a decimal point). A field that adds digits, a currency or a point where no thousands mark can sit (`1.25` for `125`), or drops what was typed, cannot pass, whatever the selector — a field that grouped what landed but lost the end says so, a mark it added after the last group that landed included (`SK31 1200 ` for `SK3112000000`) (`the first 8 typed characters are there, grouped by the field …, the last 2 did not land: dropped, or refused by the field`; on iOS that tail is typed again first): retry once; failing the same way, the field refuses the rest (a length cap, or a character it does not take — an integer-only amount ignores `,`) (since 2026-10-08 a `value:` or `text:` selector is read back too). On iOS with `treeSource: idb` and no `clear`, an empty field whose placeholder's letters and digits start the value's (`+421` for `421903123456`) is read as holding that placeholder: the field grouping the whole value passes, but a tail it dropped there is not typed again and fails with a plain count — fill with `clear: true`. A field that shows every typed character in order with separators averi does not take for its grouping (a cents mask's `12.34` for `1234`, a sign, mixed or trailing marks, groups of one) says so too (`every typed character is there, in order, with N separators added …`): check the field holds the value you meant first — a cents mask shows a typed `1234` as `12.34`, an amount a hundred times smaller — and if it does, type the value as the field shows it. Type the value as the field will show it, or focus the field with `tap`, type with `type_text` without a selector (not read back), and check the result with an `assert`. Without `clear`, the field's earlier text holding the value is no fill: a field that kept its text and only the start of the typing fails — by length, or as a tail that did not land where the field grouped what it kept (a date one digit short of full, `31.12.202`, typed `12`, keeps `31.12.2021`; on iOS the missing tail is typed again first) — a length cap, or keys that went into another input (the error then names it). To replace the field's text, fill with `clear: true`. A field that shows the value itself where the value repeats the field's earlier text (`55` typed after `5`, `1212` after `12`), without `clear`, fails with `typed N characters but the field shows only the typed text, where an append would show M — the field may have replaced its text (select-all)`: a key dropped, or a field that selected its text on focus — fill with `clear: true`. Where the field shows as many characters as were typed but not the value, the reply says why the counts are no match: `…shows N, only K of them past its earlier text` (the typing landed short or changed, padded by the text the field held: retry, or fill with `clear: true`), `…exactly its placeholder: empty, or the typing turned into that text — the tree cannot tell which` (an emptied field, or an app that changed the typing — auto-capitalisation — into its placeholder's text: check the field with `screenshot`), or `…some of them bullets: the typing cannot be compared with them` (a password field still showing its last character).
- **`Cleared … (N deletes sent) — NOT verified: the field still shows M characters that the deletes did not change`**: a clear alone (empty text) whose deletes left the field showing the same text. Almost always the field is empty and shows its hint or placeholder, which the tree reports as its value (Android EditText hints, iOS placeholders). Check with `screenshot`. If the text is real, the field ignores deletes (read-only, or an input method that drops them). With a value typed after the clear, the read-back decides instead.
- **`NOT verified: the field shows exactly its placeholder's text`**: the tree source names the field's placeholder (iOS `treeSource: wda`, or an Android dump with a hint attribute), and the field shows exactly that text. It is either empty or holds that very text, and the tree cannot tell which. Check with `screenshot`.
- **`typed N characters but the field shows N — the typed text is there but for letter case`** (or `as many characters as were typed, K differing`): the app changed what was typed: auto-capitalisation, autocorrect, smart punctuation, a mask. The fill fails, because the field does not hold the value asked for — an autocorrect that only splits a word (`a lot` for `alot`, read `every typed character is there, in order, with 1 separator added`) too: a separator added between two letters passes only in a code (digits and no space, an IBAN's `MALT MTLC`). Type the value as the field will show it (`Hello`), or turn the transformation off in the app's test build. `— the field did not change: the typing did not reach it, or the field refused it` means the field shows what it showed before typing: the focus tap missed, the field ignores input, or it was already full (a maximum length). Without `clear` this holds even when the field's earlier text already contains the value (`2026` typed into a date field already full at `31.12.2026`, or into an empty field whose unnamed placeholder holds it): a field that did not change is no fill. Only a field that showed exactly the value before typing still passes. To replace the field's text, fill with `clear: true`.
- **`cannot type U+0160 'Š': … Refused before anything was sent — nothing tapped, cleared or typed.`** (`type_text`, a flow's `fill:` or `type:`): the value holds a character this project's typing cannot type, named by its code point (never the value). Nothing was sent. The sentence after `Refused …` is the way out for this project: on iOS with `treeSource: idb` it says that `app.ios.treeSource: wda` types it — WebDriverAgent types Latin, Greek, Cyrillic and Han letters, common punctuation and symbols, NBSP and U+202F; on Android, and for a value holding a character WebDriverAgent does not take (an emoji, a combining mark, an invisible format character, a script not measured such as Arabic or Hangul), there is no typing path, and the error names the character WebDriverAgent refuses: use a value without it, or enter it by hand. A flow's optional `fill:` is not skipped for it.
- **`WDA /wda/keys did not complete on port … — it may have typed part of the text, so it is not sent again …`** (iOS with `treeSource: wda`, a value idb cannot type): WebDriverAgent did not answer the typing within its budget, or its connection went. Part of the text may be in the field: read it (`ui_snapshot`) before typing more, and fill it again with `clear: true`. `WDA /wda/keys failed: HTTP … <WebDriverAgent's error>` (`invalid element state`, for one) means WebDriverAgent could not type it: see the xcodebuild log the message names. Its own message is left out of the reply, since it may hold the value. A runner that restarted is handled: its old session's refusal makes a new session and the typing is sent once more.
- **A later step fails after any `⚠ tap` / `⚠ fill` line** (an unexpected value, a submit that never happened): suspect that tap first. Check the field values with `ui_snapshot`.
- **Placeholders** exist only while the field is EMPTY on iOS. Assert them before typing.

## Soft keyboard

### Android

Success lines (the step worked):
- `the soft keyboard covered <target>; hidden before tapping`: averi pressed `back`, found the target again and tapped it. A `press_key back` before the step is not needed.
- `… could not be read` after `back`: the step also succeeded.
- `… that the input method denied; waited Nms …`: the step also succeeded.

Failure lines:
- **`⚠ … back pressed` then `✗ … back did not close it`**: nothing was tapped. Run `ui_snapshot`, then `press_key back` once more, or tap a control above the keyboard.
- **`⚠ … back pressed` then `✗ After pressing back … Timed out`**: if no keyboard was really up, `back` navigated away. Look at the screen (`ui_snapshot` / `screenshot`) before you retry.
- **`⚠ … denied; nothing sent` then `✗ … Neither back nor the tap was sent`**: Android's two keyboard sources never agreed. Look at the screen, then tap again (or `press_key back` if a keyboard is visibly up). In a flow, add a `wait:` for something that only appears once the screen has settled.
- **`⚠ fill … the input method reports a soft keyboard shown, but the window state gives it no area`** (after `dismissKeyboard: true`), or the same words on a failed or `fully: true` `scroll_until`: the two Android keyboard sources disagreed — often a keyboard still coming up. averi pressed nothing, because `back` with no keyboard up pops the screen, and it cannot tell where that keyboard is. Take a `screenshot`. If a keyboard is up, `press_key back` once. A FLOATING Gboard does not usually cause this line: on Android 13 its panel is read and handled like a docked keyboard (a tap under it hides the keyboard first, `scroll_until` judges above it, or in the strip between the panel and the band at the bottom for an element wholly there, a pixel assert fails closed on it).

### iOS (`treeSource: wda`)

averi never presses a key, because the return key submits. A covered target is hidden by tapping the first usable `app.ios.keyboardDismiss` entry, then tapped.

Success lines:
- `hidden by tapping id:"…" before tapping`
- `gone on the second look`
- `still up … but no longer over it`

Failure lines:
- **`no dismissal, nothing sent` / `none of the configured dismissals is usable …`** (each entry is listed with its reason): nothing was tapped.
  - From the tools: tap a neutral, non-interactive element (the screen title), then tap again.
  - In a flow: add such an element to `app.ios.keyboardDismiss`. Use a title or label, never a button; for a number pad's Done toolbar, add an `accessory: true` entry.
  - `covered by <role> "…"`: something drawn later sits over that entry's centre (an alert, a sheet, a bar's label). Close it first, or configure an element it does not cover. A screen-sized, non-interactive host (any non-interactive node with children, e.g. a toolbar, scrollable or webview) with nothing of its own at that point (WDA's full-screen SwiftUI `Toolbar`) is not counted as cover, and neither is a scroll view with children, of any size, with nothing of its own at that point (a form's scroll view whose frame runs under the translucent top bar while its rows start below it): only its content at the point covers (a childless scroll view still covers). A toolbar with no items at all (WDA's empty `Toolbar` frames on a UIKit sheet such as Contacts' "New Contact") is not counted as cover either, whatever its size; a toolbar with any item (a Done, a bar button) still is. Over another screen these excuses lapse: a scroll view of a modal or sheet laid in the same window over the entry's screen, or a full-screen leaf of it (its dimming view), covers the entry, which is skipped `covered by …`; a host with children there still does not. On iOS with `treeSource: wda` a layer WebDriverAgent shows presented (`ui_snapshot` marks it `"presentation"`) covers the entry whatever it holds.
  - `an alert is presented over it ("…") — close it first` (iOS with `treeSource: wda`): an alert is up over the entry's screen, and it covers the whole screen beneath it, as for a tap. Close the alert first. An action sheet or a popover reads the same way.
- **`tapped id:"…" to hide it, still covered`**: the dismissal was tapped ONCE and may have changed the screen. Take a `screenshot` before you retry, and configure a dismissal that works on this screen.
- **The keyboard's return key** (`tap: { label: search }`) is tappable. Use it only while `ui_snapshot` shows the `keyboard` band. After a `fill`, the keyboard is usually parked below the screen, and a tap there is refused as off screen.

### iOS (`treeSource: idb`, or `auto` read through idb)

idb's tree cannot say whether the keyboard is up, so averi never hides it there and presses nothing. It does see where the keyboard's background starts, and treats everything below that line as under the keyboard. `scroll_until` starts its swipes above it and does not stop on an element whose centre lies below it. A tap on such an element is refused with `is under the soft keyboard: its centre … lies below the keyboard's top edge`, and a tap moved off covered chrome never lands inside it (`nothing of it shows above the soft keyboard`). A `color` or `ocr` assert on an element that reaches below the line fails with `the soft keyboard covers the element`. A key itself can still be tapped when it shares its row with other keys; a key alone on its row inside the background is refused like content. On iOS 27 idb lists the QuickType bar (`Passwords`) as a plain button ABOVE the background, not inside it, so a tap on it presses it, as asked; an app element whose centre lies behind the bar is left out of idb's tree, as one under the keyboard is, and a tap on it times out waiting for it to appear. Two app elements side by side behind the keyboard, not overlapping, are taken for keys and are not refused. Hide the keyboard yourself (tap a neutral title), then retry.

## Screenshots, pixels and visual checks

- **`⚠ frame:` / `the screen did not settle`**: the screen kept changing (an animation, a spinner, a clock, a caret). The picture is the last capture, and `color`/`ocr` asserts and baseline creation refuse it. Wait for the animation to end (in a flow, a `wait:` for what appears after it), or hide the live content. For `color`/`ocr`, stability is judged over the element only.
- **Baselines** are created on first use under `.averi/baselines/`. Creation is refused while the screen moves. Delete the file to re-baseline.
- **`color`/`ocr` budget**: 12 s by default (tree asserts: 3 s). An assert that keeps failing spends the whole budget, so pass `timeout` when you expect a failure. An element under the soft keyboard fails closed and names both rects; hide the keyboard first. OCR is macOS-only and fails closed elsewhere. An `ocr` assert that fails with `OCR needs the Swift compiler` keeps failing until averi restarts: install the Command Line Tools (`xcode-select --install`), then restart averi.
- **`color`/`ocr` fails with `nothing of the element is drawn: it lies outside its scroll view <scroll view> (element …, screen …)`** or **`only a sliver of the element is drawn, too thin to measure: the rest lies outside its scroll view <scroll view> (element …, drawn …, screen …)`**: iOS with `treeSource: wda`. The element lies on the screen but outside the scroll view it is listed in, which draws none of it there, or only a sliver no thicker than 2 pt at the scroll view's edge. What the capture shows there is not the element, so it is never measured. Only the part the scroll view draws is judged and sampled: something drawn over its undrawn rest does not fail it. `scroll_until` the element (with `fully: true` to measure all of it) and assert again. Under a modal or sheet still up over the element's screen the message ends `… close it first; …` instead: close that screen first.
- **`color`/`ocr` fails with `… is drawn over the element`**: something lies over the element's rect, so the capture would show it, not the element. Either the status bar (the top band the device reports; on iOS the top safe-area inset, 62 pt on a 402x874 iPhone; on Android the visible system status bar, 66 px on a 1080x2220 phone, which an app drawn edge-to-edge lays its top under) or another element of the app drawn over it, named with its rect (a pinned button bar, with `reaching …` for the area below it that the bar's background hides, a floating tab bar, a title laid over a scrolled row). Every part of the rect counts, not only the centre a tap presses. An overlap of 2 units or less (pt on iOS, px on Android) does not count, and neither does the element's own content or a transparent clickable layer over it. A wrapper with children laid over it can count, such as a floating action button's full-width host (see the covered-tap entry under "A tap target off screen"), and so does a modal's full-screen dimming view or a sheet's scroll view over the screen beneath. `scroll_until` the element with `fully: true` first, then assert again. On Android a text that lies only over the margin of the element's touch target (Compose dumps a control's touch target, 48 dp tall, past what it draws, so the next field's title overlaps a field's bottom by a few px) is judged on the frame the assert captures: where the overlap shows nothing but the element's own colour beside the text, it does not count; when the message still names it, the frame showed it drawn over the element, or could not tell (an unsettled frame, no plain colour of the element's beside the text) — check with a screenshot. When no scroll moves it out (it is pinned, or the cover holds all of it), the message says so: assert something in it that lies clear of the cover instead. Under a modal or sheet still up over the element's screen the message ends `… a screen is presented over the element (a modal or a sheet) — close it first; no scroll moves the element out from under that screen` instead, whatever else lies over it (the status bar, a possible cut at the navigation bar): the message still names what lies over it, and this replaces its own advice. Close that screen, then assert again. Under an alert (iOS with `treeSource: wda`), which covers the whole screen beneath it, the message ends `… an alert is presented over the element ("…") — close it first` instead: tap the alert's button that closes it, then assert again (an action sheet or a popover reads the same way). A keyboard the device reports over the element is still named first, with its own advice. Only what the assert reads counts: the whole rect for `ocr`; for `color` the part of the rect on the screen, less 12% on each side of it — the region its sampler reads, so a sliver of an element at the screen's edge is judged on the sliver it would measure. So an element that reaches into the status bar by design (a full-bleed header, on iOS or in an Android 15+ app drawn edge-to-edge — an app bar at 0,0 1080x220 under the 66-px bar; a whole screen) fails an `ocr` assert, and a `color` assert only if the bar reaches into its sampled middle (that app bar's does). The message then leads with the cure: for the header, assert its title; for a whole screen, something in it that lies clear of the bar. On Android the navigation bar at the bottom of a portrait screen counts too (the visible bar the device reports, from y 2154 on a 1080x2220 phone), named `the navigation bar` with its rect.
- **`color`/`ocr` fails with `nothing of the element lies on the screen (element …, screen …)`** or **`only a sliver of the element lies on the screen, too thin to measure (element …, on the screen …, screen …)`**: nothing of what the assert reads lies on the screen (below the fold, above the top, past a side), or the screen's edge leaves only a sliver of it no thicker than 2 units (pt on iOS, px on Android), too thin to measure — its few rows would be whatever lies at the edge, so it is never measured. The assert keeps polling to its deadline. Scroll it on-screen (`scroll_until` it, with `fully: true` to measure all of it) and assert again. Under a modal or sheet still up over the element's screen the message ends `… a screen is presented over the element (a modal or a sheet) — close it first; …` instead: close that screen first.
- **`color` fails with `the element has no area (rect …)`**: the element's rect is collapsed to no width or no height — a node idb lists as 0x0 once scrolled off the screen (above the top: run `scroll_until` with `direction: up`), or an Android node whose bounds come back inverted and clamped flat — so there is nothing to sample. Assert a child that has area, or scroll the element back on-screen first.
- **`ocr` fails with `… may be cut at the navigation bar`** (Android): the element's bottom lies on the navigation bar's top edge, inside a scroll container that ends there too, so the tree cannot tell a whole element from one the bar cuts. Scroll it up (`scroll_until` with `fully: true`) and assert again. A `color` assert on it is measured.
- **`scroll_until … fully: true` fails with `it stays partly under the status bar` or `… the navigation bar`**: with `fully: true` none of the element may lie under a system bar past 2 units (pt on iOS, px on Android) — the rule a `color`/`ocr` assert applies — and swiping no longer moves it out (a last row under an edge-to-edge navigation bar), or the swipes ran out first. Content no scroll can lift out of a bar is exempt and stops as before: in no scroll view, a full-bleed header laid from the screen's top edge at full width, a full-width surface laid to its bottom edge (a bottom sheet), or an element the size of the screen; or screen-sized scroll content taller than the room between the bars — a pixel assert on it still fails closed, so assert something in it clear of the bar. Its centre is clear of the bar; when the message adds that a plain `scroll_until` stops on it and a tap lands, nothing is drawn over its centre either. To measure it, assert something in it that lies clear of the bar.
- **`scroll_until … failed after N swipes — element is in the viewport but cut at its <edge> edge by <node> …, drawn after it … — and the content is exhausted: … The rest of it may stay under that <role> at the end of the content — … — or it is only that thin, laid flush against it; a tap refuses it so cut (…)`** (Android): the element is a control dumped as a strip under the tap minimum against something drawn after it, and no swipe brought more of it out — no stop rests on such a strip (`fully: true` neither). When the sentence says `the soft keyboard is up …: dismiss it first (press_key back …) — a bar riding on it goes down with it, and scroll again`, hide the keyboard and run `scroll_until` again; when it says `a layout defect (no clearance for a pinned bar?)`, the app leaves the element under that bar at the end of its content. Only if a `screenshot` shows the element whole and that thin, tap it by coordinates. At a bound (maxSwipes, the timeout) the failure says `stayed cut at its <edge> edge by <node> … — a tap refuses it so cut (…)` with the same remedy.
- **`scroll_until … fully: true` fails with `… and it is N wide (tree units), as wide as its scroll view …: fully: true holds at one exact scroll offset only, which no swipe can be aimed at — drop fully: true, or accept what it shows`** (or `… tall …`, or `… wider than its scroll view …: no scroll offset shows all of it — drop fully: true, or accept what it shows`): the element is as large as its scroll view along that axis, or larger, so no swipe can show it whole — the scroll stopped at once instead of swinging it to and fro until maxSwipes. Not a layout defect and not a budget to raise. Drop `fully: true` (a plain `scroll_until` stops once its centre is in view, and a tap works there), or accept the share the reply quotes; a rect assert or a screenshot then measures the clipped box, so assert on a part of the element that fits (a child inside it). With `(the tree does not say which way it scrolls: the swipes over it moved the element sideways)` after the scroll view, the tree gives that scroll view no axis (a Compose lazy row), and the swipes of this call showed it moving the element along it — the same answer.
- **`scroll_until` reply names clipped edges**: the element only intersects the viewport (a floating nav bar is a common cause). Use `fully: true` before a `rect` assert or a screenshot, or you measure the clipped box.
- **`scroll_until … fully: true` fails with `… element is in the viewport but cut at its bottom edge by <node> (x,y WxH), drawn after it — the dump (Compose's, on Android) leaves out of a node's bounds what a later node covers, so the rest of it may lie under that <role> — and the content is exhausted: …`** (Android; or `top edge`), with no share of it given: the element lies in no scroll view, and the node drawn after it runs across its whole edge and past it at both ends (a button bar pinned over a column with margins). uiautomator dumps the element cut where that node begins, so averi cannot say how much of it lies under it, and does not call it fully visible. The pixel assert fails closed the same way: **`color`/`ocr` fails with `<node> meets the element's bottom edge (element …), drawn after it — … so the rest of the element may lie under that <role>`**. A tap at the element's centre is still taken (the cut leaves the centre clear). To measure it, assert on a node inside it that lies clear of the bar, or take a `screenshot`; `rect` reports the cut bounds only. A row in a list is never read this way: at rest a list's first row lies whole and flush under a sticky header, a dump identical to a row the header cuts, so averi leaves it to the scroll.
- **`scroll_until … fully: true` fails with `… under text "…" (x,y WxH), drawn over it — N% of it shows — a screenshot shows it drawn over its bottom N px`** (or `— a screenshot could not tell whether it draws over it (<why>)`; Android; `top` alike): the text lies only over the margin of the element's touch target (Compose dumps a control's touch target, 48 dp tall, past what it draws: the next field's title over a field's bottom edge). One screenshot was asked whether it paints anything there. Where every pixel of the overlap is the element's own colour beside the text, `fully` is met and the reply says so (`fully visible after N swipes — text "…" (…), drawn after it, overlaps its bottom N px with nothing a screenshot shows …`). `shows it drawn over` means the text draws ink or a background of its own over the element. When it scrolls with the element (the next field's title in the same list), the first read after a swipe that carried the two together ends the call: `failed after N swipes (the text drawn over it moved with it, both by dx,dy since a screenshot saw it there: it scrolls with the element, so no swipe brings the element out from under it) — …` — the app's layout, not the scroll; check with a `screenshot`, and drop `fully: true` or assert on a node clear of the text. A text that stayed where it was while the element moved (pinned over the list), or that moved with the list's own container (a sheet dragged), is asked again where the swipe left the two. `could not tell` (a blended frame, no plain colour beside the text): it is asked again after a swipe that moves the two; else take a `screenshot`.
- **`scroll_until … fully: true` says `fully visible` but the element is partly hidden (Android)**: uiautomator reports a node's bounds clipped to its scroll container, so the part under a pinned top bar is not in the tree and averi cannot see it. Compare the element's height with its siblings' in `ui_snapshot` (a short one is clipped), and take a `screenshot` before a `rect` assert on it. A node that carries `cutBounds` in `ui_snapshot` was dumped cut short of its own children (something drawn over part of it, such as a sticky header); averi judges it by its children's extent, the `rect` shown. A row whose touch target overflows into the next row of its list carries `cutBounds` too: one dump cannot tell the next row from a sticky header, a permanent limit.
- **`scroll_until` reply or failure ends `; the sheet moved from its Half screen detent to Expanded`** (iOS): the sheet's grabber (`Sheet Grabber` in `ui_snapshot`) reported another detent at the scroll's last read than at its first: the sheet moved during the call. The usual cause is a swipe on a half sheet's list at its top, which drags the sheet up before it scrolls the list; a call that sent no swipe says it too, when the sheet moved on its own between two reads. The verdict before the note stands as it is; the screen is now in another state, so check the sheet (or drag it back) before steps that assume its old height.
- **`scroll_until` reply or failure has `; 1 swipe up did not move it — the tree lists the content of <scroll view> ending at its top — so averi turned down, as the tree places the element below it`** (iOS with `treeSource: wda`): the step asked for the wrong direction. The swipe that way moved nothing, the tree lists that scroll view's content ending there, and it places the element past the scroll view's other end — so averi turned once and swiped the other way itself. The verdict stands as it reads. `3 swipes up, the last of which did not move it` means the swipes before it did move the list (a bounce at its end). Fix the step's `direction` (here `down`), so the next run does not spend a swipe on the wrong way.
- **`scroll_until … failed after 1 swipe (swiping up did not move it: the tree lists the content of <scroll view> ending at its top — content exhausted) — …`** (iOS with `treeSource: wda`; `did not change the screen` for an element not in the tree): one swipe was enough to prove the end, because the tree itself lists where that scroll view's content ends, so no further swipe that way can bring anything in. Elsewhere (Android, idb) averi needs 2 swipes that move nothing, and says `content exhausted, or the swipes were not taken`: a swipe not taken moves nothing too. Read the text after the dash: it says where the element was last seen and which `direction` reaches it, or that it is not in the tree — then it is not in this scroll view at all (another screen, another tab).
- **`scroll_until … failed after 2 swipes (the last 2, swiping right, did not change the screen: each went across the scroll view it was drawn over, 0,0 1080x2220, which scrolls vertically, and the tree shows no scroll view that may scroll horizontally — … then scroll_until it; else: content exhausted, still loading, or the swipes were not taken) — …`** (Android): the swipes went over the page, which scrolls up and down, because the tree shows nothing on it that scrolls sideways. A carousel Android dumps as neither scrollable nor clipping is not seen as one. Find the list in `ui_snapshot` or a `screenshot`, `swipe` inside it by coordinates (from its right part to its left, on its middle row), then `scroll_until` the element again. A list the tree shows as scrollable is swiped inside without this. When the tree does show one that scrolls sideways but the swipes did not go over it (beside the page, not in it), the reply names it instead: `… and the tree shows <scroll view>, which scrolls horizontally, and which the swipes did not go over — scroll_until it again with within: {"x":…,"y":…,"width":…,"height":…}`: call `scroll_until` again with that `within` (copy it as it stands), and the swipes go inside that list until the element is read. With `, but which had no room for a swipe — swipe inside it (swipe, its coordinates), then scroll_until it` it is too small for one: swipe inside it as above (the same words come when the element was already read in another scroll view, where `within` no longer counts).
- **`scroll_until … failed after 2 swipes (the last 2, swiping down, did not change the screen: the swipes went over the scroll view 0,303 1080x605 only; the tree shows another scroll view that scrolls vertically, which the swipes did not go over: scrollable (0,1046 1080x495) — … scroll_until it again with within: {"x":0,"y":1046,"width":1080,"height":495}; else: content exhausted, still loading, or the swipes were not taken) — …`** (Android, iOS with `treeSource: wda`; `were drawn over the screen whole (aimed at no scroll view), touching down at x,y inside the scroll view …` where WDA marks none clipping): the element is not in the tree yet, and averi cannot tell which list holds a row it never saw, so it swiped the largest (or the screen) and never another list on the same screen. When the element belongs to the named list, call `scroll_until` again with `within:` that list — its rect as the reply gives it, or a selector of an element inside it (`within: 'id:…'`) — and the swipes go inside it until the element is read; with several named (each `<scroll view> as within: {…}`, then `… lies in one of them, scroll_until it again with that one's within`), pass the `within` of the one that holds it. "Did not go over" means no swipe of the call touched down in it. Up to 3 are named, largest first, then `and N more`. The same clause comes before `else: raise maxSwipes or timeoutMs` at a `(maxSwipes: …)` or `(timeout …: …)` stop — raising the bound alone swipes the same list again — and inside a `they touched down at … (else: …)` clause. With `treeSource: idb` nothing is named: idb lists no scroll view.
- **`scroll_until … fully: true` reply opens `visible after N swipes, NOT CONFIRMED WHOLE: …`** (or `NOT CONFIRMED UNCOVERED: …`, `NOT CONFIRMED WHOLE OR UNCOVERED: …`; `visible by the tree after …` when a screenshot could not tell either): the stop is a success, but averi could not confirm what `fully: true` asks — an edge of the element lies where Android may cut it and no probe checked it (WHOLE; the entries below name each reason), or the input method reports a keyboard nothing could place (UNCOVERED, the `⚠ fill` entry above). It never opens with `fully visible` then: a reply that does is a checked or clean stop. Do not measure the element on this reply: take a `screenshot`, or call `scroll_until` again (its probe may settle it). In a flow the line is marked `⚠ scroll_until`. Before 2026-11-09 the same stop opened `fully visible after N swipes; but …`.
- **`scroll_until … fully: true` reply says `… and every scroll container around it from that one outward scrolls only sideways, so no probe swipe can move its top edge into view to check it — it may be cut there, a rect assert or screenshot may measure part of it`** (Android; `up and down` for a left or right edge): the element's edge lies on its scroll container's, where Android cuts a node's bounds, and the only scroll containers around it scroll across that edge (a card in a horizontal carousel with no vertical list around it), so the probe swipe that checks such an edge was not sent: it would move nothing. Take a `screenshot` before a `rect` assert or a screenshot check on it.
- **`scroll_until … fully: true` reply says `its top edge lies on the edge of <node> (x,y WxH), pinned at its scroll container's (…) top and drawn after it`** (Android; `left` alike): the element lies flush under a node pinned at the start of its own list — a sticky header Compose cuts the rows at — and the dump of a row the header cuts is the same as one lying whole under it. With `and 2 probe swipes toward it moved nothing — nothing of it is cut there` two probes moved nothing, which reads as whole: measure it (two probes in a row the app did not take read the same, ADR 0013's T12 amendment). With `then 2 swipes after it moved nothing`, see the entry below. With `NOT CONFIRMED WHOLE: … and no swipe or time was left to check it` (or another reason), it may lie partly under that header: raise `maxSwipes`/`timeoutMs`, or take a `screenshot`. With `NOT CONFIRMED WHOLE: it spans its scroll container (…) from the edge of <node>, pinned at the container's top …, to the container's bottom edge`, the element runs from under that node to the list's far edge, and no probe can tell which end is cut: take a `screenshot` before measuring it. The colour and ocr asserts cannot tell this (they have no probe) and sample what the dump lists of such a row: run `scroll_until … fully: true` on it first, then assert.
- **`scroll_until … fully: true` reply says `visible after N swipes, NOT CONFIRMED WHOLE: its <edge> edge lies on … and a swipe toward it showed P px more of it, then 2 swipes after it moved nothing — the content ended there or the app did not take them — it may be cut there, a rect assert or screenshot may measure part of it; calling again tells`** (Android; any edge, a scroll container's or a pinned node's): a swipe proved part of the element lay past that edge, and two swipes after it moved nothing (a reveal and its retry, each counting as a swipe). averi cannot tell whether the content ended there or the app did not take them, so do not measure it yet: call `scroll_until` again and read its first probe. Holding (`after 2 swipes`, `2 probe swipes toward it moved nothing — nothing of it is cut there`) reads as whole; two probes in a row the app did not take read the same (ADR 0013's T12 amendment). Moving the element tells "cut", not "whole": in the lab's carousel with C cut, the repeat moved C 8 of 8, and all 8 ended on `maxSwipes` with C still cut (that card is as wide as its carousel).
- **`scroll_until … fully: true` fails `… element reached the viewport but its bottom edge still lies on its scroll container's (…), where Android cuts a node's bounds to the container, and a probe swipe toward it showed N px more of it — part of it lay past that edge, so it may still be cut there`** (Android; any edge, or `the edge of <node> … pinned` for a sticky header): the probe swipe moved the element and more of it showed on that same edge, so part of it lay past the edge before that swipe — it may still be cut (or the swipe brought the last row whole to its list's end) — and no swipe or time was left to reveal the rest or check. Raise `maxSwipes` or `timeoutMs` (with them, the next swipe reveals the rest in one stroke — unless the swipes have measured that another would most likely overshoot, the `more swipes are unlikely to help` failure below), or scroll it further in before asserting. A repeat call's probes may tell: holding twice, it reads as whole; moving it, it reveals on. A raised budget can lead to the `then 2 swipes after it moved nothing` reply above. With `, and no scroll container around it has room for a swipe to reveal the rest` (the screen changed after the probe: a keyboard or an overlay came up), or `… scrolls only sideways, so no swipe can reveal the rest` (the screen changed after the probe: the list around it now scrolls only across), or `, and the swipe that followed to reveal the rest moved nothing but was too short to tell from a tap` (the row nearly fills its list: too little room for a longer reveal), or as a stuck failure (`… and swiping down no longer moves it`), more budget does not help: take a screenshot to see whether it is cut, and dismiss what came up before scrolling again.
- **`scroll_until … fully: true` fails `… stopped after N swipes, without swiping further — element is on screen but its <edge> edge still lies on its scroll container's (…), … in this call a K-px swipe, no longer than the next would be, moved it P px, and only M px of room remain on its <side> side, so another swipe would most likely push its <side> side out past its scroll container rather than show it whole — act on the part that shows (a tap, or an assert on a child inside it), or drop fully: true; more swipes are unlikely to help`** (Android): a probe swipe proved the element cut at that edge, and the swipes that revealed the rest measured how far even the shortest of them carries it — farther than its other side has room left, so the next one would most likely cut that side instead (a drag's carry varies a few px, so now and then one more swipe would have fit; the stop saves the swipes that usually do not). Usual for a card about as wide (or as tall) as its carousel that the dump lists cut to it (a RecyclerView's). Not a layout defect and not a budget to raise: the element is on screen — tap it or assert on a part of it that fits (a child inside it), or drop `fully: true` (a plain `scroll_until` stops once its centre is in view).
- **`scroll_until` reply says `above the soft keyboard over [x,y][x2,y2]`**: the keyboard was up. The viewport was the screen above it and the swipes started there. A part under the keyboard does not count as visible. With `fully: true` it fails if the content ends with the element still under the keyboard. A keyboard over the whole screen fails at once. Hide the keyboard first (`press_key back` on Android, a tap on a neutral title on iOS; in a flow, `dismissKeyboard: true` on the fill before), then scroll again.
- **`rect` fails with `… CONTENT width`**: no trustworthy screen width was found. On iOS, set `treeSource: wda`.
- **`text` assert fails, but the hint says the string is inside a longer label**: iOS merged the labels. Use `match`, not a bug report.

## Layout contracts (`verify` with `contract:`)

- **`## rect parity`**: per-anchor deltas against the contract and android-vs-ios. The `aspect` row compares shape even for sides nobody pinned. Set `aspect: false` on an anchor only when the platforms derive a side differently by design, e.g. Android's 48 dp touch-target floor against iOS's 44 pt, and write the reason beside it.
- **`## color parity`**: android-vs-ios at `tolerance_de` (8), against the contract at 1.5×. A single-platform run gets only the looser axis and can miss a real drift (measured dE00 10.19 under 12), so set `tolerance_de: 6` in the contract for single-platform work. Strokes of 1–2 px are invisible to sampling; judge them from the screenshot.
- **`## text parity`**: the `src` column says `ocr` (what renders) or `tree` (the weaker fallback). Use `text_dynamic: true` for amounts and dates.
- **`OCCLUDED` (`UNREAD, cause not determined`)**: averi could not read the anchor. Something covers it (usually the keyboard), or it has unreadable contrast, which is a finding in itself. Open the screenshot to tell which.
- **Copy differs between platforms**: check Figma for which side is right before fixing either.

## Launch and logs

- **iOS `⚠ … after launching <app>, the UI tree was still …`** (the second line of a `launch_app` reply, or a `⚠ launch` trace line; the idb tree source, or `auto` before its first tree read): averi waited 3 s for the tree to show the launched app and it still showed another app, or SpringBoard. A read now may judge the wrong app, and an `absent` check would pass on it. The screenshot does not settle it: it shows the launched app before idb's tree does. Read again before you trust the tree. Only when a read 20 s or more after the launch is still labelled so, while the screenshot shows the launched app, is that label the app's on-screen name (a localized display name), and the note can be ignored — the note itself says when that reading is ruled out.
- **iOS `⚠ … after launching <app>, WebDriverAgent still read <other> as the active app …`** (`treeSource: wda`): for 3 s WebDriverAgent named another app — or SpringBoard: the home screen, the launch animation or a system alert — as the one it reads. A `ui_snapshot` now reads that app's tree, and an `absent` check would pass on it. A bundle id is exact, so this is never the launched app under another name. Read again; if it repeats, take a `screenshot` — a system alert may be in front.
- **iOS `⚠ iOS has not brought <app> forward yet: a system alert is up, "<title>" — buttons "<label>" at (x, y), …`** (the second line of a `launch_app` reply, or a `⚠ launch` trace line; either tree source): the launch happened, but a system alert is in front — usually an unanswered "Open in “<app>”?" left by an earlier link — and every launch stays behind it until it is answered. Reading again does not help. averi tapped nothing. `tap text:"<label>"` for the button you mean, its label as the line quotes it — or `tap` at the x/y the line gives, when the label holds a `"` or two buttons share it — then read again before you trust a read.
- **iOS `iOS has not opened <url> yet: it asks "<title>" — buttons "<label>" at (x, y), …`** (or `… a system alert is up, "<title>" …`; the whole `open_deep_link` reply): iOS shows a system alert instead of opening the link — for a link to the project's own scheme, "Open in “<app>”?", seen only when the simulator ignored or refused averi's pre-approval of the scheme (averi records the Open answer before every such link; a refusal also puts "averi: could not pre-approve" on stderr) — and every `launch_app` stays behind it until it is answered. averi tapped nothing. `tap text:"<label>"` for the button you mean, its label as the reply quotes it — or `tap` at the x/y the reply gives, when the label holds a `"` or two buttons share it — then read again.
- **iOS `⚠ averi did not see <app> come forward after the link: …`**, **`⚠ averi could not check that <app> came forward after the link: …`** or **`⚠ whether <app> came forward after the link was not checked (WebDriverAgent is not running yet)`** (the second line of an `open_deep_link` reply, for a link to the project's own scheme): for 3 s the tree source named another app, or could not tell, or was not asked. Most likely iOS is asking "Open in “<app>”?" — it does when the app is not in front and the simulator ignored or refused averi's pre-approval of the scheme (a refusal also puts "averi: could not pre-approve" on stderr) — and the link waits behind the alert, as does every `launch_app` until it is answered. Take a `screenshot`; if it shows the alert, `tap text:"<label>"` for the button you mean — `text:"Open"` opens the link, `text:"Cancel"` drops it (the labels as iOS shows them) — or `tap` at its x/y. Otherwise the rest of the line is `launch_app`'s note for the same case, above: read again before you trust a read.
- **iOS `⚠ could not check that <app> is in front (…)`**: averi could not tell which app the tree shows, and the parentheses say why. The tree may still be the previous app's. Read again before you trust a read (the screenshot switches before the tree).
- **Android `Android has not opened <url> yet: its chooser (<component>) is in front, asking which app opens it. …`** (the whole `open_deep_link` reply): two activities handle the link and none is the device's default, so Android shows its "Open with" chooser instead of opening either. Until it is answered every read is the chooser's — a selector for the app misses, and an `absent:` assert passes without the app on screen. averi tapped nothing. Take a `ui_snapshot`, `tap` the app you mean, then "Just once" if it shows — never "Always": it makes that app the device's default for such links, and every later run inherits it. `press_key back` drops the link. To avoid the chooser, give the link to one activity in the app's manifest. A bare `Opened` for such a link means averi did not see the chooser at its one read (it was not in front yet, or it is an OEM's own): take a `screenshot` when the handler matters.
- **iOS `No app on this simulator handles <scheme>: links, so nothing opened (…code 115)…`** (the whole `open_deep_link` reply, an error): simctl found no app for the scheme. The simulators measured so far have no `tel:` handler. For a link to your own scheme, check that the app is installed.
- **Launch opened LeakCanary (or another launcher)**: set `app.android.activity`.
- **`Android started no activity in <package> for this intent`**: no exported activity matches the intent, or the matching one refused it. The quoted `am start said:` line tells which.
- **`get_logs`**: always pass `grep`, a case-insensitive regex. Only the last `maxLines` (400) come back, and the header says how many matched. Narrow the regex before you widen the tail.
