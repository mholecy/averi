# Troubleshooting averi output

Find the line or error you see, then act on it. Each entry gives the meaning, then the action.

## Traces and the ladder

- **`✗ <step> — failed — <reason>`**: the step that failed. Steps log only on success, so the line before it is the last step that worked, not the culprit.
- **`✗` followed by `⚠ reach <flow>`** inside an `ensure_state`: that rung failed and the ladder went on to the next one. It is not the headline error. Fix the rung anyway, because it only costs time.
- **`⚠ reach <flow>: this rung is DESTRUCTIVE`**: averi is about to wipe the app's data. **`⚠ clearState` + count**: it did. A count that climbs while you debug means stop re-running.
- **`⛔ reach <flow>` / `Refused to run reach flow …`**: averi refused a destructive rung because the screen was unreadable or still bare after a ~20 s second look. Nothing was wiped. Take a `screenshot` and retry once the screen has rendered. If the screen shows only unlabeled icons, it reads as bare too; `run_flow` the rung yourself if you mean it.
- **`⚠ detect: <condition> treated as not detected — …`**: a probe that read nothing usable (`(second look over 20 s)` on the second look). It is a diagnostic, not the failure.
- **`↻ recovery <state>`**: the earlier safe rungs ran once more because a late screen beat the ladder. **`↻ no recovery`**: the call's one pass was already spent. **`⚠ recovery` / `⚠ salvage`**: the pass reporting its own stumbles, never the cause.
- **`could not be checked`**: a state with no reach flows met an unreadable tree. Take a `screenshot` first.

## The tree is empty, bare or unreadable

- **`ui_snapshot` returns `[]` plus `0 matches for … in a tree of N nodes`**: the tree has content and none of it matches. If the screen may still be loading (a spinner, an overlay), confirm with an `assert` with a `timeout`, or with a `screenshot`.
- **`[]` plus `⚠ … the tree is bare`**: the tree is empty or unrendered. On iOS right after `launch_app` it may hold only the status bar and the app's icon; that is SpringBoard, not the app, and is bare too. Take a `screenshot`. If the screen is rendered, the tree source is stuck; do not read the element as absent.
- **iOS `idb returned an empty accessibility tree …`** (a lone 0×0 `Application`): a stuck idb, or the first second after `launch_app`. If it says `retried once after 1 s`, it is still stuck. Recover in this order:
  1. `terminate_app`, then `launch_app` (only a new process recovers);
  2. the simulator reboot the error names;
  3. or `app.ios.treeSource: wda` as an alternative source.
- **Android `device <id> is not reachable: adb get-state says "device offline"`**: recover the emulator (wait for `adb devices` to show `device`, else `adb kill-server && adb start-server`). Do not call `ensure_state` meanwhile: its probes read nothing.
- **Android `device <id> is not answering: adb get-state timed out`**: adb itself hangs, not the app. Run `adb devices`; if it hangs too, `adb kill-server && adb start-server`, otherwise restart the emulator (or reconnect the USB cable).
- **Android `… is unauthorized` / `… is offline`** (`No usable Android emulator/device found`, `select_device`, or a selected device): adb lists the device but cannot drive it. Unauthorized: unlock the phone and accept the "Allow USB debugging?" prompt; for an emulator, `adb kill-server`, then `adb devices`. Offline: wait for `adb devices` to show `device`, else `adb kill-server && adb start-server`.
- **Android `is still settling`** (uiautomator's null root right after a launch): take a `screenshot` (it waits for stability), then retry.
- **Android `is reachable but SLOW`**: the host is under load. The app is not dead.
- **`scroll_until … failed after 38204ms (timeout 15000ms; no swipe was sent; 1 tree read took 38204ms) — …`**: the scroll ran out of time, and the text after `—` says only where the element was at the last read. The parenthesis says what spent the time: the time taken, the budget (`timeoutMs`), the swipes sent and how long the tree reads took (in all, and the last one). The budget is checked once a round, after its tree read and keyboard queries, so the time taken can pass `timeoutMs` by one swipe, the settle after it and one more round — its tree read and, on Android, its keyboard queries — and includes them. When the reads took most of it, especially with no swipe sent, the tree source was slow or restarting (a WebDriverAgent restart is reported on the averi server's stderr, not in the reply); the content is not at fault. Retry the step, and check the server's stderr if it recurs. When swipes were sent and the reads took little of the time, the swipes did not bring the element into view in time: pass a larger `timeoutMs`, or check the selector and `direction`.
- **`absent` assert fails with "could not verify"**: the tree was bare. Absence is never passed on an empty screen.

## iOS: an `id:` misses an element that is on screen

Under the default `treeSource: idb`, this is expected:
- React Native `testID` on a static `Text` or a container is invisible, because idb returns only accessibility elements;
- the same applies to a SwiftUI identifier on an `.accessibilityElement(children: .contain)` container.

Do not restructure app code (a `Pressable` wrapper, blanket `accessible={true}`) to please the tool. Set `app.ios.treeSource: wda` in `averi.yaml`:
- `id:` then resolves on static text and containers, as on Android;
- taps, typing and install stay on idb/simctl;
- tree reads are ~2× slower, and the first WebDriverAgent build per Xcode version takes minutes and needs `xcodebuild`.

WDA comes from `appium-webdriveragent`, an optional dependency of averi. If an install skipped it (`--omit=optional`), the error names the package.

Alternatively, detect on a button or row id.

## A tap target off screen

- **`… is off screen at (x,y) on a WxH screen … — scroll_until it first; nothing was tapped`**: the element is in the tree but its centre is outside the screen. iOS keeps a scroll view's content below the fold in the tree with real rects. Nothing was tapped, so focus did not move. Run `scroll_until` for the same selector, then tap again (unless the refusal says a screen is presented over it: see that entry below).
- **`… only N% of it … is on screen … — scroll_until it with fully: true first`**: the element is clipped at an edge with its centre outside. Since 2026-10-09 a plain `scroll_until` also keeps scrolling until the element's centre is on screen (and clear of anything drawn over it), so either works; pass `fully: true` when the next step measures the element.
- **`… is outside its scroll view <scroll view> at (x,y): nothing of it is drawn (rect …) — scroll_until it first; nothing was tapped`** (or `only N% of it (rect …) is drawn, and a tap goes to its centre — scroll_until it with fully: true first`): iOS with `treeSource: wda`. The element's centre is on the screen, but outside the scroll view it is listed in. WebDriverAgent lists a scroll view's content at its laid-out rect even past the scroll view's frame, and the scroll view draws none of it there: what shows at that point is something else, such as the background below a form that ends above a pinned button bar. Nothing was tapped. Run `scroll_until` for the same selector, then tap again. With the keyboard up, the keyboard is hidden first and the element judged again, since a scroll view laid out above the keyboard grows back.
- **`… is cut at its scroll container's bottom edge (container …); only a WxH part of it shows, N deep across that edge, under the M a tap needs — scroll_until it first (if it is whole …, tap a child of it that lies clear of that edge, or tap by coordinates); nothing was tapped`**: the element's centre is on screen, but its scroll container cuts it to a strip too thin to tap (Android; a strip that thin had taken the tap and done nothing). Run `scroll_until` for it, then tap again. A cut at the top or a side names the `direction:` to pass. `scroll_until` does not stop on such a strip either. If it fails with `… cut at its scroll container's … edge … and the content is exhausted`, the list has no room to show the element whole, or the element is whole but its content touches that edge, which averi cannot tell from a cut. Then tap a child of it that lies clear of that edge, or tap by coordinates. averi refuses only when the tree shows the element runs on past the edge, or when the element touches the edge inside something cut there to such a strip: then the message adds `as is the … it lies in` and says to tap something in what it lies in that lies clear of that edge, or by coordinates: a child touching the cut is no better than its parent. A whole small element that merely touches the edge is tapped. A cut element with no children cannot be told from a whole one, and is tapped, unless what it lies in is refused at that edge. A whole thin row at a list's top with a hidden child laid out above it (a swipe-action view) reads as cut and is refused; tap a child of it that lies clear of that edge, or tap by coordinates.
- **`… is under <cover> (x,y WxH) at its centre (x,y), drawn over it; only a WxH part of it shows … — scroll_until it first; nothing was tapped`**: something the app draws later lies over the target's centre (a pinned button bar, a floating tab bar), and too little of the target shows beside it to move the tap there. Run `scroll_until` for it, then tap again (unless the refusal says a screen is presented over it: the next entry). A wrapper with children (a `container` or an `other`) laid after the content counts as drawn over its whole rect, unless, among others, it is the screen's size (90 % of it or more), or it has no label and no value and holds the target together with the target's whole scroll view, or it has no label, value or identifier and holds only empty frames: the tree cannot tell a host that swallows touches (a tab bar's) from a transparent one that only positions its child. So on Android a target beside or under a floating action button can be refused naming the FAB's full-width host (Clock's `container id:fab_container`), and a `color`/`ocr` assert there fails closed on it. When the wrapper holds one child only, a control of at most a quarter of its area, the refusal ends `… — the wrapper may only position its one child, <child>: tap that child when it is the target; otherwise scroll_until this element out of the wrapper's band first` instead; a wrapper of several children (a tab bar's host) gets no such line.
- **`… a screen is presented over it (a modal or a sheet) — close it first; no scroll moves it out from under that screen`** (tap or `scroll_until`): the target lies on the screen beneath a modal or sheet that is still up — whatever else keeps it from a tap (its centre under that screen, off the screen or under the status bar — wholly too, since the screen is judged presented over the target itself, wherever it lies — or a cut at its scroll container's edge), a tap says this in place of that remedy (`scroll_until it first`, the status bar's advice); nothing was tapped and no further swipe was sent. `scroll_until` says it as `… a screen is presented over it (a modal or a sheet) — close it first; no scroll moves it out from under that screen, and a swipe on it may dismiss it, so none was sent` (or `so no further swipe was sent`). Close or finish that screen (its close button, Cancel, Done), then repeat the step. On iOS with `treeSource: wda` that screen is a layer WebDriverAgent shows presented — it reports every node of the screen beneath not visible while the layer shows, and `ui_snapshot` marks the layer `"presentation": "screen"` — and the refusal names what of that layer lies at the point (a row, its title, the sheet's container), the layer itself (`container (0,0 402x874)`) where nothing of it draws there. If no modal is visible on the screenshot, WebDriverAgent may have read the screen mid-animation (repeat the step), or — on a tree that carries no such mark (Android) — the app may keep a full-screen dimming view or scroll view laid over the screen after closing it: report the tree with `ui_snapshot`. A full-screen host that only carries a bar or other content of its own (a host with children: Safari's full-screen host of its bottom bar) is no such screen: only what it draws covers. `scroll_until` says the same when the target is in the tree but not in the viewport (below the fold, under the soft keyboard, cut) and the next swipe would touch down on such a screen: `… — element lies below the viewport, and the next swipe would touch down at (x,y) on <that screen's dimming view or scroll view> — a screen is presented over it …`, and no swipe was sent, because that swipe would land on the modal or sheet (closing a popover, moving a sheet to another size) and not on the target's screen. A failure at a bound adds `The next swipe would have touched down at (x,y) on … — a screen is presented over it …` for the same reason. Close that screen first here too. Under a layer WebDriverAgent shows presented (iOS with `treeSource: wda`) no swipe is sent for a target not in the tree either — `scroll_until … stopped before any swipe — element is not in the tree, and the next swipe would touch down at (x,y) on … — a screen is presented over it …` — unless the swipe would touch down on a scroll view of that layer's own (a search inside the sheet's own list), which is swiped as usual.
- **`… an alert is presented over it ("…") — close it first`** (tap or `scroll_until`; iOS with `treeSource: wda`): an alert is up (WebDriverAgent's `Alert`: `ui_snapshot` marks its layer `"presentation": "alert"` and the Alert itself `"presentationElement": true`), and it covers the whole screen beneath it, whatever lies around its card — the target is refused wherever it lies, and nothing was tapped. `scroll_until` says it as `… an alert is presented over it ("…") — close it first, and a swipe would land on the alert, so none was sent` (or `so no further swipe was sent`), and under an alert it sends no swipe even for a target not in the tree: `scroll_until … stopped before any swipe — element is not in the tree, and the next swipe would touch down at (x,y) on … — an alert is presented over it ("…") — close it first, and a swipe would land on the alert, so none was sent`. The alert's own buttons and texts are reached as usual: tap the button that closes it, then repeat the step. For a target not in the tree, a swipe that would touch down on a scroll view of the alert's own is sent (a search inside the alert); for a target beneath the alert, no swipe is sent wherever it would touch down. An action sheet or a popover (WebDriverAgent's `Sheet`, `Popover`; `"presentation": "actionSheet"` or `"popover"`) reads the same way, named by its kind and label — `… an action sheet is presented over it ("…") — close it first`, `… a swipe would land on the action sheet …` — and its own buttons and dismiss region are reached.
- **`… was not tapped: after back was pressed …` / `after id:"…" was tapped …`**: the keyboard guard hid the keyboard first, and the layout then moved the element off screen. The screen has changed; take a `screenshot`, then `scroll_until` it.
- **`either way up`** in the refusal or a `scroll_until` failure: the tree suggested the screen may be turned but nothing confirmed it, so averi counted both orientations, and the element is outside both.
- **`… to appear` with `(it matched only 0×0 nodes (scrolled off screen, or collapsed) …)`**: the selector matched only zero-area nodes. iOS (idb) reports a node scrolled above the top that way. Run `scroll_until` with `direction: up`, then retry. If it is not in a scroll view, the view is collapsed or not laid out yet.
- **`… to appear` with `(it matched only nodes clipped out above its scroll container (scrolled past it) — scroll_until it with direction: "up" first)`** (or `below` / `"down"`, Android): uiautomator reported the element scrolled wholly past its list (inverted bounds; `ui_snapshot` shows it zero-size with `clippedOut`). Run `scroll_until` with the direction it names, then retry. A plain `scroll_until` (direction down) does not turn back for an element already clipped out above on its first read.
- **`scroll_until … failed … — element was in the tree before the first swipe, clipped out above its scroll container, … — scroll_until it with direction: "up"`** (or `in tree but never intersected … — it lay clipped out above its scroll container …`, or `above the viewport` on iOS): the element lay past the edge the swipes push content out through, so the default direction carried it further away. Run `scroll_until` again with the direction it names. **`… element never appeared in the tree — if it lies above, try direction: "up"`**: the swipes moved the content and then it stopped changing without the element showing — most likely the end of the content in the direction asked, so it is probably above (or, with `direction: "up"`, below — try `"down"`) or not on this screen. A screen that only finished loading between the first two reads also counts as moved, so treat the hint as a guess, not a finding.

## Typing and fields

- **`⚠ fill … typing APPENDS`**: the field already held text and `clear` was off. The length check passed, but the content may be wrong. Add `clear: true`, unless a pre-filled value must survive.
- **`Typed N characters into … — NOT verified: the matched node exposes no value`** (a `⚠ fill … NOT verified` line in a flow): the selector matched a node that is not a `textfield` and shows no text, so averi could not check the typing. (A `textfield` showing no text is empty: a fill whose characters it dropped fails with `typed N characters but the field shows 0`.) If `clear` was set, nothing was deleted either. Check the field with `ui_snapshot`.
- **`Typed N characters into … — NOT verified: the field could not be found again (the screen changed while typing)`**: the text was typed, but the selector stopped matching (typically a `value:` selector, once the value changed) and the screen's identified nodes changed while typing (an inline error went away, a notice or the keyboard appeared), so averi would not guess which node is the field. The field may well hold the text. With `(the selector no longer matches it)` the field moved, has a twin, or nothing was read before typing. Check the field with `ui_snapshot`, or select it by something that does not change as you type (`id:`). A clear alone (empty text) whose field was lost reads `Cleared … (N deletes sent) — NOT verified: …`: the deletes were sent, nobody saw the field empty. `Focused … — NOT verified: clear sent no delete …` means only the focus tap happened.
- **`⚠ … the matched node is role text, not a textfield`**: the selector found a label, not the input. Typical on iOS with `treeSource: idb`, where a floating label is its own `text` node. `clear` deletes nothing there. The line names the nearest input. It is not shown when the matched node's value changed to show the text, because then that node took it. Select it with `role:textfield` plus its `id:`, or its current `value:` when inputs share an id.
- **A fill fails with `typed N characters but the field shows M`** on a field that reformats what is typed (`0.00` becomes `1000.00`): the read-back compares the field with the value exactly when `clear` is set, and looks for it inside the field without. A reformatting field cannot pass that, whatever the selector (since 2026-10-08 a `value:` or `text:` selector is read back too). Type the value as the field will show it, or focus the field with `tap`, type with `type_text` without a selector (not read back), and check the result with an `assert`.
- **`Cleared … (N deletes sent) — NOT verified: the field still shows M characters that the deletes did not change`**: a clear alone (empty text) whose deletes left the field showing the same text. Almost always the field is empty and shows its hint or placeholder, which the tree reports as its value (Android EditText hints, iOS placeholders). Check with `screenshot`. If the text is real, the field ignores deletes (read-only, or an input method that drops them). With a value typed after the clear, the read-back decides instead.
- **`NOT verified: the field shows exactly its placeholder's text`**: the tree source names the field's placeholder (iOS `treeSource: wda`, or an Android dump with a hint attribute), and the field shows exactly that text. It is either empty or holds that very text, and the tree cannot tell which. Check with `screenshot`.
- **`typed N characters but the field shows N — the typed text is there but for letter case`** (or `as many characters as were typed, K differing`): the app changed what was typed: auto-capitalisation, autocorrect, smart punctuation, a mask. The fill fails, because the field does not hold the value asked for. Type the value as the field will show it (`Hello`), or turn the transformation off in the app's test build. `— the field did not change: the typing did not reach it, or the field refused it` means the field shows what it showed before typing: the focus tap missed, the field ignores input, or it was already full (a maximum length).
- **A later step fails after any `⚠ tap` / `⚠ fill` line** (an unexpected value, a submit that never happened): suspect that tap first. Check the field values with `ui_snapshot`.
- **Placeholders** exist only while the field is EMPTY on iOS. Assert them before typing.

## Soft keyboard

### Android

Success lines (the step worked):
- `the soft keyboard covered <target>; hidden before tapping`: averi pressed `back`, found the target again and tapped it. A `press_key back` before the step is not needed.
- `… could not be read` after `back`: the step also succeeded.
- `… that the input method denied; waited Nms …`: the step also succeeded.

Failure lines:
- **`⚠ … back pressed` then `✗ … back did not close it`**: nothing was tapped. Run `ui_snapshot`, then `press_key back` once more, or tap a control above the keyboard.
- **`⚠ … back pressed` then `✗ After pressing back … Timed out`**: if no keyboard was really up, `back` navigated away. Look at the screen (`ui_snapshot` / `screenshot`) before you retry.
- **`⚠ … denied; nothing sent` then `✗ … Neither back nor the tap was sent`**: Android's two keyboard sources never agreed. Look at the screen, then tap again (or `press_key back` if a keyboard is visibly up). In a flow, add a `wait:` for something that only appears once the screen has settled.
- **`⚠ fill … the input method reports a soft keyboard shown, but the window state gives it no area`** (after `dismissKeyboard: true`), or the same words on a failed or `fully: true` `scroll_until`: the two Android keyboard sources disagreed — often a keyboard still coming up. averi pressed nothing, because `back` with no keyboard up pops the screen, and it cannot tell where that keyboard is. Take a `screenshot`. If a keyboard is up, `press_key back` once. A FLOATING Gboard does not usually cause this line: on Android 13 its panel is read and handled like a docked keyboard (a tap under it hides the keyboard first, `scroll_until` judges above it, a pixel assert fails closed on it).

### iOS (`treeSource: wda`)

averi never presses a key, because the return key submits. A covered target is hidden by tapping the first usable `app.ios.keyboardDismiss` entry, then tapped.

Success lines:
- `hidden by tapping id:"…" before tapping`
- `gone on the second look`
- `still up … but no longer over it`

Failure lines:
- **`no dismissal, nothing sent` / `none of the configured dismissals is usable …`** (each entry is listed with its reason): nothing was tapped.
  - From the tools: tap a neutral, non-interactive element (the screen title), then tap again.
  - In a flow: add such an element to `app.ios.keyboardDismiss`. Use a title or label, never a button; for a number pad's Done toolbar, add an `accessory: true` entry.
  - `covered by <role> "…"`: something drawn later sits over that entry's centre (an alert, a sheet, a bar's label). Close it first, or configure an element it does not cover. A screen-sized, non-interactive host (any non-interactive node with children, e.g. a toolbar, scrollable or webview) with nothing of its own at that point (WDA's full-screen SwiftUI `Toolbar`) is not counted as cover, and neither is a scroll view with children, of any size, with nothing of its own at that point (a form's scroll view whose frame runs under the translucent top bar while its rows start below it): only its content at the point covers (a childless scroll view still covers). A toolbar with no items at all (WDA's empty `Toolbar` frames on a UIKit sheet such as Contacts' "New Contact") is not counted as cover either, whatever its size; a toolbar with any item (a Done, a bar button) still is. Over another screen these excuses lapse: a scroll view of a modal or sheet laid in the same window over the entry's screen, or a full-screen leaf of it (its dimming view), covers the entry, which is skipped `covered by …`; a host with children there still does not. On iOS with `treeSource: wda` a layer WebDriverAgent shows presented (`ui_snapshot` marks it `"presentation"`) covers the entry whatever it holds.
  - `an alert is presented over it ("…") — close it first` (iOS with `treeSource: wda`): an alert is up over the entry's screen, and it covers the whole screen beneath it, as for a tap. Close the alert first. An action sheet or a popover reads the same way.
- **`tapped id:"…" to hide it, still covered`**: the dismissal was tapped ONCE and may have changed the screen. Take a `screenshot` before you retry, and configure a dismissal that works on this screen.
- **The keyboard's return key** (`tap: { label: search }`) is tappable. Use it only while `ui_snapshot` shows the `keyboard` band. After a `fill`, the keyboard is usually parked below the screen, and a tap there is refused as off screen.

### iOS (`treeSource: idb`, the default)

idb's tree cannot say whether the keyboard is up, so averi never hides it there and presses nothing. It does see where the keyboard's background starts, and treats everything below that line as under the keyboard. `scroll_until` starts its swipes above it and does not stop on an element whose centre lies below it. A tap on such an element is refused with `is under the soft keyboard: its centre … lies below the keyboard's top edge`, and a tap moved off covered chrome never lands inside it (`nothing of it shows above the soft keyboard`). A `color` or `ocr` assert on an element that reaches below the line fails with `the soft keyboard covers the element`. A key itself can still be tapped when it shares its row with other keys; a key alone on its row inside the background is refused like content. On iOS 27 idb lists the QuickType bar (`Passwords`) as a plain button ABOVE the background, not inside it, so a tap on it presses it, as asked; an app element whose centre lies behind the bar is left out of idb's tree, as one under the keyboard is, and a tap on it times out waiting for it to appear. Two app elements side by side behind the keyboard, not overlapping, are taken for keys and are not refused. Hide the keyboard yourself (tap a neutral title), then retry.

## Screenshots, pixels and visual checks

- **`⚠ frame:` / `the screen did not settle`**: the screen kept changing (an animation, a spinner, a clock, a caret). The picture is the last capture, and `color`/`ocr` asserts and baseline creation refuse it. Wait for the animation to end (in a flow, a `wait:` for what appears after it), or hide the live content. For `color`/`ocr`, stability is judged over the element only.
- **Baselines** are created on first use under `.averi/baselines/`. Creation is refused while the screen moves. Delete the file to re-baseline.
- **`color`/`ocr` budget**: 12 s by default (tree asserts: 3 s). An assert that keeps failing spends the whole budget, so pass `timeout` when you expect a failure. An element under the soft keyboard fails closed and names both rects; hide the keyboard first. OCR is macOS-only and fails closed elsewhere.
- **`color`/`ocr` fails with `nothing of the element is drawn: it lies outside its scroll view <scroll view> (element …, screen …)`** or **`only a sliver of the element is drawn, too thin to measure: the rest lies outside its scroll view <scroll view> (element …, drawn …, screen …)`**: iOS with `treeSource: wda`. The element lies on the screen but outside the scroll view it is listed in, which draws none of it there, or only a sliver no thicker than 2 pt at the scroll view's edge. What the capture shows there is not the element, so it is never measured. Only the part the scroll view draws is judged and sampled: something drawn over its undrawn rest does not fail it. `scroll_until` the element (with `fully: true` to measure all of it) and assert again. Under a modal or sheet still up over the element's screen the message ends `… close it first; …` instead: close that screen first.
- **`color`/`ocr` fails with `… is drawn over the element`**: something lies over the element's rect, so the capture would show it, not the element. Either the status bar (the top band the device reports; on iOS the top safe-area inset, 62 pt on a 402x874 iPhone; on Android the visible system status bar, 66 px on a 1080x2220 phone, which an app drawn edge-to-edge lays its top under) or another element of the app drawn over it, named with its rect (a pinned button bar, with `reaching …` for the area below it that the bar's background hides, a floating tab bar, a title laid over a scrolled row). Every part of the rect counts, not only the centre a tap presses. An overlap of 2 units or less (pt on iOS, px on Android) does not count, and neither does the element's own content or a transparent clickable layer over it. A wrapper with children laid over it can count, such as a floating action button's full-width host (see the covered-tap entry under "A tap target off screen"), and so does a modal's full-screen dimming view or a sheet's scroll view over the screen beneath. `scroll_until` the element with `fully: true` first, then assert again. When no scroll moves it out (it is pinned, or the cover holds all of it), the message says so: assert something in it that lies clear of the cover instead. Under a modal or sheet still up over the element's screen the message ends `… a screen is presented over the element (a modal or a sheet) — close it first; no scroll moves the element out from under that screen` instead, whatever else lies over it (the status bar, a possible cut at the navigation bar): the message still names what lies over it, and this replaces its own advice. Close that screen, then assert again. Under an alert (iOS with `treeSource: wda`), which covers the whole screen beneath it, the message ends `… an alert is presented over the element ("…") — close it first` instead: tap the alert's button that closes it, then assert again (an action sheet or a popover reads the same way). A keyboard the device reports over the element is still named first, with its own advice. Only what the assert reads counts: the whole rect for `ocr`; for `color` the part of the rect on the screen, less 12% on each side of it — the region its sampler reads, so a sliver of an element at the screen's edge is judged on the sliver it would measure. So an element that reaches into the status bar by design (a full-bleed header, on iOS or in an Android 15+ app drawn edge-to-edge — an app bar at 0,0 1080x220 under the 66-px bar; a whole screen) fails an `ocr` assert, and a `color` assert only if the bar reaches into its sampled middle (that app bar's does). The message then leads with the cure: for the header, assert its title; for a whole screen, something in it that lies clear of the bar. On Android the navigation bar at the bottom of a portrait screen counts too (the visible bar the device reports, from y 2154 on a 1080x2220 phone), named `the navigation bar` with its rect.
- **`color`/`ocr` fails with `nothing of the element lies on the screen (element …, screen …)`** or **`only a sliver of the element lies on the screen, too thin to measure (element …, on the screen …, screen …)`**: nothing of what the assert reads lies on the screen (below the fold, above the top, past a side), or the screen's edge leaves only a sliver of it no thicker than 2 units (pt on iOS, px on Android), too thin to measure — its few rows would be whatever lies at the edge, so it is never measured. The assert keeps polling to its deadline. Scroll it on-screen (`scroll_until` it, with `fully: true` to measure all of it) and assert again. Under a modal or sheet still up over the element's screen the message ends `… a screen is presented over the element (a modal or a sheet) — close it first; …` instead: close that screen first.
- **`color` fails with `the element has no area (rect …)`**: the element's rect is collapsed to no width or no height — a node idb lists as 0x0 once scrolled off the screen (above the top: run `scroll_until` with `direction: up`), or an Android node whose bounds come back inverted and clamped flat — so there is nothing to sample. Assert a child that has area, or scroll the element back on-screen first.
- **`ocr` fails with `… may be cut at the navigation bar`** (Android): the element's bottom lies on the navigation bar's top edge, inside a scroll container that ends there too, so the tree cannot tell a whole element from one the bar cuts. Scroll it up (`scroll_until` with `fully: true`) and assert again. A `color` assert on it is measured.
- **`scroll_until … fully: true` fails with `it stays partly under the status bar` or `… the navigation bar`**: with `fully: true` none of the element may lie under a system bar past 2 units (pt on iOS, px on Android) — the rule a `color`/`ocr` assert applies — and swiping no longer moves it out (a last row under an edge-to-edge navigation bar), or the swipes ran out first. Content no scroll can lift out of a bar is exempt and stops as before: in no scroll view, a full-bleed header laid from the screen's top edge at full width, a full-width surface laid to its bottom edge (a bottom sheet), or an element the size of the screen; or screen-sized scroll content taller than the room between the bars — a pixel assert on it still fails closed, so assert something in it clear of the bar. Its centre is clear of the bar; when the message adds that a plain `scroll_until` stops on it and a tap lands, nothing is drawn over its centre either. To measure it, assert something in it that lies clear of the bar.
- **`scroll_until` reply names clipped edges**: the element only intersects the viewport (a floating nav bar is a common cause). Use `fully: true` before a `rect` assert or a screenshot, or you measure the clipped box.
- **`scroll_until … fully: true` says `fully visible` but the element is partly hidden (Android)**: uiautomator reports a node's bounds clipped to its scroll container, so the part under a pinned top bar is not in the tree and averi cannot see it. Compare the element's height with its siblings' in `ui_snapshot` (a short one is clipped), and take a `screenshot` before a `rect` assert on it. A node that carries `cutBounds` in `ui_snapshot` was dumped cut short of its own children (something drawn over part of it, such as a sticky header); averi judges it by its children's extent, the `rect` shown. A row whose touch target overflows into the next row of its list carries `cutBounds` too: one dump cannot tell the next row from a sticky header, a permanent limit.
- **`scroll_until` reply or failure ends `; the sheet moved from its Half screen detent to Expanded`** (iOS): the sheet's grabber (`Sheet Grabber` in `ui_snapshot`) reported another detent at the scroll's last read than at its first: the sheet moved during the call. The usual cause is a swipe on a half sheet's list at its top, which drags the sheet up before it scrolls the list; a call that sent no swipe says it too, when the sheet moved on its own between two reads. The verdict before the note stands as it is; the screen is now in another state, so check the sheet (or drag it back) before steps that assume its old height.
- **`scroll_until` reply says `above the soft keyboard over [x,y][x2,y2]`**: the keyboard was up. The viewport was the screen above it and the swipes started there. A part under the keyboard does not count as visible. With `fully: true` it fails if the content ends with the element still under the keyboard. A keyboard over the whole screen fails at once. Hide the keyboard first (`press_key back` on Android, a tap on a neutral title on iOS; in a flow, `dismissKeyboard: true` on the fill before), then scroll again.
- **`rect` fails with `… CONTENT width`**: no trustworthy screen width was found. On iOS, set `treeSource: wda`.
- **`text` assert fails, but the hint says the string is inside a longer label**: iOS merged the labels. Use `match`, not a bug report.

## Layout contracts (`verify` with `contract:`)

- **`## rect parity`**: per-anchor deltas against the contract and android-vs-ios. The `aspect` row compares shape even for sides nobody pinned. Set `aspect: false` on an anchor only when the platforms derive a side differently by design, e.g. Android's 48 dp touch-target floor against iOS's 44 pt, and write the reason beside it.
- **`## color parity`**: android-vs-ios at `tolerance_de` (8), against the contract at 1.5×. A single-platform run gets only the looser axis and can miss a real drift (measured dE00 10.19 under 12), so set `tolerance_de: 6` in the contract for single-platform work. Strokes of 1–2 px are invisible to sampling; judge them from the screenshot.
- **`## text parity`**: the `src` column says `ocr` (what renders) or `tree` (the weaker fallback). Use `text_dynamic: true` for amounts and dates.
- **`OCCLUDED` (`UNREAD, cause not determined`)**: averi could not read the anchor. Something covers it (usually the keyboard), or it has unreadable contrast, which is a finding in itself. Open the screenshot to tell which.
- **Copy differs between platforms**: check Figma for which side is right before fixing either.

## Launch and logs

- **iOS `⚠ … after launching <app>, the UI tree was still …`** (the second line of a `launch_app` reply, or a `⚠ launch` trace line; default idb tree source only — with `treeSource: wda` the launch does not check, which is unmeasured there): averi waited 3 s for the tree to show the launched app and it still showed another app, or SpringBoard. A read now may judge the wrong app, and an `absent` check would pass on it. Take a `screenshot`. If it shows the launched app, its on-screen name differs from its Info.plist name (a localized display name) and you can go on. Otherwise read again before you trust the tree.
- **iOS `⚠ could not check that <app> is in front (…)`**: averi could not tell which app the tree shows, and the parentheses say why. The tree may still be the previous app's. Take a `screenshot` before you trust a read.
- **Launch opened LeakCanary (or another launcher)**: set `app.android.activity`.
- **`Android started no activity in <package> for this intent`**: no exported activity matches the intent, or the matching one refused it. The quoted `am start said:` line tells which.
- **`get_logs`**: always pass `grep`, a case-insensitive regex. Only the last `maxLines` (400) come back, and the header says how many matched. Narrow the regex before you widen the tail.
