# averi tools in full

The tool descriptions an agent sees every session say what each tool does, its result and the rules that must not be
broken. This file holds the rest for each tool whose description was shortened: every refusal case, the platform and
tree-source specifics, and the mechanisms behind them. Read the section of a tool when its reply or refusal surprises you; for a `⚠`/`✗` line or an error
message, [troubleshooting.md](troubleshooting.md) is organised by symptom.

## Shared arguments

- `configPath`: Path to averi.yaml (default: ./averi.yaml in the server working directory). Paths INSIDE it — the build paths, .env.averi, .averi/baselines/ — resolve against the file, so a config in a subdirectory needs nothing else. Read only when this call uses a value from it; a call that reads it fails on an invalid file (naming it) rather than ignoring it, and a missing file fails only the tools that cannot work without one (ensure_state, run_flow, verify, install_app without a path). On iOS every tool that touches the device reads it for app.ios.treeSource, so all the tools of one project drive the same adapter, and launch_app's wait for the launched app asks that project's tree source.
- `environment`: Credential environment from averi.yaml `environments:` (e.g. "starterkit") — pass when the build under test points at a different backend than usual. Defaults to $AVERI_ENV (settable in .env.averi), then `defaultEnvironment:`.

## `select_device`

- Pin which booted device subsequent tools target for a platform.
- Without a pin, tools use the first booted device adb/simctl lists — ambiguous when a phone, an emulator, and a watch are all connected.
- The pin lasts for the server session; a pinned device going offline is an error, never a silent fallback to another device.

Arguments:

- `device`: Device id from list_devices (adb serial / simulator UDID)

## `install_app`

- Install an app build (.apk / .app bundle) on the booted device.
- Omit path to use the build path from averi.yaml (app.android.apk / app.ios.app), which is resolved relative to averi.yaml itself — no need to pre-absolutize it when the config sits in a subdirectory; on iOS a call with a path still reads averi.yaml, for the tree source.

Arguments:

- `path`: Path to .apk (android) or .app (ios)

## `launch_app`

- Launch an app by package name / bundle id. clearState wipes app data first (forces fresh login); the reply then carries a ⚠ clearState line counting the wipes this server session has made, flow launches included.
- Android: activity pins the entry point — without it (and without app.android.activity in averi.yaml) the launcher activity is picked arbitrarily, which opens LeakCanary instead of the app on debug builds that bundle it. intent exercises non-launcher entry points (share/SEND); an intent without an activity is delivered within the app's package (never to another app, and not to app.android.activity), and fails if no activity there handles it. On Android averi.yaml is read only for that fallback (neither activity nor intent named), and an invalid one then fails the call instead of launching without its activity; on iOS it is read for the tree source.
- iOS: returns once the tree source names the launched app — for a second or two after an app switch iOS still serves the previous app's tree, on which an absent assert would pass — waiting at most 3 s. The default idb tree source: until the tree's Application label is one of the app's names. `treeSource: wda`: until WebDriverAgent names the launched bundle as its active app — asked only once WDA is running (the project's first tree read starts it, which outlasts the switch), so a launch before any read does not wait. When it never saw the app, the reply carries a ⚠ line naming what it saw (troubleshooting.md): read again before trusting a read (the screenshot switches before the tree). When iOS's system alert is in front (an unanswered "Open in …?"), the ⚠ line names it and its buttons' centres instead — the launch waits behind it until it is answered; answer it with `tap text:"<label>"` for the button you mean, or `tap` at its x/y (averi taps nothing).

Arguments:

- `appId`: Android package name or iOS bundle id
- `activity`: Android only: activity to start (".MainActivity" or fully-qualified). Defaults to app.android.activity from averi.yaml when no intent is given either.
- `intent`: Android only: am start parameters for custom entry points. Without activity, resolved within the package (am start -p).

## `open_deep_link`

- Open a deep link / universal link URL on the device. The reply is `Opened <url> on <platform>`, plus a ⚠ line when averi has reason to doubt it — or, on iOS, `iOS has not opened <url> yet: …` when a system alert holds the link (below).
- iOS: when the link's scheme is one the project's app declares (averi.yaml `app.ios.bundleId`, its Info.plist's `CFBundleURLTypes`), averi waits as `launch_app` does — at most 3 s — until the tree source names that app. Before such a link averi records iOS's "Open" answer for `simctl openurl` (the answer an Open tap records; simulator-wide, kept), so iOS should not ask "Open in “<app>”?". If it asks anyway (the simulator ignored that answer, or refused it — stderr then says averi could not pre-approve), the alert covers the current screen; the link is not opened, and every later `launch_app` stays behind the alert, until it is answered. When averi finds that alert (idb lists it in its reads; under WDA it reads the tree once at the 3 s bound), the reply is one line instead: `iOS has not opened <url> yet: it asks "<title>" — buttons "Cancel" at (127, 474), "Open" at (275, 474). Answer it with tap text:"<label>" for the button you mean, or a tap at its x and y …` — the title and every button quoted verbatim (localised as iOS shows them), each with its centre; `a system alert is up, "<title>"` in place of `it asks` when the title does not name the app. averi never taps it: answer with `tap text:"<label>"` — the label as the reply quotes it — or `tap` at the button's x/y when the label holds a `"` or two buttons share it. Otherwise a ⚠ line means averi did not confirm the app came forward — `averi did not see <app> come forward after the link` (it read another app), `averi could not check …`, or `… was not checked (WebDriverAgent is not running yet)`: take a `screenshot`; if it shows a system alert, answer it with a `tap` — `text:"Open"` opens the link, `text:"Cancel"` drops it (the labels as iOS shows them); otherwise read again before trusting a read. To test a link without the prompt, `launch_app` the app first (a warm link — not the same code path as a cold one).
- iOS, any other link (`https`, iOS's own schemes like `tel:` or `mailto:`, another app's scheme, no averi.yaml, an Info.plist averi could not read): opened and returned at once, unchecked — a reply of `Opened` says only that `simctl openurl` succeeded.
- Android: a link no installed app handles fails the call. A link two apps handle opens Android's "Open with" chooser, which the reply does not mention (unmeasured): take a `screenshot` when the handler matters.

## `ui_snapshot`

- Normalized accessibility tree as JSON — cheap text-based verification.
- Optional selector filter (e.g. 'role:button', 'id:login_button', 'label~"Pay.*"') returns only matching nodes. iOS: if `id:` finds nothing — React Native static text/containers (identifier: null everywhere), a SwiftUI `.accessibilityElement(children: .contain)` identifier, a UIKit table cell label's identifier — that is the default idb tree source, which never exposes container identifiers, drops some others, and lists nothing beneath the keyboard or a presented layer — set `app.ios.treeSource: wda` in averi.yaml and retry, or ask by text:/label:.
- A filter that matches nothing returns [] plus a second text block: the unfiltered tree size and roles, or — when the tree holds nothing of the app's (only wrappers, unlabeled decoration, or iOS's status bar and launch icon) — a ⚠ that the accessibility tree is empty or unrendered: still loading, or stuck empty on a rendered screen.
- Compare with screenshot before reading the element as absent.
- On iOS idb the measured stuck tree (a 0×0 Application, for minutes on a rendered screen) fails the call instead, naming it; assert polls (3 s by default; set "timeout" in the spec).
- Does not itself wait, but for one re-read a second later of an unreadable first read (Android's "null root node", iOS idb's empty tree — a launch's first second or a stuck idb); an iOS error that says it was retried was still empty a second later.
- iOS wda with the software keyboard up: one node has role "keyboard" — its rect is the band the keyboard covers (keys, AutoFill bar, accessory toolbar slot), where a tap is refused — and the two Windows that ARE the keyboard's UI carry "ofKeyboard": true (their descendants — keys, Done, the Passwords bar — are tappable); an input-accessory toolbar (the Done above a number pad) has role "toolbar".
- iOS wda: a node carrying "hidden": true lies in a subtree whose ROOT — any element but a structural wrapper — WebDriverAgent reports neither visible nor accessible, and every node of which it reports not visible (a descendant may be accessible: a hidden tab button's icon), e.g. a tab bar a pushed screen hides, still listed at its old place — it is no cover of what lies under it (a screen presented over that element covers it all the same, through the layer WebDriverAgent shows presented — "presentation", below); and the content of a table cell not yet laid out (the cell wholly outside its scroll view), which WebDriverAgent lists at a parked frame inside that scroll view, is given at its cell's rect — so a tap on it is refused as off screen and scroll_until scrolls to it.
- iOS wda: a layer (a Window's direct child) WebDriverAgent shows presented carries "presentation": "alert" when it holds an alert (WebDriverAgent's `Alert`, which carries "presentationElement": true; likewise "actionSheet" and "popover"), or "presentation": "screen" when every node of the screen-sized layer beneath reads not visible while it shows (a sheet, a modal); an empty screen-sized element inside a layer, listed after the screen's content at its origin (an in-screen menu's backdrop), carries "presentation": "backdrop" when WebDriverAgent's flags show it over that content (it hidden while the content shows, or it shown while every node of the content reads not visible) and covers it the same way — the refusal then says 'a menu's backdrop is presented over it (an empty element WDA lists over the whole screen, after the screen's content) — close it first (if a screenshot shows no menu up, the backdrop is an overlay that lets touches through: tap the target by its coordinates (its centre from ui_snapshot)); no scroll moves it out from under that backdrop' — and the root carries "presentationsJudged": true whenever the payload has visibility flags.
- Such a layer covers the whole screen beneath it, whatever lies around it, and its own buttons and texts are reached.
- Under an alert, tap and scroll_until refuse a target there naming the alert ('an alert is presented over it ("…") — close it first'), color/ocr fail closed likewise ('an alert is presented over the element ("…") — close it first'), and an action sheet or a popover is named the same way; under a "screen" layer they name what of that layer lies at the point — the layer itself where nothing of it draws — and say 'a screen is presented over it (a modal or a sheet) — close it first; no scroll moves it out from under that screen'.
- An EMPTY textfield's "value" is often its hint or placeholder text — every tree source reports it that way; where the source also names it (iOS wda, an Android dump with a hint attribute) the node carries "placeholder", and a value equal to it is an empty field.
- A textfield its source marks secure (Android: password="true"; iOS: a secure text field, idb and wda) carries "secure": true — its "value" reads as bullets, one per character, which a fill compares by length; a field without the mark is plain or not said.
- The ROOT says the tree source's dialect: "unclippedFrames": true under iOS wda — every frame as laid out, a scroll view's content past the scroll view's frame too, where nothing of it is drawn (tap, scroll_until and color/ocr judge only what the scroll view draws), and a node of it carrying "readingOrder": true lists its children by their tops — maybe SwiftUI's reading order, not draw order, so which of two overlapping controls among them is drawn on top is not told (see tap), while a child carrying "heading": true (iOS: the Header trait, idb and wda) listed before a node it overlaps is drawn over it — SwiftUI's pinned section header over the rows scrolled under it; "flatList": true under iOS idb — every element a sibling of one rectless root, no nesting, listed in reading order ("readingOrder": true) — and when that root also carries "presentation": "screen" the list holds UIKit's dismiss region over the whole screen: idb lists only that presented layer, so tap, fill and scroll_until say 'a screen is presented over it (a modal or a sheet) — close it first; no scroll moves it out from under that screen' for a target not found there; "activeWindowOnly": true under Android — uiautomator lists the active window only, and when that root also carries "presentation" ("dialog": a window floating off the screen's top and left edges, an AlertDialog; "screen": a window whose clickable scrim lies above its sheet, a bottom sheet) the screen beneath is not in the tree at all — tap, fill and scroll_until say 'a dialog is presented over it — close it first' for a target not found there; "boundsCutAtScreen": true under Android too — uiautomator cuts a node's rect at the screen's edge even where it runs past a scroll view ending inside the screen (a carousel's card dumped ending at the screen's right edge, or a list's row dumped ending at the screen's bottom below its list's), so how far it runs past that edge is unknown: scroll_until says 'at most N%' of it is in the viewport, and a default stop takes one more swipe toward that side first (see scroll_until).
- A scroll view whose type says the one axis it scrolls on carries "scrollAxis" ("vertical" or "horizontal"): on Android by its class (ScrollView, ListView vertical; HorizontalScrollView, ViewPager horizontal — a Compose lazy list or a RecyclerView carries none), under iOS wda a Table (vertical); scroll_until strokes along a scroll view of its own axis and keeps the stroke off a nested one of the other (under wda a scroll view's axis is also read from its content laid out past its frame, which ui_snapshot does not print).
- Android: a node that scrolls (scrollable="true" in uiautomator; a Compose scroller keeps role "container") carries "clipsDescendants": true — uiautomator cuts most rects under it to its rect, so a row whose edge sits exactly on that rect may be partly hidden there (a rect listed past it, as a Compose scroller's may be, is judged only where it is drawn, inside it); a node carrying "clippedOut" ("top", "bottom", "left", "right") was dumped with inverted bounds — clipped out above, below, left or right of its scroll container, scrolled past it — and its rect is zero-size at that edge; a node carrying "cutBounds" was dumped cut short of its own children by something drawn after it over part of it (e.g. a sticky header): "cutBounds" is the rect as dumped, "rect" its children's extent, which averi judges — a tap on such a row whose part clear of the header is too small to tap is refused (scroll_until it first).
- One dump cannot tell a sticky header from the NEXT row of the same list, so a row whose touch target overflows into the next row also carries "cutBounds" — a permanent limit, not a bug; a screen-sized wrapper with nothing of its own there (a snackbar host) never causes it.

Arguments:

- `filter`: Selector to filter nodes

## `tap`

- Tap an element by selector (preferred: 'id:login_button', 'text:"Continue"', 'role:button label~"Pay.*"') or by x/y coordinates.
- Selector values containing spaces must be double-quoted: text:"Sign in" (exact) or text~"Sign in" (regex) — an unquoted text:Sign in fails at "in".
- With a selector, waits up to 5 s for the element to appear and hold still (same policy as a flow tap: step) and fails with "Timed out … to appear" if it never shows (or "… to hold still (found, but never at the same position in two consecutive reads)" if it shows but keeps moving (also when one read took the whole budget and the one more read taken after it finds the element at a different position), "… (found once / on the last read, but no second read came …)" or "… (found once; the one read after the budget did not find it again)" if one read took the whole budget) — a selector matching nothing is a wait, not an immediate error.
- Ignores zero-area nodes (a timeout whose selector matched only 0×0 nodes says so — iOS reports a node scrolled above the top that way; on Android one dumped clipped out of its scroll container is named so, with the scroll_until direction that brings it back); a target whose centre lies OFF the screen (iOS keeps a scroll view's content below the fold in the tree, with its real rect) — or under the status bar (on iOS the top safe-area inset, 62 pt on a 402x874 iPhone, where a tap scrolls the app to its top; on Android the visible system status bar, 66 px on a 1080x2220 phone, under which an edge-to-edge app draws — a portrait screen only) — is REFUSED, nothing tapped — scroll_until it first (a plain scroll_until stops once its centre is on screen, below the status bar, and clear; fully: true when the next step measures it), unless a screen is presented over the target (below); a target PINNED under the status bar (in no scroll view: a layout that does not keep clear of it) is refused too, and no scroll moves it — the refusal says which, as far as the tree can tell (an idb tree cannot: it names both); a target whose centre lies under another element of the app drawn over it (a pinned button bar, a floating tab bar) is tapped on a part of it nothing is drawn over — never under the status bar — when one is large enough (about 6 % of the screen's shorter side each way), and the response says where and what covered the centre; with less showing it is REFUSED, naming the cover, nothing tapped — scroll_until it first, unless the cover is a screen presented over the target (below); on iOS a control overlapping the target in a container listed in reading order (a SwiftUI container lists its elements by their tops, not in draw order — an in-screen menu's row over the row beneath) counts as such a cover too, listed after the target or before it (before it, where one such holds its centre); averi then takes ONE screenshot and compares the two controls' colours where they overlap and beside it: the target seen on top is tapped as usual; the other seen on top refuses it, "under …, drawn over it as a screenshot shows (the two are listed in reading order)" — close a menu or popover first, no scroll; when the screenshot cannot tell (the two look alike, a frame mid-animation) the refusal says "overlapped by …, the two listed in reading order: which is drawn on top is not told" and why the screenshot could not tell, advising no scroll (if the target is the one on top, tap it by coordinates).
- On iOS with treeSource: wda a target whose centre lies on the screen but outside its scroll view (WebDriverAgent lists a scroll view's content at its laid-out rect past the scroll view's frame, which draws none of it there — a form's row below a pinned button bar) is REFUSED as off screen, naming the scroll view, nothing tapped — scroll_until it first — after the keyboard is hidden (a scroll view laid out above the keyboard grows back), unless a screen is presented over the target (below).
- With treeSource: idb, which lists no scroll view, such a target is judged on the screen alone and may be tapped on what lies beneath its scroll view's clip — set app.ios.treeSource: wda to have the scroll views judged.
- A target its scroll container cuts to a strip thinner than that minimum (Android: its rect flush with the container's edge, its own content running on past it) is REFUSED likewise, nothing tapped — scroll_until it first (the refusal names the direction when the cut is not at the bottom), unless a screen is presented over the target (below).
- So is a control Android dumps as a strip thinner than that minimum flush against an element drawn after it that spans it (Compose leaves out of a node's bounds what a later node covers: a field under a submit bar riding on the soft keyboard) — and an element in no scroll view with no role that is no text, dumped as such a strip at its top or bottom edge against an element that also reaches past it at both ends (a pinned button) — the refusal names that element, where the strip lies and how much of it shows (above the keyboard, when it is up), and says: with the keyboard up and that element riding on it (ending just above the keyboard), dismiss the keyboard first (a bar riding on it goes down with it), or scroll_until it out from under that element; only if a screenshot shows the control whole and only that thin (the tree cannot tell), no scroll shows more: tap it by coordinates.
- A wrapper with children (a `container` or an `other`) laid after the content counts as drawn over all of its rect, unless, among others, it is the screen's size (90 % of it or more), or it has no label and no value and holds the target together with the target's whole scroll view, or it has no label, value or identifier and holds only empty frames — since the tree cannot tell a host that swallows touches (a tab bar's) from a transparent one that only positions its child (an Android floating action button's full-width host, e.g. Clock's fab_container): a target beside or under such a FAB can be refused naming the container.
- When such a wrapper holds one child only, a control of at most a quarter of its area, the refusal says so in place of "scroll_until it first": 'the wrapper may only position its one child, <child>: tap that child when it is the target; otherwise scroll_until this element out of the wrapper's band first'; a wrapper of several children (a tab bar's host) gets no such line.
- Under a screen presented over the target — iOS wda: a layer WebDriverAgent shows presented (see ui_snapshot's "presentation"; an alert, an action sheet or a popover is named as ui_snapshot says); elsewhere (Android): a modal's full-screen dimming view or a sheet's scroll view, laid after the target's screen in the same window — the refusal says so instead of "scroll_until it first" or the status bar's advice, whatever else keeps the target from a tap — its centre under that screen, off the screen or under the status bar (wholly too: the screen is judged presented over the target itself, wherever it lies), or a cut at its scroll container's edge: 'a screen is presented over it (a modal or a sheet) — close it first; no scroll moves it out from under that screen'.
- Close that screen first.
- A full-screen host that only carries a bar or other content of its own (a host with children) is no such screen: only what it draws covers.
- On Android uiautomator lists the active window only: with a dialog or a bottom sheet up the tree holds that window alone (ui_snapshot's root carries "presentation": "dialog" or "screen"; a full-screen dialog or a sheet whose dump carries no scrim, once the wait has found nothing, by the window manager's word), so a target beneath it is not in the tree, and the wait for it (this tap's, and fill's) ends "Timed out after …: element … is not in the tree, which lists only the window presented on top … — a dialog is presented over it — close it first" instead of "… to appear" — where that window holds a list of its own, the reply says first to scroll_until it in that list (a flow's wait: on an element says "(a dialog is presented over it, and the tree lists only that window — close it first)" beneath its "Timed out …", every assert's "not found within …" after it).
- With no window marked presented the wait still ends "… to appear", with "(the tree lists only the active window: if a sheet or a dialog is open over the screen, close it first)" beneath it when the window manager does not say the window is the app's screen alone (its call failed, or another window of the app shows; unless the target matched only 0×0 nodes, whose hint takes its place: the tree cannot tell such a window from none) — and with nothing beneath it when it does, as scroll_until's "element never appeared in the tree" carries it (its stop under a keyboard over the whole screen too), and so do a flow's tap, fill and scroll_until steps (the same waits), a flow's wait: on an element (beneath its "Timed out …"), every assert's "not found within …" (after it) and a skipped optional step's line ("(not present) (…)", or a skipped wait:'s "Timed out … (…)"): every reply that says a target is not in such a tree, once. when several match taps the only interactive one and says so; if several interactive elements match it refuses and lists them — narrow the selector.
- On Android a selector target lying under the soft keyboard is not tapped through it: the keyboard is hidden (back) and the element found again first, and the response says so; coordinate taps are sent as given.
- On iOS with treeSource: wda a target COVERED by the on-screen keyboard (its band: keys, AutoFill bar, accessory toolbar slot) is hidden first by tapping the first entry of averi.yaml app.ios.keyboardDismiss that is on screen (a tap: on a neutral element such as the title, or accessory: true for the input-accessory toolbar's Done), the element found again, then tapped — the response says so.
- When a tapped entry leaves the keyboard up, the next usable entry is tried, then averi's own: a slow upward drag of the target's scroll view, which hides the keyboard where the scroll view dismisses it on a drag and otherwise lifts the target above it — one move at a time, each confirmed, the response naming the one that got the target clear; never the return key (it submits).
- With none configured, or none on screen, the tap is REFUSED, nothing tapped or pressed, since no key hides the keyboard without submitting: hide it yourself (tap a neutral, non-interactive element such as a title), then tap again; with every move spent and the keyboard still up it is refused naming each move.
- The keyboard's own controls — a key, the toolbar's Done, the Passwords bar, dictation — are tappable as always.
- With treeSource: idb nothing in the tree is marked as the keyboard (on iOS 27 idb lists the keys as plain buttons), so nothing is hidden and app.ios.keyboardDismiss is inert; averi reads where the keyboard's background starts by its shape, and a target whose centre lies below that line is REFUSED, nothing tapped — hide the keyboard yourself (tap a neutral element such as the title), then tap again.
- Measured twice on iOS 27, a covered node was absent from idb's tree and the tap timed out waiting for it to appear; where idb's keys are read up by that shape, the timeout (the tap's and type_text's) says so beneath its headline — "the soft keyboard is up (its top edge at y …) and idb lists nothing beneath it, so the element may lie there — tap a neutral element such as the screen title to hide it, then try again" — before idb's reasons.
- On iOS 27 idb lists the QuickType bar ("Passwords") as a plain button ABOVE that background, not inside it: a tap on the bar presses it, as asked, and an app node whose centre lies behind the bar is left out of the tree the same way.

Arguments:

- `selector`: Element to tap, e.g. 'id:login_button' or 'text:"Sign in"' (quote values with spaces)

## `swipe`

- Swipe across the screen, by direction OR by coordinates — exactly one of the two. direction (up/down/left/right) names the FINGER's movement, as a flow's swipe: step does (up = the finger travels up, revealing content below): a stroke through the screen centre, 30% of the screen either side, over the device's screen size (adb wm size / idb describe) turned the way the UI tree's window is; when that size cannot be read the UI tree's window stands in, and when the tree cannot be read the screen is taken as built — the reply says either; with neither size the swipe is refused and nothing is sent.
- On iOS a direction and coordinates alike read the tree source from averi.yaml (optional, like scroll_until): a missing file is the default, an invalid one fails the call.
- Coordinates (fromX, fromY, toX, toY — all four) are sent as given, in the platform's tree units (Android pixels, iOS points).
- To bring an element into view use scroll_until instead.

Arguments:

- `direction`: Finger movement over the screen centre — instead of the four coordinates

## `type_text`

- Type text.
- With selector: focuses that field first (and with clear: true deletes its current content — typing otherwise APPENDS to pre-filled fields), then verifies the text landed and retries a dropped clear-fill once; a matched node that exposes no value (not a textfield: a textfield with none is empty, so typing it dropped fails as "shows 0"), or a field the read-back could not find again (the screen changed while typing, or the selector no longer matches it — after a clear too), is reported as "Typed … — NOT verified" with that reason (never "Filled") — a clear alone (empty text) as "Cleared … (N deletes sent) — NOT verified", or "Focused … — NOT verified" when nothing was deleted — "cleared" counts the characters actually deleted, and a match that is not a textfield (e.g. an iOS idb floating label) gets a ⚠ line naming the nearest input unless its value changed to show the text (then it took it) — clear sends it no delete (its length is not the field's).
- The field is resolved like a tap: up to 5 s to appear and hold still (a timeout if it never does), zero-area nodes ignored, the only interactive match preferred and reported; several interactive matches are refused with the list (never typed into the first); a field whose centre lies off the screen is refused, nothing tapped or typed — scroll_until it first.
- With treeSource: idb a field under the soft keyboard is not in the tree: the timeout says, as tap's, that the keyboard is up and how to hide it, then try again.
- If the UI tree cannot be re-read after typing, the call FAILS rather than reporting a fill it could not re-read.
- Without selector: types into whatever is focused.
- Only printable ASCII is typed, on both platforms: anything else fails `cannot type U+…` before anything is sent (docs/verification.md, ADR 0037).
- An EMPTY field's hint or placeholder, which the tree reports as its value, is not content: clear stops once its deletes change nothing (never on a masked field), then types.
- A clear alone (empty text) on such a field reads, where the source names no placeholder (idb, Android API 33), "Cleared … — NOT verified: the field still shows N characters that the deletes did not change" (a hint, or a field ignoring deletes); where it names one (iOS wda, an Android dump with a hint attribute), a field showing exactly its placeholder reads "Focused … — NOT verified: the field shows exactly its placeholder's text" (empty, or holding that very text), as does typing a value equal to the placeholder.
- A text the app transforms (auto-capitalisation, autocorrect, a mask) FAILS the read-back; the error says whether only letter case differs, how many characters of a same-length reading do, or that every typed character is there with separators added — never the text.
- The focus tap is guarded like tap: a field under the soft keyboard is hidden-then-refocused on Android, and on iOS (treeSource: wda) hidden by the first on-screen entry of averi.yaml app.ios.keyboardDismiss (then the next, then averi's own drag, as tap says) then refocused, or refused with none (nothing typed); a field whose centre lies off screen, or under another element of the app drawn over it with too little of it showing, is refused like tap, and one tapped on its uncovered part says so in the note.
- The keyboard is NOT dismissed after typing here (a flow's fill: has dismissKeyboard for that).

Arguments:

- `selector`: Field to focus first, e.g. 'id:amount_input'
- `clear`: Delete existing content before typing (needs selector)

## `scroll_until`

- Swipe until the element is visible in the viewport — the portable way to reach content below the fold (no coordinates). direction = where the content lies (down = below the current view).
- By default "visible" means INTERSECTS the viewport, so the element may still be clipped at an edge; a clipped stop says which edges clip it and what fraction is on screen, a clean one says "fully visible".
- Another element of the app drawn over it (a pinned button bar, a floating tab bar listed after it in the tree) counts: by default the scroll goes on until its CENTRE is clear of such an element — the point a tap presses — and a stop with part of it still under one says so; with fully: true nothing may be drawn over any of it below the status bar (what lies only under the bar is hidden by it anyway).
- When swiping no longer moves it out from under one, it fails naming that element (on Android a floating action button's full-width host counts as one — see tap).
- On Android, with fully: true, a target in no scroll view also counts as under an element drawn after it whose own node begins exactly where the target's top or bottom edge ends and reaches past the target at both ends of that edge — a pinned button (Compose leaves out of a node's bounds what a later node covers, so the rest of the target may lie under it): the failure says it is cut there and may run on under that element (a target in a scroll view is not judged so: at rest a list's first or last row lies whole and flush against a bar pinned over the list, the same tree).
- On iOS a control overlapping it in a container listed in reading order (as for tap: "overlapped by …, the two listed in reading order: which is drawn on top is not told") is judged on one screenshot, as for tap — seen on top, it is reached; else it stops before any swipe, no scroll moving it out from under the other or telling which is on top, and a stroke beside an in-screen menu may close it.
- Once a read finds the target in the viewport under a screen presented over it (as for tap: a layer WebDriverAgent shows presented, or elsewhere a modal's full-screen dimming view or a sheet's scroll view, laid after the target's screen in the same window), scroll_until confirms with one more read when the timeout allows, and fails without swiping further — "stopped before any swipe …" or "stopped after N swipes, without swiping further …", then "a screen is presented over it (a modal or a sheet) — close it first; no scroll moves it out from under that screen, and a swipe on it may dismiss it" — since a swipe there could dismiss a sheet or raise its discard prompt.
- The same holds, with the same confirming read, for a target in the tree that is NOT judged in the viewport (below the fold, under the soft keyboard, cut, or under a bar of its own screen) when the next swipe would touch down on such a screen: it fails without that swipe, saying why the target is not in the viewport and where the swipe would have landed — e.g. "element lies below the viewport, and the next swipe would touch down at (201,699) on container "dismiss popup" (0,0 402x874) — a screen is presented over it …" — since that swipe would land on the presented screen, not on the target's (a popover closed, a sheet moved to another detent); a read that fails meanwhile is retried, never answered with a swipe.
- When a bound (maxSwipes, the timeout, content exhausted) ends the scroll first, the failure adds "The next swipe would have touched down at (x,y) on … — a screen is presented over it …".
- A row of the presented sheet itself is still swiped for on the sheet, and a target not yet in the tree is still swiped for — except under a layer WebDriverAgent shows presented (iOS wda: an alert, an action sheet, a popover, or a "screen" layer such as a sheet), where no swipe is sent for any target unless it would touch down on a scroll view of that layer's own (a search inside the sheet's list): "stopped before any swipe — element is not in the tree, and the next swipe would touch down at (x,y) on … — an alert is presented over it ("…") — close it first, and a swipe would land on the alert, so none was sent".
- The same on Android when the tree is a presented window (ui_snapshot's root carries "presentation": "dialog" or "screen"; or, for a target its read does not hold, the window manager names the window a Dialog's — asked once before the first swipe: a full-screen dialog, a sheet whose dump carries no scrim): uiautomator lists that window alone, so a target beneath it is never in the tree, and no swipe is sent for it — one would land on the dialog's dim and dismiss it, or drag the sheet — "… — a dialog is presented over it — close it first, and a swipe would land on the dialog, so none was sent".
- The same on iOS idb when its list holds UIKit's dismiss region over the whole screen (a medium sheet, a popover: ui_snapshot's root carries "presentation": "screen"): idb lists only that layer.
- Wherever no tree shows the layer (idb beneath a large sheet, an alert, a cover), a swipe that CHANGES THE SCREEN — the read after it lists none of the ids the read before listed, and nothing it touched down on is still listed (a labelled node by its label, a scroll view by its frame) — stops the scroll: "stopped after 1 swipe — the swipe CHANGED THE SCREEN: … it most likely dismissed a sheet or a modal presented over the screen …", a target found on the new screen not claimed visible, no further swipe sent.
- The status bar (on iOS the top safe-area inset, 62 pt on a 402x874 iPhone; on Android the visible system status bar, 66 px on a 1080x2220 phone; a portrait screen only) counts as off the screen for the CENTRE: no stop — fully: true included — has the centre there (the point a tap presses), and a scroll that cannot move it out fails naming the status bar; for a default stop the rest of the element may lie under it, so full-bleed content at the top stops once its centre lies below the status bar (one whose centre, rounded as a tap sends it, lies in the bar — at y 0, shorter than twice the bar's height less a point (122 pt or less under 62 pt) — never stops, and fails naming the status bar).
- With fully: true none of the element may lie under the status bar, or the navigation bar the device reports (Android), past 2 units (pt on iOS, px on Android) — the rule a color/ocr assert applies: the scroll goes on, and an element that stays under a bar (a last row under an edge-to-edge navigation bar) fails naming the bar.
- Content in no scroll view that no scroll can lift out of a bar — a full-bleed header laid from the screen's top edge at full width, a full-width surface laid to its bottom edge (a bottom sheet), an element the size of the screen — or screen-sized scroll content taller than the room between the bars, is exempt and stops, and a color/ocr assert on it still fails closed (assert something in it clear of the bar); an ocr assert may also refuse an element whose bottom rests exactly on the navigation bar's top inside a list that ends there (it may be cut).
- A top bar the tree does not list, or lists before the scroll view (an iOS navigation bar under WDA), is not seen.
- Nor does a default stop rest on an element its scroll container cuts to a strip thinner than a tap needs (Android: its rect flush with the container's edge, its own content running on past it) — a tap refuses that strip, so the scroll goes on, and fails naming the cut when swiping no longer moves it.
- Nor does any stop rest on a control Android dumps as such a strip flush against an element drawn after it that spans it (a field under a submit bar riding on the soft keyboard), or on an element in no scroll view with no role that is no text dumped as such a strip at its top or bottom edge against an element drawn after it that also reaches past it at both ends (a pinned button): the scroll goes on, and fails naming that element when swiping no longer moves it — with the keyboard up and that element riding on it, dismiss the keyboard first and scroll again; or, only if a screenshot shows the control whole and that thin, a coordinate tap reaches it.
- Pass fully: true when the next step MEASURES the element (a rect assert, a screenshot) — a clipped rect measures the clipped box, and fully: true fails loudly instead, naming the shortfall.
- With fully: true, an element as wide (or as tall) as the scroll view that scrolls it along that axis, or larger, clipped there, fails on the first read that shows it so, with no further swipe — even before the first: it is fully visible at one exact scroll offset at most, which no swipe can be aimed at. The reply says 'element is in the viewport but CLIPPED at left: 98% of it is drawn, and it is 948 wide (tree units), as wide as its scroll view scrollable (66,380 948x234): fully: true holds at one exact scroll offset only, which no swipe can be aimed at — drop fully: true, or accept what it shows' ('… wider than its scroll view scrollable (66,380 948x234): no scroll offset shows all of it — drop fully: true, or accept what it shows' when it is larger), quoting the smallest of its scroll views along that axis; a plain scroll_until stops on it once its centre is in view. Within 1 unit of that scroll view's size counts as as large. It is judged only where both its sides are known along that axis (on Android not where the dump cuts it at the screen's edge, so a carousel's card first fails once a swipe brings both its sides inside the screen); where that scroll view scrolls on that axis as the tree tells it (on Android by its class — a Compose lazy list or a RecyclerView tells none; under wda also by its content laid out past its frame); where what of it is drawn is not cut shorter by an outer scroll view; and where its frame there is not cut by the soft keyboard or a system bar (that failure names the keyboard or the bar instead). Across a scroll view's axis (a row as wide as its vertical list) it is the stuck failure as before. An element with a little more room than that (up to about the shortest swipe, ~50 px) can still be swung to and fro until maxSwipes.
- With treeSource: idb, which lists no scroll view, a fully: true stop is first checked on one screenshot for a line its scroll view cuts it at (its edge band reading as the screen beside it, 'cut at the edge of a scroll view the tree does not list'), and the plain stop, like tap, judges a row past its scroll view's clip on the screen alone — set app.ios.treeSource: wda to have the scroll views judged.
- When a sheet's grabber (iOS `Sheet Grabber`) reports another detent at the last read than at the first, the reply or the failure ends "; the sheet moved from its Half screen detent to Expanded" — the sheet moved during the call (a swipe on a half sheet's list at its top drags it up, but it is said too when no swipe was sent); the verdict is the same.
- A stop reached after a swipe is reported only once a further read finds the element where it was (a fling can carry it on; one still moving after 3 such reads is reported as still moving); one a fling carried past the viewport (on Android also one then dumped clipped out past its scroll container's edge — never on the first read, where the given direction stands), or one resting in it at the edge the swipes push it out through (clipped there, its centre under the status bar, with fully: true across the navigation bar's top (Android), or under something of the app drawn over that side — or over all of it but a strip on that side — in that half of the screen), is swiped back, each turn with half the reach — also when a list drops it from the tree right after a read had it short of the edge it left through — and an element in the tree, off screen with a non-zero rect, that 2 swipes no longer move fails then ("content exhausted, or the swipes were not taken" — or, when the swipes touched down on something drawn over the list, naming it first), as does an element not in the tree after 2 identical swipes that change nothing on screen (not while a progress indicator shows; under idb, which lists only what a presented sheet, alert or cover leaves, it adds: if the element lies beneath one, close it first — and until a swipe has changed the screen, a swipe toward content above for an element never in the tree is sent short and slow, 160 pt over 600 ms, so such a sheet springs back rather than being dismissed); no swipe is sent before a tree read has succeeded (the reads go on to the timeout, which then says none succeeded); fully: true fails likewise on a clipped element 2 swipes no longer move; an element in the viewport that the swipes no longer move gets one swipe the other way first, when that way was not swiped yet, and fails only if that moves it neither.
- With treeSource: wda (iOS), 1 swipe that moves nothing is enough where the tree itself lists the content of the scroll view swiped ending that way, along the axis it scrolls on, and the swipe touched down on nothing drawn over it ("the tree lists the content of … ending at its top — content exhausted"); when that tree places the element past the OTHER end of that same scroll view, the swipes turn once toward it instead of failing, at full reach, and the reply or failure says so ("1 swipe up did not move … so averi turned down, as the tree places the element below it") — the given direction is always swiped first.
- With treeSource: wda too, once the element is in the tree short of what its scroll view shows and a swipe was seen to carry it, no swipe reaches further than it still needs at what that swipe carried it, where one swipe could carry it past (a short scroll view's fling).
- The timeout is checked once a round, after its tree read (and, on Android, its keyboard queries), so a call can run past it by one swipe, the settle after it and one more such round — the one that shows what that swipe did; the time a failure reports includes all of it.
- On Android each swipe is drawn over the target's scroll container (the screen's largest before the target is found), touching down above anything drawn over the container's lower half (a floating tab bar) when the content lies below, and slowly enough to drag, not fling, the list — about 1 s for a full-screen stroke, ≈ 0.45 screen heights a second — so one swipe moves the content about its own length and no row is skipped between reads.
- On Android a node's bounds are mostly cut to its scroll container (and the display; a rect past it is judged by what of it the container draws), so a fully: true stop whose top or bottom edge (left/right for a sideways scroll) lies exactly on its scroll container's is checked with one short probe swipe toward that edge (well under a pull-to-refresh), drawn inside a scroll container with room for it: if nothing moves the stop stands and the reply says it was checked; if more of the element shows still on that edge it was cut, and the next swipe reveals the rest (with no swipe or time left, or no room for that swipe, the call fails naming the cut — never "fully visible"); if it moves otherwise it is judged again.
- On Android a node running past a scroll view that ends inside the screen is dumped cut at the SCREEN's edge (a carousel's card ending at the screen's right edge past its carousel's; a list's row ending at the screen's bottom below its list's, above the navigation bar), so how far it runs past is unknown: a clipped stop says "at most N% of it is in the viewport — uiautomator does not say how far it runs past the screen's right edge", as do the stuck and bound failures. Its centre is unknown too, so a default stop on it, when the content lies that way, first takes ONE more swipe — cut so the side it knows comes at most up to its scroll view's far edge — and then stops as the next read finds it; never a swipe the other way, never past maxSwipes or the timeout. Such a swipe counts as one of the swipes.
- The probe counts as a swipe (a list's first row at rest costs one); with none left the reply says the edge may be cut.
- With no scroll container around it that has room for the probe, or when every one from that edge outward scrolls only across it (a horizontal carousel for a top or bottom edge, no vertical list around it), no probe is sent and the reply says the edge may be cut and why.
- An element whose two edges along the scroll both lie on its scroll container's (it fills it exactly) is not probed — one probe cannot tell which side is cut — and the reply says it may be cut (usual for a card as tall as its carousel; check with a screenshot).
- With the soft keyboard up (Android; iOS with treeSource: wda, or idb's band read by its shape) the viewport is the screen ABOVE it: the part of an element under the keyboard does not count as visible, the swipes touch down clear of it (and never higher than without a keyboard), and a reply clipped at the top edge of the keyboard, or a failure, names it (a keyboard that covers the whole screen fails at once).
- Nothing is pressed to hide it — press_key back first (Android) to judge the whole screen.
- On Android, a stop that would say "fully visible" while the element lies flush with a node drawn after it outside its scroll view (a bar pinned over the list or riding on the keyboard, whose surface may draw past its node) is first checked with one screenshot per claimed stop (a fully: true call refused so may claim again after a swipe that moved it: at most one per swipe, plus one): if a band of the colour around that node lies over the element's edge, the reply says how many px and which colours — the stop stands only when the band leaves its centre clear; with fully: true, or a band over its centre, the swipes go on; if the screenshot cannot tell, the reply says "fully visible by the tree" and why.
- A node as wide as the screen beside it is not checked.
- On Android, with fully: true, a text drawn after the element over the margin of its touch target only (Compose dumps a control's touch target, 48 dp tall, past what it draws: the next field's title over a field's bottom edge, narrower than the field and clear of its centre) is judged on a screenshot — one while the two lie where it was taken, another when a swipe moves them; one for the call once it shows the text drawn over the element: where every pixel of the overlap is the colour of the element's own rows beside the text, it does not count, and the reply says so ('fully visible after N swipes — text "…" (…), drawn after it, overlaps its bottom 6 px with nothing a screenshot shows …'); else it counts, and the failure says what the screenshot showed.
- A color/ocr assert judges it so on the frame it captures anyway.
- No other stop takes a screenshot.
- On Android, when the input method reports a keyboard the window state gives no area (one still coming up?), a failure or a fully: true reply says so: that keyboard was not judged; with a floating keyboard, everything below its panel's top edge, full width, counts as covered — except the strip between its panels and the band it keeps at the bottom, which none of it covers: an element wholly inside that strip that stops cleanly there is judged there (its reply names no keyboard).
- With treeSource: idb nothing in the tree is marked as the keyboard; averi reads where its background starts by its shape and judges against that line as above: the swipes touch down above it, no stop has the element's centre below it, and with fully: true none of the element may lie below it.

Arguments:

- `selector`: Element to scroll into view, e.g. 'id:submit_button'
- `direction`: Default down
- `maxSwipes`: Default 6
- `fully`: Require the element ENTIRELY inside the viewport, not just overlapping. Default false
- `timeoutMs`: Default 15000

## `ensure_state`

- Get the app into a named state from averi.yaml (e.g. "logged_in"): detects if already there, otherwise runs the reach flows (login etc.) and confirms.
- Idempotent — always prefer this over manual login taps.
- If the UI tree cannot be read (e.g. iOS idb stuck on a 0×0 tree) or holds nothing rendered (a cold launch's decor or splash) for the whole ~20 s second look, a destructive reach flow (clearState, or destructive: true) is refused rather than run blind: the call fails with "Refused to run reach flow …" and a ⛔ line in the trace — nothing was wiped; compare with screenshot and retry once the screen has rendered, or run_flow the rung deliberately.
- Returns the step trace and a final screenshot, settled the same way `screenshot` settles it.

Arguments:

- `state`: State name from averi.yaml

## `assert`

- Run declarative checks against the current screen: element exists (default) / absent / text exact / match regex, rect geometry vs Figma-frame values ({"element":{...},"rect":{"x":24,"w":345,"frameWidth":393}} — deltas in % of screen width; y is measured but never fails), fill color vs an expected hex ({"element":{...},"color":{"expected":"#FDFDFD","deltaE":8}} — CIEDE2000 over the element's sampled region; hex only, token names resolve upstream), rendered text read back off the screenshot ({"element":{...},"ocr":{"text":"CONTINUE","heightPct":2.96}} — what the user SEES, which the tree often does not carry: on iOS SwiftUI collapses a button into one node whose label is an authored a11y summary, so the visible string is absent; text is compared exactly — whitespace runs folded, case kept — except that a reading that differs only in what the recognizer cannot tell apart (typographic punctuation ’ “ – … vs its ASCII look-alike, letters with vs without diacritics — either way round) passes with a note naming the characters; a match pattern written with them matches such a reading with its own folded, and a pattern with no typographic or accented character of its own (none spelled as an escape either) is also run on the reading with those folded — match "Payee's" matches a reading Payee’s, the note saying the reading's ’ was folded (case is never folded, and a pattern that names a typographic character keeps it: (?<!’) still sees the reading's ’); heightPct is rendered ink height in % of screen width, the type-size check, single-line only; macOS-only, fails closed elsewhere), and screenshot pixel-diff vs. a stored baseline (auto-created on first use under .averi/baselines/; on iOS the status band (top safe area) is left out of a baseline diff).
- Prefer element asserts (deterministic, cheap) over screenshots.
- A color/ocr assert never samples what lies over its element: one under the soft keyboard (Android; iOS with treeSource: wda, or idb's band read by its shape), under the status bar (the top band the device reports — on iOS its top safe-area inset, 62 pt on a 402x874 iPhone; on Android the visible system status bar, 66 px on a 1080x2220 phone, which an app drawn edge-to-edge lays its top under), or under another element of the app drawn over any part of it (a pinned button bar and the area below it, a floating tab bar, a top bar over a scrolled row — judged over the whole rect, not only its centre; the element's own content listed beside it, a transparent clickable layer, and an overlap of 2 units or less are not counted; on Android also, for an element in no scroll view, an element drawn after it whose node begins exactly where the element's top or bottom edge ends and reaches past it at both ends — a pinned button: Compose leaves out of a node's bounds what a later node covers, and the failure says the element may run on under it) fails closed naming what covers it and its rect, and the poll goes on, so one moved out before the deadline is measured; scroll_until it with fully: true first, or assert something in it that lies clear of that — except for a control overlapping it in a container iOS lists in reading order (as for tap), where the assert judges which is drawn on top on the frame it captures anyway, as for tap: the element seen on top is measured; else the failure names the control drawn over it (or says the order is not told) and advises no scroll.
- Under a screen presented over the element (a layer WebDriverAgent shows presented, or a modal's full-screen dimming view or a sheet's scroll view, as for tap) no scroll helps, and the failure says so instead: 'a screen is presented over the element (a modal or a sheet) — close it first; no scroll moves the element out from under that screen' (whatever else lies over it — the status bar, a possible cut at the navigation bar — in place of its own advice, and wherever the element lies, nothing of it on the screen included; a keyboard the device reports is still named first, with its own).
- An element nothing of which (of what the assert reads) lies on the screen fails closed with 'nothing of the element lies on the screen (element …, screen …)', and one of which the screen's edge leaves a sliver no thicker than 2 units (pt on iOS, px on Android) with 'only a sliver of the element lies on the screen, too thin to measure (element …, on the screen …, screen …)' — scroll it on-screen (scroll_until it first), or, under a presented screen, close that screen first; the poll goes on, so one scrolled on-screen before the deadline is measured.
- On iOS with treeSource: wda an element on the screen that its scroll view draws none of (listed past the scroll view's frame, as WebDriverAgent lists a scroll view's content) fails closed likewise with 'nothing of the element is drawn: it lies outside its scroll view <the scroll view> (element …, screen …)', and one its scroll view's edge leaves a sliver no thicker than 2 pt with 'only a sliver of the element is drawn, too thin to measure: the rest lies outside its scroll view <the scroll view> (element …, drawn …, screen …)' — never measured on what shows there; only the part the scroll view draws is judged and sampled.
- With treeSource: idb, which lists no scroll view, a color assert whose region holds nothing but the colour of the screen beside it fails closed ('its region reads as the screen beside it (#…): idb lists no scroll view to say it is drawn there') — measure it under treeSource: wda.
- On Android the navigation bar at the bottom (the visible bar the device reports, from y 2154 on a 1080x2220 phone; a portrait screen only) counts the same way, and an ocr assert on an element that may be cut at it — its bottom and its scroll container's both on the bar's top edge — fails closed too (scroll it up: scroll_until it with fully: true); a color assert on such an element is measured.
- Judged over what the assert reads: the whole rect for ocr; for color the part of the rect on the screen, inset 12% a side — the region its sampler reads — so an ocr assert on a whole screen fails on the status bar, a color assert on one does not.
- On Android an assert whose element is not in the tree fails "not found within … (the tree lists only the active window: if a sheet or a dialog is open over the screen, close it first)" when the window manager does not say the window is the app's screen alone: uiautomator lists the active window only, so the element may lie beneath a sheet or a dialog the tree does not list — if one is up, close it and assert again.
- Beneath a dialog or a sheet the tree lists alone (ui_snapshot's root "presentation": "dialog" or "screen") the parenthesis names it instead: "(a dialog is presented over it, and the tree lists only that window — close it first)".
- A `match` (element or ocr) that is not a valid JavaScript regex is refused with the arguments, naming the field, before any device is touched.
- With averi.yaml naming the app for the platform, an appAlive health line follows the results; without averi.yaml the asserts run alone, and an invalid one fails the call on either platform.
- Budgets: an assert without its own `timeout` waits up to 3 s (tree asserts) or 12 s (color/ocr — a round is a tree read plus a settled pair of captures, ~4.3 s on an Android emulator, and a screen with a clock or caret needs two); a passing assert returns at once, a color/ocr assert that keeps failing (a wrong colour or text, a frame that never settles, an element not found) polls out its whole budget — pass `timeout` to shorten it — while one that can never be measured fails closed after one read: a screenshot the device refuses, or an ocr assert on a host with no usable recognizer (no macOS Vision, no swiftc, or a recognizer that did not compile).

Arguments:

- `asserts`: Assert specs, e.g. [{"element":{"id":"transfer_form"}}, {"element":{"id":"error_banner"},"absent":true}, {"element":{"id":"amount"},"text":"100.00"}, {"screenshot":{"baseline":"transfers","threshold":0.01}}, {"element":{"id":"card"},"rect":{"x":24,"w":345,"h":129,"frameWidth":393}} (Figma-frame units; y measured but never fails), {"element":{"id":"card"},"color":{"expected":"#FDFDFD","deltaE":8,"sample":"dominant"}} (fill vs hex, CIEDE2000), {"element":{"id":"cta"},"ocr":{"text":"CONTINUE","heightPct":2.96}} (what the element RENDERS, read back from the screenshot — not the same question as "text", which reads the accessibility tree: on iOS a button's visible label is often absent from the tree entirely; heightPct pins rendered ink height in % of screen width, single-line elements only; macOS-only)]

## `verify`

- THE verification tool: run the same sequence — optional ensure_state, optional flow, then asserts — on the requested platforms (default: both android and ios) and return per-platform results plus screenshots.
- The legs run concurrently; their sections and images are always reported in android-then-ios order regardless of input order (images in that order, one per leg that returned a screenshot; a leg whose section says FAILED or `⚠ screenshot:` has none).
- Single-platform work passes platforms: ["android"] or ["ios"]; for cross-platform tasks, run the default (both) before declaring the task done. contract points at a layout-contract JSON (screen anchors in Figma-frame units) → a per-anchor geometry table is appended (## rect parity), when anchors carry bg/bg_dark/sample fields the legs' screenshots are sampled per anchor into a ## color parity table (CIEDE2000; ALWAYS the light axis — bg values — since averi cannot switch device themes; bg_dark anchors wait for the dark-mode round), and when anchors carry text/text_dynamic a ## text parity table compares the RENDERED copy and type size (OCR off the same screenshots; macOS-only, falls back to the tree with a note): numbers over impressions.
- A contract field a requested table cannot read (a bg that is neither hex nor token, an unknown sample mode, a non-string text, a non-boolean text_dynamic, a tolerance_de / tolerance_size_pct / tolerance_aspect_pct that is not a positive number) REFUSES the call before any device is touched, listing every such field.
- An `environment` averi.yaml does not declare is refused the same way, before any device, naming the known ones.

Arguments:

- `platforms`: Platforms to verify (default: both). Duplicates collapse; legs run concurrently and are reported android-then-ios.
- `state`: State to ensure first (from averi.yaml)
- `flow`: Flow to run (from averi.yaml)
- `asserts`: Assert specs, e.g. [{"element":{"id":"transfer_form"}}, {"element":{"id":"error_banner"},"absent":true}, {"element":{"id":"amount"},"text":"100.00"}, {"screenshot":{"baseline":"transfers","threshold":0.01}}, {"element":{"id":"card"},"rect":{"x":24,"w":345,"h":129,"frameWidth":393}} (Figma-frame units; y measured but never fails), {"element":{"id":"card"},"color":{"expected":"#FDFDFD","deltaE":8,"sample":"dominant"}} (fill vs hex, CIEDE2000), {"element":{"id":"cta"},"ocr":{"text":"CONTINUE","heightPct":2.96}} (what the element RENDERS, read back from the screenshot — not the same question as "text", which reads the accessibility tree: on iOS a button's visible label is often absent from the tree entirely; heightPct pins rendered ink height in % of screen width, single-line elements only; macOS-only)]
- `contract`: Path to a layout-contract JSON ({screen, tolerance_pct, tolerance_aspect_pct, figma_frame_width, anchors:[{id,x?,y?,w?,h?,aspect?,bg?,bg_dark?,sample?,text?,text_dynamic?}]}, Figma-frame units) — after the legs, geometry is compared per anchor in % of screen width and a "## rect parity" table is appended. Anchors with bg (hex; #RRGGBBAA alpha dropped) additionally get their fills sampled from the legs' screenshots into a "## color parity" table (dE(a,i) primary at tolerance_de, default 8; vs-contract at 1.5x); anchors without bg are color-compared platform-to-platform only. A derived `aspect` row also compares each anchor's SHAPE android-vs-ios; omitting w/h does not disable it (omission means "not pinned", and the row's value is catching shape bugs on unpinned sides) — set `aspect: false` on an anchor whose height the two platforms genuinely derive by different mechanisms (e.g. Android's a11y touch-target floor inflating a node box to 48 where iOS reports 44), and put the reason beside it. `tolerance_aspect_pct` is its own threshold because a ratio spread is not a %-of-screen-width delta; it defaults to tolerance_pct. The color check always runs the LIGHT axis (bg): bg_dark is carried in the contract for the deferred dark-mode round, which needs a theme input AND a device actually captured in dark mode. Anchors with text (the exact rendered string) or text_dynamic (true for amounts/dates, whose locale formatting legitimately differs) get a "## text parity" table: the copy is read back off the legs' screenshots with OCR — what the user SEES, since on iOS the tree carries authored a11y summaries rather than rendered copy — and compared android-vs-ios and vs the contract, plus rendered ink height as the type-size check (tolerance_size_pct, default 10%, compared only where both strings match). OCR is macOS-only; elsewhere the table falls back to tree evidence and says so.

## `get_logs`

- Device logs (logcat / os_log) since N seconds ago — scan for crashes and exceptions. grep filters to lines matching a case-insensitive regex (e.g. "tpm|validation") — prefer it, unfiltered pulls run to thousands of lines.
- Only the LAST maxLines matching lines come back (the tail is where the failure is); the header reports how many the grep matched against how many are shown, so raise it deliberately rather than by default.
- A grep that is not a valid JavaScript regex is refused with the arguments, before any device is touched.

Arguments:

- `sinceSeconds`: How far back to read
- `grep`: Case-insensitive regex; only matching lines are returned
- `maxLines`: Keep only the last N matching lines (default 400). A grep alone is not a budget — a broad one matched 2,002 lines / 483k characters in one measured session.
