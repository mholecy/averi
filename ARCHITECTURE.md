# Agent Mobile Verify — Architecture & Design Doc

*A free MCP server that lets coding agents verify their work on iOS Simulators and Android Emulators, including apps that require a login step.*

Working name: **`averi`** (Agent VERIfier). Rename freely.

---

## 1. Problem & positioning

Coding agents (Claude Code, Cursor, etc.) can now write native mobile code, but they can't close the loop: build → install → **get past login** → navigate → verify. Generic tools exist, but none of them solve the *stateful app* problem:

| Tool | Strength | Gap for us |
|---|---|---|
| [mobile-mcp](https://github.com/mobile-next/mobile-mcp) | Generic taps/screenshots via accessibility tree, iOS+Android | No app knowledge: agent must rediscover login every session |
| [Maestro MCP](https://docs.maestro.dev/get-started/maestro-mcp) | Agent writes/repairs Maestro YAML tests | Oriented at producing test suites, heavy dependency; login state still the agent's problem each run |
| Appium | Mature drivers | Per-project setup, slow, overkill for "verify my change" |

**Differentiator:** the tool is *app-aware*. Teams check an `averi.yaml` descriptor into the repo that declares how to reach known states (logged-in, specific screens). The agent calls one high-level tool — `ensure_state("logged_in")` — instead of fumbling through a PIN keyboard with 15 tap calls. That determinism + cross-platform parity + verification helpers is the product.

## 2. High-level architecture

```

The arrows show the main path only; a layer may import any layer below it (flow → verify for inline `assert:` steps, verify → adapters for captures, mcp → interact/adapters for the primitive tools — the one-way rule is below).

Clean separation of concerns:

- **Device Adapter** (`adapters/`) — the only layer that knows platform commands. One interface, two implementations. Everything above is platform-agnostic. `adapters/types.ts` also holds `everyNode`, the ONE pre-order tree walk (since 2026-10-06; it was in `field-errors.ts`, a pairing module two unrelated callers imported from): field-error pairing, `verify/text-hint.ts`'s `flattenTree` and `ui-tree/bare-tree.ts` all walk with it. ```sh
grep -rn "from '\.\./" src | sed "s|:.*from '\.\./|  ->  |"
```

The rule earned its keep: the platform layer once imported the selector layer (for a `tapElement` that contained no platform code), and `flow/config.ts` had become the de-facto home of vocabulary — `ElementSpec`, `ElementAssert`, `parseDuration` — that neither flow nor config owns. Runs entirely locally on the dev machine (device access requires it); nothing talks to the cloud.

    dragSpeed?: number              // OPTIONAL (since 2026-10-09): screens a second under which a stroke drags rather than flings this platform's scroll views — Android 0.45 (measured fling, AOSP spline, time cost: adapters/android.ts#dragSpeed); absent on iOS (unmeasured; its default 300 ms stroke); scroll_until sizes its strokes from it (interact/swipe.ts#dragMs)

    keyboard?: KeyboardOracle       // OPTIONAL capability (since 2026-10-04): present where the keyboard is a separate window `back` hides — Android; absent on iOS, where it is part of the tree.       touchable(): {witness, region}            // since 2026-10-08: the keyboard WINDOW's touchable region (`touchable region=SkRegion((l,t,r,b)…)` of `dumpsys window InputMethod`) beside `mInputShown`, one adb call (`TOUCHABLE_COMMAND`), raw facts — asked by a reading (`ui-tree/keyboard-cover.ts#readKeyboard` — the one composer of an oracle reading, behind every reader of the keyboard) — only after state() read shown, and only for a question about area; `panelsBeyond` decides what counts (input method shown in the same call, a region holding the band exactly, rects inside the band's screen, never the band) and the reading carries it as `panels` beside `frame` — a floating Gboard's panel, outside its 132-px band (docs/bugs/2026-10-05-android-floating-gboard-keyboard.md, device check). Device discovery is NOT on this interface either (2026-10-08, the iOS adapter
stack review's candidate 1): which devices a platform has is a question about the
platform, answered by `adapters/discovery.ts` (`listAndroidDevices`: `adb devices -l`
plus one `adb -s <id> shell getprop` per online device, its argv `adb-shell.ts#adbShellArgv`'s;
`listIosDevices`: `simctl list devices --json` through `xcode-env.ts#simctl`, the one
spelling of a simctl call — `xcrun simctl` under the DEVELOPER_DIR probe — which
`IosAdapter`'s simctl calls go through too). The registry takes it as its second dependency beside the adapter
factory (`DeviceDiscovery`, `mcp/registry.ts` — both injected or neither, so a test
with a fake factory cannot list the host's real devices) and asks it on every
`get()`, as it asked a probe adapter before. Until then `listDevices()` was an adapter
member, so both adapters carried an unbound mode the registry used for nothing else —
an `IosAdapter` without a UDID (simctl's `booted` alias, a lazily resolved UDID for
idb, a `uiTree()` that refused) and an `AndroidAdapter` without a serial (adb without
`-s`, "the default adb device", a "more than one device" diagnosis). The serial / UDID
(and on iOS the tree source) is now a constructor invariant, and that mode is gone.
`setClipboard` went the same day: an interface member with no caller, which Android
only threw for; a first caller (pasting an OTP) would bring it back as an optional
capability, like `keyboard?`.

Since 2026-10-09 (C5) the Android listing also keeps an `unauthorized` device (state
`unauthorized`, Android only), and `discovery.ts#androidUnusable` words why an
`unauthorized` or `offline` Android device cannot be driven and what to do; the
registry puts it after the device's name in its three refusals (auto-pick,
`select_device`, a pinned device), which until then said "No booted Android
emulator/device found", "boot it first" and "is no longer booted". Such a device is
never picked.

Selector-based tapping is deliberately NOT on this interface: `tapElement(adapter,
target, opts)` (`interact/tap.ts`, formerly `ui-tree/tap-element.ts`) resolves the target against the normalized
tree through `interact/`'s one resolution policy and keyboard guard (§8) and calls `tap(x, y)`. Nothing in it is platform-specific, and both adapters
had implemented it identically — which forced the platform layer to import the
selector layer above it, inverting exactly the direction this section describes.

**Android implementation** — pure `adb`:
- screenshot: `adb exec-out screencap -p` — since 2026-10-08 the bytes are judged in the adapter (`adapters/screenshot-bytes.ts`, shared with iOS): exec-out exits 0 with whatever the guest wrote, so an empty or non-PNG capture (`Killed` on a dying emulator) is a transport error naming the device and the command. Until then it was returned unchecked, and two empty captures are `Buffer.equals`, so the stability wait called a dead device's 0-byte frame SETTLED and the `screenshot` tool returned it with no note; `verify/capture.ts` keeps a length floor under that contract (`screenshotOf`), and its decode failure no longer names adb or simctl commands. A refused capture throws, and each caller contains it: inside a color, ocr or screenshot-baseline assert it ends THAT assert after one capture, rather than polling a dead device to the deadline, as a fail-closed failure quoting the adapter's first line (`screenshot failed: …; failing closed, color unchecked`), and `assertAll` goes on to the next assert (`verify/pixel-poll.ts`'s header; since the same day an `ocr` assert's measurement takes the same exit for an OCR engine that will never read, by marking its verdict `final`, and `failClosed` itself drops the reason's trailing full stop; flow `assert:` steps take element asserts only, so they never capture); as the final capture of a `verify` leg or `ensure_state` it is caught (`run/verify.ts#finalFrame`) so the trace, asserts and health line stand, with one `⚠ screenshot:` line and no image.
- UI tree: `adb exec-out uiautomator dump /dev/tty` (the XML on stdout, then uiautomator's status line; XML → normalized JSON). With `settle`, one re-read after 1 s of "null root node" (`NULL_ROOT_RETRY_MS`). Fallback for Compose apps with poor semantics: coordinate taps from screenshots.
- input: `adb shell input tap/swipe/text/keyevent`; the viewport from `adb shell wm size` (pixels, memoized — `viewport-memo.ts`). Which characters `input text` cannot take as text (C0 controls and DEL) and what it may do with them (ENTER for a newline or a return, a key event otherwise) is `adapters/input-text.ts`'s, read by `interact/type-text.ts`'s refusal and the adapter's defensive one (round 7)
- install/launch: `adb install -r`, `adb shell am start` / `pm clear`. A launch names its entry point one of three ways: nothing (`monkey -c LAUNCHER`), an activity (`am start -n pkg/activity`, with the intent if one is given), or an intent alone (`am start -p pkg -a …` — scoped to the package, Android resolves the activity; since 2026-10-03). Whether a start started anything has ONE owner, `runStart` in `adapters/android-start.ts` (2026-10-07; the 2026-10-04 review's C10 had left this code in place until openDeepLink could share it): it reads the `am start` of a launch and of `openDeepLink`, and the `monkey` launch, into `started` or `refused` with the command's own lines, and throws anything else (adb failure, timeout) as it came. `am start` refuses in its output — an `Error` line or a Java exception, at exit 0 too — and monkey by its exit status, with its `** ` reason on stdout, which the ExecError message dropped. The callers word the refusal: the launch names `activity:` / `app.android.activity`, the deep link its url. A deliberate exception to "adapters speak platform only" (since 2026-10-03, extended to the monkey launch 2026-10-07): the Android launch refusals, from `am start` and from `monkey`, name config keys (`app.android.activity` in averi.yaml), the flow step's `activity:` and the `launch_app` tool, because the reader's next move is in the config or the call, not in adb; a typed error translated by the two callers (run/ for `launch_app`, flow/ for the launch step) would have been one message with two translation sites that must agree. Only words cross the layer, no import (`launchRefused` in `adapters/android.ts`). A deep link nothing handles therefore throws (until then `open_deep_link` answered "Opened"). What is unmeasured there is written once, in that module's header.
- logs: `adb logcat`
- what the device's shell receives: ONE owner, `adapters/adb-shell.ts` (2026-10-07). adb joins everything after `shell` with a space, unescaped, and the device's `sh -c` splits it again, so an unquoted `&`, space, `;`, `$` or backtick in a value was interpreted on the device (measured that day: a deep link cut at its `&`, an extra split at a space, `$HOME;id` executed). Every device command in `AndroidAdapter` goes through `shell(argv)`, which quotes each word (`shellQuote`), `execOut(argv)`, which does not — for `exec-out` the adb client escapes the words itself (`escape_arg`) — or `rawShell(line)`, the named exception for a pipe or `|| true`, with any user word quoted into it by `shellCommandLine`. `shell(argv)` and `listAndroidDevices`' getprop (`adapters/discovery.ts`) both build their argv with `adbShellArgv(serial, argv)`, so the `adb -s <serial> shell` + quoting is spelled once. Pinned through a real sh standing in for the device (`tests/helpers/device-sh.ts`). What this changed for `typeText` (a newline, return or tab is refused — `pressKey('enter')` is the route for a newline or a return, and since the code review of round 7 (P2) the refusal names it for those two only — a tab has no key, nor has any other control character, `adapters/input-text.ts#controlCharRemedy`; since the code review the same day the refusal is `interact/type-text.ts`'s, the one statement of what text averi types: every C0 control character and DEL, on both platforms, before any device call — `fillField` checks before its keyboard guard, focus tap and clear, the type_text tool without a selector and the flow's `type:` step type through `typeIntoFocused`; iOS used to type a `\n` — with the adapter's check kept as a defensive assert) and `isAppRunning`, and what is UNVERIFIED on a device, is written once, in the header of `adb-shell.ts`.

  - **Shutdown contract (0.8.1; one hop longer since 2026-10-02):** the child WDA is owned by `WdaServer`, `WdaServer` by `WdaTreeSource`, the tree source by `IosAdapter`, adapters by `AdapterRegistry`, the process by `mcp/lifecycle.ts` — and disposal runs down that chain, never across it. `lifecycle.ts` handles SIGTERM/SIGINT/SIGHUP (Node runs no `exit` hook for a signal) and awaits `registry.shutdown()` within a 1.5 s budget; `IosAdapter.dispose` returns its tree source's `dispose()`, which for the WDA source is `WdaServer.shutdown()`: it stops the child and waits for the port to go quiet, killing the listener if xcodebuild's teardown did not reach the runner (it lives under `launchd_sim`, outside our process group). The idb source has nothing to release. After its dispose the WDA source is terminal: a read is refused, naming the deselection or shutdown, rather than starting a server nobody would dispose — reachable when a `select_device` evicts the adapter a running flow still holds. `process.exit(0)` then runs the old `exit` hook as a backstop. Not covered: SIGKILL, a second signal during the wait, a SIGTERM during the first WDA build (`docs/bugs/2026-09-18-wda-orphan-after-server-restart.md`).

**Normalized UI tree** is the key abstraction: `{role, label, identifier, value, rect, children}` (plus the optional `error` and `ofKeyboard` marks, and the other optional source marks `adapters/types.ts#UiNode` documents — among them WDA's `hidden`) identical on both platforms. Selectors like `id:login_pin_field`, `text:"Continue"`, `role:button label~"Pay.*"` resolve against it on either OS. This is what makes flow descriptors cross-platform.

## 4. Flow descriptors (`averi.yaml`)

Checked into the app repo. Describes app states and how to reach them. Every path it contains — the build paths below, the sibling `.env.averi`, the `.averi/baselines/` directory — resolves relative to **the descriptor's own location**, so the file is portable across working directories (nested repos, monorepos) and absolute paths stay untouched. Example for a PIN-login banking app:

```yaml
app:
  android: { package: md.victoriabank.myvb.dev, apk: app/build/outputs/apk/dev/debug/app-dev-debug.apk }
  ios:
    bundleId: md.victoriabank.myvb.dev
    app: build/Debug-iphonesimulator/MyVB.app
    # treeSource: wda                 # optional: RN / SwiftUI container ids (§3); keyboardDismiss needs it
    keyboardDismiss:                  # optional, ordered (§8): how to hide the soft keyboard when it covers a tap target —
      - tap: { id: login_title }      #   a NON-interactive element (a title, a label) whose tap hides it without submitting,
      - accessory: true               #   or the input-accessory toolbar's trailing button (the "Done" above a number pad)

credentials:              # values come from the environment (or .env.averi), never from YAML
  username: ${AVERI_USER}
  password: ${AVERI_PASSWORD}
  pin:      ${AVERI_PIN}
# Values resolve from the environment the load assembles: the real one, over
# a `.env.averi` file next to averi.yaml (gitignore it) — existing env vars
# take precedence, so the project is self-contained and CI can still inject
# via real env. The file is re-read on every ensure_state / run_flow / verify
# call (the tools that resolve credentials, §5) and never written into
# process.env (since 2026-10-04 it is a value the loader returns beside the
# config, flow/load.ts).

environments:             # optional: per-backend credential overrides
  dev:
    credentials:
      username: ${AVERI_DEV_USER}
  staging:
    credentials:
      username: ${AVERI_STAGING_USER}
# Layered ON TOP of `credentials:` per key, so shared secrets are declared once.
# Selected by the tool's `environment` argument, else $AVERI_ENV, else
# `defaultEnvironment:`. Resolved once per engine, so one run can never mix one
# environment's username with another's password; an unknown name is refused
# by the run layer's pre-flight before any device is touched (2026-10-05). The
# active environment is the first trace line:
# a wrong login name is rejected one screen AFTER it is typed, so without that
# provenance an environment mix-up is indistinguishable from a bad credential.

states:
  logged_in:
    detect:                       # how to recognize we're already there
      any:
        - element: { id: dashboard_root }
        - element: { text: "Accounts" }
    reach: [login]                # flows that get us there, cheapest first

flows:
  login:
    steps:
      - launch: { clearState: false }
      - branch:
          - when: { element: { id: pin_keyboard } }     # returning user → PIN
            do:
              # keypad matches per-digit keys by resource-id or, for keypads
              # without ids (common in Compose), by visible text:
              #   keypad: { text_pattern: "{digit}" }
              - type_pin: { value: $pin, keypad: { id_pattern: "pin_key_{digit}" } }
          - when: { element: { id: username_field } }   # fresh install → full login
            do:
              - tap:  { id: username_field }
              - type: { value: $username }
              - tap:  { id: password_field }
              - type: { value: $password }
              - tap:  { text: "Log in" }
              - wait: { element: { id: pin_setup_screen }, timeout: 15s }
              - type_pin: { value: $pin, twice: true }   # set + confirm
      - optional:                                        # dismissable interstitials
          - tap: { text: "Not now" }        # biometrics prompt
          - tap: { id: promo_close }        # marketing popup
      - wait: { state: logged_in, timeout: 20s }

  goto_transfers:
    requires: logged_in
    steps:
      - tap:  { id: tab_payments }
      - tap:  { text: "New transfer" }
      - wait: { element: { id: transfer_form } }
```

The example is not the whole schema — that is `flow/config.ts` (its module-private `configSchema`, typed out as `AveriConfig`), and `skill/references/averi-yaml.md` has the agent-facing reference. Beyond what it shows: `app.android.activity` pins the launch activity, `defaultEnvironment:` names the environment used when none is asked for, and a flow may carry `destructive: true`. The step kinds are `launch` (`clearState`, Android `activity`/`intent`), `tap` (+ `timeout`), `type`, `type_pin`, `fill` (`value`, `clear`, `dismissKeyboard`), `swipe` (`direction`, `times`), `scroll_until` (`element`, `direction`, `maxSwipes`, `fully`, `timeout`), `wait`, `assert` (element asserts only), `branch`, `optional` and the per-step `android:`/`ios:` override.

Design points:

- **State detection before action.** `ensure_state` first checks `detect`; login runs only when needed. Handles the "reinstall wipes the session" case automatically, and is idempotent.
- **`reach:` is an escalation ladder, not a script.** `detect` is re-checked after *each* flow in the list and the rest are skipped once it is satisfied, so `reach: [dismiss_post_login_prompts, login]` means "try the cheap idempotent one; escalate only if it did not work". "Did not work" covers both ways a rung can fail to deliver: completing without reaching the state, and *throwing* — a cheap prelude typically fails by timing out on a `tap:` for an interstitial that was not there, and aborting the ladder on that would leave the prelude working only on the runs that did not need it. A thrown rung is never swallowed: it is logged as `⚠ reach <flow>` with the reason, and the last rung's failure still fails the call — after the recovery pass below. This is load-bearing, not a nicety: before it, listing a cheap flow ahead of a destructive one *guaranteed* the destructive one also ran — a `launch { clearState: true }` login burning a device registration on a session that was already alive, because one post-login interstitial defeated `detect` for a single probe (2026-08-26). Order the list cheapest-first.
- **…and it gets one pass backwards.** The mirror of the same finding, measured the same day: the ladder is one-shot and forward-only, so the LAST rung's aftermath can produce a screen an EARLIER rung exists to clear — login finishes, the biometrics interstitial arrives a network round-trip later, after that login's `optional:` windows closed — and nothing re-runs the cure. One `ensure_state` failed where an immediately repeated, identical one passed, because the second restarted the ladder from rung 1; the engine already held the cure and never applied it inside one call, which is not what "idempotent — call it freely" promises. So reaching the end of the ladder short of the state triggers at most one recovery pass per tool call — per engine run, so nested `requires:` and a `verify` leg's state-then-flow share it (since 2026-10-07; the leg used to get one for each) — (`↻ recovery` in the trace) over the earlier rungs, re-checking `detect` after each, then fails with the original error. "Reaching the end" covers both ways it happens: the final wait timing out, and the LAST RUNG THROWING. The second is the shape production configs actually have — a login flow's success criterion is written as the flow's own trailing `wait: { state: logged_in }`, so a late interstitial makes the rung throw and the final wait, where the pass would arm, is never reached. Covering only the first left the motivating incident failing exactly as it had before the fix (measured on device, `docs/bugs/2026-08-26-recovery-pass-skips-throwing-last-rung.md`). A throwing last rung also has its own `detect` to re-check — the one the ladder gives every other failed rung, for the flow that reaches the state and then dies on a later step. Both run before the throw is rethrown, and the caller still sees the ORIGINAL error; the pass is safe on a throw for the reason it is safe on a timeout, since what it re-runs is bounded by the two rules below rather than by why the ladder ended. Two bounds keep it from re-opening the hole above: the last rung is never re-run — it is the anchor the ladder climbs *to* — and every candidate must be provably non-destructive. "Provably" is a static walk (`flowIsDestructive`): `launch { clearState: true }` anywhere in a flow's steps including inside `branch`/`optional`/platform overrides, anything reachable through its `requires:`, an explicit `destructive: true`, an unknown flow, or a `requires` cycle. Every default in that walk points at "destructive", because being wrong there costs a second wipe while being wrong the other way only costs the latency this fix was already spending. The ladder's pre-flight "this rung is DESTRUCTIVE" line is a different question and uses a different, non-transitive predicate (`flowItselfIsDestructive`: the rung's own steps and `destructive: true`, `requires` not followed): it is printed as a fact before `requires` has been checked, and with the transitive walk every navigation flow requiring a logged-in state warned on every call, one line before "already active" (2026-10-05, `docs/bugs/2026-10-06-destructive-rung-warning-false-positive.md`). An escalating `requires` loses nothing — the nested ladder warns on the rung that actually wipes.
- **…and it never wipes blind.** A destructive rung (`flowItselfIsDestructive`) whose immediately preceding probe never read a RENDERED tree is REFUSED: the probe before rung 0 is the entry detect, before any later rung that rung's predecessor's re-check. A probe is `unknown` when every one of its reads failed (`pollTree`'s `treesRead === 0`), and — since 2026-10-07 — `bare` when every tree it read was bare (`ui-tree/bare-tree.ts#isBareTree`: only wrappers and unlabeled decoration, a launch's decor or splash); one rendered read in a window makes it a real "no". Such a probe first gets ONE second look over `ensureTimeoutMs` (20 s by default — the budget that already means "how long a state may take to appear"; the final wait after the ladder uses it too): the entry probe is a single read, so the warm path stays one read, and a cold launch is unreadable or bare for a while — agents hit it by calling `ensure_state` right after `launch_app`. Measured 2026-10-06 on an RN debug build on an Android 13 emulator: null root to ~+3 s, the decor alone (`android:id/content`, `action_bar_root`) +5.3…+13.8 s, `login_screen` at +18.3 s; through WDA the 7-node splash is read at +0.3 s. Until 2026-10-07 the second look was the 5 s settle budget (`tapTimeoutMs`) and only an `unknown` probe got it, and a bare tree counted as "no": the look ended on the decor and `ensure_state logged_out` wiped an app that was already logged out, three runs of three; under WDA the ENTRY probe read the splash as "no" and the wipe ran with no second look at all (docs/bugs/2026-10-06-second-look-reads-android-decor-as-not-in-state.md). The second look is one poll with one deadline, so null root → decor → rendered is ridden out as one transient. A second look that reads the state ends the call ("already active", or "reached after" the previous rung); one whose window held a rendered tree outside it runs the rung, warning as usual — after polling to its deadline, as every detect window does, so a cold launch onto a screen genuinely outside the state pays up to 20 s before the wipe; only a second look that still reads nothing rendered refuses. Then the ladder logs `⛔ reach <flow>` in place of the DESTRUCTIVE warning and throws `UnreadTreeRefusal`, whose cause (`UnreadCause`) is what the probe before the rung and its second look learned TOGETHER: `unknown` with the last read error only when neither read any tree; `bare` with the last bare tree's shape (`7 nodes (roles: container ×6, image ×1)`) when the second look read one; `bare-then-failed` — that shape AND the last read error — when only the probe before it did. Until the 2026-10-07 review the cause was the second look alone, so a bare entry read followed by failed reads said "never read a UI tree", and a failed entry read followed by bare ones said "every read was bare". One clause (`describeUnreadCause`) words it for the `⚠ detect` line, the refusal and the no-reach `SetupError`. Measured 2026-10-06: idb returned a 0×0 tree for minutes on a rendered PIN screen, every probe read "not in state", and mp-native's `logged_in.reach: [dismiss_post_login_prompts, login_registered, login]` would have wiped a registered app. Cheap rungs still run at once on an unknown probe, with no second look (they are how a ladder gets a readable tree; a device that cannot be read is not a screen still drawing); on a BARE probe, since 2026-10-08, they get the same second look first — see "…and a bare tree decides no condition" — and run if it still reads nothing rendered. The look and the refusal are one check at the top of the ladder loop. The bare rule's known miss — a LOADED screen whose only non-wrapper nodes are identified-but-unlabeled icons is called bare — therefore now costs a refusal there: such a screen cannot reach a destructive rung through `ensure_state` (`run_flow` of the rung still runs it). The refusal is terminal like a `SetupError` (`isTerminal`, asked by the ladder's catch; the final wait never enters a ladder, so its catch still asks only for a `SetupError`): an outer ladder whose rung's `requires:` refused must not escalate past it into its own next rung. Salvage runs no rung and the recovery pass never runs a destructive one, so neither needs the check; `run_flow` never refuses the flow's own body (the caller's decision), though a `requires:` inside it runs a ladder that applies the rule. The cost: a transient that outlasts the second look is refused too, and the call is retried (or the rung run deliberately with `run_flow`) — a retry is cheap, a wipe on an unread screen is not. This resolves the 2026-10-03 follow-up the detect probe carried since its read error stopped being swallowed.
- **…and a bare tree decides no condition** (since 2026-10-08, flow-engine review candidate 2). `flow/condition.ts` is the one module asked about a `Condition` — `evaluateCondition` (one condition against one tree), `describeCondition` (its name in the trace) and `conditionStateRefs` (the states it names, which `config.ts`'s existence and cycle checks read) — and its answer is three-valued: `yes`, `no`, or `unknown`, "this tree is BARE and cannot decide it". The leaf rule is `ui-tree/verdict.ts` (there, not in `flow/`, because the absent assert asks it too and `verify/` may not import `flow/`): a present element is `yes` when found whatever the tree holds, else `no` on a rendered tree and `unknown` on a bare one; an `absent: true` element is `no` when a match is visible whatever the tree holds, else `yes` on a rendered tree and `unknown` on a bare one — so a rendered tree never yields `unknown` and every screen an app has drawn answers exactly as before. `any:` and `all:` combine in Kleene's logic (any: `yes` if some arm is, else `unknown` if some arm is, else `no`; all: `no` if some arm is, else `unknown` if some arm is, else `yes`), stopping at the deciding arm in written order as before; `{ state: x }` is `x`'s detect with the same semantics. Each caller keeps its own policy, and none reads `unknown` as `yes`: the detect probe counts any round that is not `yes` on a bare tree as bare (its 2026-10-07 rule, unchanged), so the ladder's unread handling above — the second look, the never-wipes-blind refusal, "could not be checked" — now covers an absent detect too, and a BARE probe gets the second look (over `ensureTimeoutMs`) before ANY rung, not only a destructive one: with an absence undecided on the decor, `no_prompt: { detect: { id: prompt, absent: true }, reach: [dismiss] }` — "already active" there before — would otherwise run `dismiss` at once and fail on its tap of `later` once the decor outlasted `tapTimeoutMs`; now a rendered, detected screen ends the call, a rendered screen outside the state runs the rung on a tree that means something, and one still bare runs a cheap rung as before (a destructive one is refused). An `unknown` probe — every read failed — keeps running a cheap rung at once. The cost: a screen that is bare by the accepted miss (a map, a camera, an identified-only icon screen) delays a cheap rung by up to `ensureTimeoutMs` — and a whole ladder by up to N × `ensureTimeoutMs` for N rungs on a screen that never renders, before its ⛔ or its final wait's timeout, since each cheap rung may have relaunched the app and restarted the cold-launch clock, so each probe after it gets its own look (measured by the review: mp-native's three-rung ladder reaches ⛔ in about 60 s, where it took about 20 s before); `wait:` and `branch:` keep polling on `unknown` as on `no` — a `branch:` takes arm i only when every arm before it is `no`, so an earlier arm that is `unknown` holds the round undecided even when a later arm is `yes` on the same tree (an arm on the decor's own `content` is), since that earlier arm might win once the app renders and written order is the priority — and a timeout whose LAST tree was undecided says so beneath its headline (`the last UI tree read was bare, <shape> holding nothing of the app's (only wrappers, unlabeled decoration, or iOS's status bar and launch icon), so it could not decide this — the screen had not rendered by the deadline; compare with screenshot, and a longer timeout may be all it needs`, in place of the idb container-id hint; dropped, like that hint, when the last read failed); the `absent` assert keeps polling on a bare tree and fails as `could not verify within N s (the last UI tree read was bare, …)` with the same note, the wording an unreadable tree already had. Until then the evaluation was the engine's private `matches`, a boolean whose `absent` was `absentFromViewport` alone: nothing in a cold launch's decor or WDA's splash matches any selector, so a state detected by an absence was "already active" before the app had drawn anything, a `wait:` on it passed at once, a `branch:` arm on it was taken, and the absent assert PASSED — the bare rule lived only in the detect probe, and only for a tree that MISSED. The cost, the bare rule's known miss again: on a loaded screen whose only non-wrapper nodes are identified-but-unlabeled icons an absent condition can no longer pass (a wait or branch on it times out with the bare note, the assert fails as could-not-verify).
- **…and a loop through `requires:` fails its rung, never the call's chance to escalate** (since 2026-10-08). A reach rung's `requires:` leading back to the state being ensured is not a config error (only a `detect` cycle is — the mutual login/logout shape works from either state on the loop), so the engine refuses it at run time: a state re-entered while its own ensure is still on the stack, and not detected on that entry, throws a `ReentryError` naming the loop (`states.logged_in → flows.login → states.login_screen → flows.logout → states.logged_in`) where the call used to hang. It fails the rung whose `requires:` closed the loop and is deliberately NOT terminal: the ladder escalates to its next rung as for any failed rung, so a declared fallback (`reach: [login, hard_login]`) still runs and a destructive one still meets the never-wipes-blind check; with no rung left the call fails with that error. Each state is on the stack at most once, so it terminates, but the bound is the product of the loop's rung counts, not their sum (n states each with two rungs requiring the next: 2^(n+1)−3 reads, 253 at n = 6); no step runs in a re-entry subtree, so it costs reads only, never a tap. A state re-entered and detected by then answers "already active" as any ensure does — whose cost is the outer entry's stale read: the loop unwinds through rungs the app did not need, a spurious logout and login, or a wipe when the unwinding rung is destructive (identical on fb171ef). Right after `launch_app` this shape now fails fast with the unread cause ("none of this loop's states could be read on this probe (…)") where it used to ping-pong login/logout taps (7 taps measured on fb171ef) — retry once the screen renders, as with an `UnreadTreeRefusal`.
- **Failures carry their trace.** A flow that throws attaches the steps that already ran to the error message (`FlowError`). A bare "Timed out after 20000ms waiting for state logged_in" cannot tell you which reach flow ran, how far it got, or what it cost; the trace can, and it exists either way. The trace is the whole RUN's: a `verify` leg with a state and a flow is one run since 2026-10-07, so a failing flow carries the state's lines (and any wipe) before its own.
- **`branch` + `optional`** absorb the two realities of real apps: different login paths (fresh vs. returning) and random interstitials (rating prompts, promos, biometric sheets). An `optional:` step never fails the flow on what the screen did — a config refusal (an empty or undeclared credential, an unset `${VAR}`, a `type_pin` value with no digits: the engine's `isTerminal` set) fails it even inside `optional:` (since 2026-10-08), with the ✗ on the step that raised it, because skipping it would run on with the login half-typed; so does, since 2026-10-09, a tap (an optional tap, or any step's tap inside one — a `fill`'s focus tap) REFUSED on a present element — interact's `RefusedOnPresentElement` marker (resolve.ts): its centre off the screen (on iOS that includes under the status bar, an `OffScreenRefusal` although the centre lies inside a rect the reader sees on screen; its remedy offers `scroll_until` only where the tree shows a scroll view that can move it, and otherwise names it pinned under the bar — `tap-judgement.ts#systemBarRemedy`, code review of round 6, P1) or under a node drawn over it, or a soft keyboard over it with nothing sent and the target resolved on both looks (`KeyboardWithoutDismissal`, `KeyboardStateDisagreement`): `optional:` skips an absent element and the named failures skill/references/averi-yaml.md lists (a keyboard failure after averi acted, a target lost on the second look, a `scroll_until` that found its target but could not stop, and the rest listed there), never a refused tap nor a fill's value — this one is the interstitial itself (skipped, mp-native's `login_registered` rung ran on and the ladder escalated to the registering login). It fails as the engine's `OptionalNotSkipped`, ✗ `optional step not skipped: its element is present, but the tap was refused — <the refusal>`, and is in the `isTerminal` set: the ladder probes `detect` once (the rung may have reached the state before a trailing optional tap was refused — then the call passes), and otherwise stops — it does not escalate past a present-but-refused element, even though a later rung might have cleared the screen, and does not salvage it. That is the owner's decision (2026-10-09). The same refusal OUTSIDE `optional:` is the step's plain failure and escalates as before. By the same decision (2026-10-09, later) a `fill` that failed on its VALUE is an `OptionalNotSkipped` too, marked `interact/fill.ts#FillValueFailure`: `did-not-land` — the three `FillFailure`s (a read-back mismatch, a clear that left text twice, a re-read that failed after the focus tap; the last is the one dead-device case not skipped — an exception kept on purpose, the owner's decision on code review of round 6b P3: a dead device or adb error during an optional fill's read-back fails the flow; elsewhere it is skipped) — ✗ `optional step not skipped: its field is present, but its value did not land — …`, and `refused` — a control character, before anything is sent — ✗ `optional step not skipped: averi refused its value before anything was typed — …`. Not marked, and still skipped: a device error from the fill's `typeText`/`clearText` (the known gap: a fill whose typing command the device refused may leave partial text), an `AmbiguityRefusal` from a mid-fill re-read, and the `type:` step's own control-character refusal. A keyboard failure after a `back` or a dismissal tap (`AfterKeyboardDismissal`, `AfterDismissalTap`), or one whose second look lost the target, is still skipped (resolve.ts#RefusedOnPresentElement says why); so is an optional `scroll_until` that found its target but could not stop on it (clipped, covered, under the status bar) — deliberately: only a refused TAP (a `tap:`, or a `fill`'s focus tap) on a present element, or a `fill`'s value, is terminal (code review of round 6, P3); otherwise its trace line says why it was skipped — `(not present)` only when the interaction module reports the element was never found on a screen it could read (`ElementNotFoundError`, since 2026-10-08 — an optional tap's presence check, a nested fill's or tap's settle wait, a `scroll_until` that never matched; an optional tap the presence check DID sight quotes its tap's own timeout if the element then leaves, since a failure after finding is never absence), otherwise the failure's own headline (a keyboard that would not hide, a `wait:`/`branch:` that timed out — never an off-screen or covered target since 2026-10-09), with the read-error line joined on when the last tree read failed, so a dead device never reads as an absent interstitial. Until that date the engine guessed, and a found field whose fill failed read `(not present)`.
- **Secrets** are referenced (`$name` → `credentials:` → `${VAR}`, from the environment or `.env.averi`), never stored. Keychain URIs are not implemented (§10). Server redacts them from logs and from anything echoed back to the agent — the agent never sees the actual PIN, it just calls the flow.
- Platform overrides per step where needed: `ios: { tap: {...} }`.
- Same file doubles as documentation of the app's navigation for humans.

### Which tools read averi.yaml

Declared once per tool, in `mcp/config-policy.ts#TOOL_CONFIG`, and carried out by `flow/tool-config.ts#loadForCall` — at most one read of averi.yaml (and of `.env.averi`, where marked) per call, handed down as a value. Since 2026-10-08; until then each handler picked one of four loaders, an iOS `assert` read the file twice under two policies, and `assert` on Android and `launch_app` swallowed a broken file in a catch-all.

| Tool | Android | iOS | `.env.averi` |
|---|---|---|---|
| `install_app` | required — only without `path` (\*) | required — only without `path` (\*) | no |
| `launch_app` | optional — only with neither `activity` nor `intent` (the `app.android.activity` fallback) | none | no |
| `ui_snapshot`, `tap`, `type_text`, `scroll_until` | none | optional (tree source; dismissals for `tap`/`type_text`) | no |
| `swipe` | none | optional — only with `direction` (tree source); coordinates read nothing | no |
| `assert` | optional (health line) | optional (tree source, health line) | no |
| `ensure_state`, `run_flow`, `verify` | required | required | yes |
| every other tool | none | none | no |

(\*) The table entry is plain `required` and does not look at `path`, by design: the handler's `path ?? appBuildPath(…)` short-circuits before the read, so a call with a path reads nothing, and the entry keeps `cfg` typed non-optional where `appBuildPath` needs it. `launch_app` and `swipe` are the entries that take the call's arguments.

- **none** — the file is not read; a broken one beside the call is not its business, because the call uses no value from it.
- **optional** — a MISSING file is no config and the call proceeds on the defaults (no health line, the idb tree source, no dismissals, the launcher's activity).
- **required** — a missing file fails the call.
- Under **optional** and **required** alike, a present-but-INVALID file fails the call, naming the file, before any device is bound. Android and iOS differ only where the tool uses different values on them — never in how a broken file is judged. Two calls that passed before 2026-10-08 now fail on a broken averi.yaml: an Android `assert` (it silently lost the health line) and an Android `launch_app` naming neither activity nor intent (it silently lost `app.android.activity` — the LeakCanary case its description warns about); the same two calls also stop passing over a read error other than a missing file (a directory at the path: EISDIR). A health check that throws outside `appHealth`'s own guard still only omits `assert`'s health line, as before: the guard around it was narrowed to the health check alone, not removed.

Verification philosophy: three tiers, cheapest first — (1) AX-tree asserts (fast, deterministic), (2) screenshot to the agent's own vision (semantic judgment), (3) pixel-diff vs. stored baseline (regression). The tool provides all three; the skill teaches when to use which.

## 8. Reliability details that make or break this

- **Waits, not sleeps**: every action polls the AX tree for the expected postcondition (configurable timeout); screen-stability heuristic (two identical consecutive screenshots, up to 5 re-captures 300 ms apart) before any frame is measured or returned (the one exception, by design: `scroll_until`'s eyes measure a single capture taken after the stop's settled tree reads — `verify/eyes.ts`, ADR 0013; a bar or IME still animating then could be misread, the stated residual) — owned by `verify/capture.ts`, applied by the `screenshot` and `ensure_state` tools, the color, ocr and screenshot-baseline asserts, and the final frame of every `verify` leg, so a mid-animation frame is never the verdict (the legs took a bare screenshot until 2026-10-02, the screenshot-baseline assert until 2026-10-04 — that assert now pays the stability budget documented on `capture.ts`'s `STABILITY_*` constants where it took one capture). Since 2026-10-05 that budget has ONE owner and the frame SAYS whether it settled: `pollMs` is a poll interval and nothing else — until then the Verifier forwarded it to the capture as the delay between stability captures, so an assert inside a flow (engine default 500) waited 500 ms where the MCP `assert` tool waited 300, and "the same budget for every consumer" was false in production; `Frame.stability` (settled / moving / unjudged — decided once in capture.ts, never re-derived from the count) and `Frame.captures` report the wait's outcome; the color and ocr asserts treat a moving frame as a miss (the deadline, not a moving frame, decides, and the timeout says the frame never settled), the screenshot-baseline assert refuses to CREATE from one (it used to store the last of six differing frames as the ground truth) and still diffs against an existing baseline with a `⚠ frame:` note on the result, and the `verify` legs and the `screenshot`/`ensure_state` tools return the best frame with that note. An OTP is a credential like any other (`$name` → `${VAR}`) typed with `type_pin` or `type`.
- **Determinism aids**: `clearState` per launch (`launch { clearState: true }`, `launch_app`'s `clearState`). NOT IMPLEMENTED: `simctl status_bar override` / adb demo mode for clean screenshots, and fixed locale/timezone options — screenshots carry the device's own status bar, locale and clock.
- **Crash detection**: a SUCCESSFUL `ensure_state` or `run_flow`, every `assert` call that returns (failing asserts included), and each `verify` leg that completes ends with `appAlive: true | false | unknown` (`run/verify.ts#appHealth`) when averi.yaml names the app for the platform — `false` with a crash excerpt from the last 60 s of logs, `unknown` when the device could not be ASKED (adb/simctl timeout under load, device offline), which is deliberately not `false` (2026-09-18). A failed run has no health line: a failing flow throws its step trace (`FlowError`), a failed `verify` leg is a `FAILED:` section, and neither attaches logs — after a failure, `get_logs` (grep for the crash) and `screenshot` are the scan.
- **A differential harness replays recorded trees through two checkouts** (`scripts/differential/`, its README): every tree a device check saved, run through OLD's and NEW's MCP tool handlers with the same arguments, and every call whose reply or device calls differ reported. It sits at the tree-source seam, not inside the tree logic: a RAW payload (WDA `/source`, idb `describe-all`, a `uiautomator` dump) is read by the side's own parser — WDA through a recorded `IosTreeSource` that the harness hands `IosAdapter` (it takes the side's `parseWdaSourceValue`; no `IosTreeSourceKind` names it, so no averi.yaml can select it), idb and Android through the side's own adapters, whose `idb`/`adb` commands a fake device at the process boundary answers — while a NORMALIZED `ui_snapshot` tree is served as it is and the run says the parser was not exercised on it. Time is virtual (the one sleep owner, `util/sleep.ts`). The corpus of device trees stays outside the repository; its own tests run on a few `tests/fixtures` trees. A device check should save the raw payload next to each tree it reads (the README says how), so a parser change is visible to the next run.

## 10. Risks

- **Compose/SwiftUI semantics gaps** → AX tree may be sparse; mitigation: coordinate taps (`tap` x/y, `swipe` coordinates), `app.ios.treeSource: wda` for the React Native / SwiftUI container ids idb drops (§3), `text`/`label`/`role` selectors, and `ocr` asserts for copy the tree does not carry. Not built: a lint tool that reports missing `testTag`/`accessibilityIdentifier` (it would also be a selling point: it pushes teams toward accessible apps).
- **idb maintenance risk** (Meta's investment fluctuates) → the tree read sits behind the `IosTreeSource` seam with two adapters, idb and WDA (§3). Exercised 2026-08-12 behind a flag; a seam since 2026-10-02 — changing the default tree backend is one constant, `DEFAULT_IOS_TREE_SOURCE` in `adapters/ios-node.ts`, not an edit to `IosAdapter` or the registry. Input (`idb ui tap/swipe/text`) is NOT behind it: a full idb exit still needs a WDA input path, which drags in session management (plan, decision 4).
- **Overlap with mobile-mcp** → averi's value over raw taps is the flow-descriptor layer, cross-platform parity, and the maintained skill.
- **Secrets in a banking context** → local-only processing and redaction of credential values from traces and errors are in place; keychain integration, planned for v1, did not ship in 0.9.0 and is still open — credentials come from the environment or a gitignored `.env.averi`.
