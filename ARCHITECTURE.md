# Agent Mobile Verify — Architecture & Design Doc

*A free MCP server that lets coding agents verify their work on iOS Simulators and Android Emulators, including apps that require a login step.*

Working name: **`averi`** (Agent VERIfier). Rename freely.

---

## 1. Problem & positioning

Coding agents (Claude Code, Cursor, etc.) can now write native mobile code, but they can't close the loop: build → install → **get past login** → navigate → verify. Generic tools exist, but none of them solve the *stateful app* problem:

| Tool | Strength | Gap for us |
|---|---|---|
| [mobile-mcp](https://github.com/mobile-next/mobile-mcp) | Generic taps/screenshots via accessibility tree, iOS+Android | No app knowledge: agent must rediscover login every session |
| [Maestro MCP](https://docs.maestro.dev/get-started/maestro-mcp) | Agent writes/repairs Maestro YAML tests | Oriented at producing test suites, heavy dependency; login state still the agent's problem each run |
| Appium | Mature drivers | Per-project setup, slow, overkill for "verify my change" |

**Differentiator:** the tool is *app-aware*. Teams check an `averi.yaml` descriptor into the repo that declares how to reach known states (logged-in, specific screens). The agent calls one high-level tool — `ensure_state("logged_in")` — instead of fumbling through a PIN keyboard with 15 tap calls. That determinism + cross-platform parity + verification helpers is the product.

## 2. High-level architecture

Clean separation of concerns:

- **Device Adapter** (`adapters/`) — the only layer that knows platform commands. One interface, two implementations. Everything above is platform-agnostic. `adapters/types.ts` also holds `everyNode`, the ONE pre-order tree walk (since 2026-10-06; it was in `field-errors.ts`, a pairing module two unrelated callers imported from): field-error pairing, `verify/text-hint.ts`'s `flattenTree` and `ui-tree/bare-tree.ts` all walk with it.
- **UI tree** (`ui-tree/`) — the normalized tree and everything asked OF it: selector resolution, `ElementSpec`, screen width, per-id rects, tap points, the viewport predicates (`geometry.ts`: intersects / absent / visible fraction / clipped edges). Knows no platform commands and no averi.yaml. Since 2026-10-04 the structured `ElementSpec` lookup is the selector grammar's own matcher over `conditionsOf(spec)` (exact match, `text` = label or value), not a second hand-written one — proved by a frozen-oracle differential (deleted 2026-10-05, once trusted); the test now checks the definition and the grammar's results; the viewport predicates moved from `selectors.ts` to `geometry.ts` where the rest of the rect arithmetic is (since 2026-10-07 the point-in-rect test `containsPoint` and the draw-order question `shadowing` — which later content node is drawn over a point — are there too, moved out of `interact/keyboard.ts` by the review of the stage B branch; `STRUCTURAL_ROLES`, which `shadowing` reads to skip wrappers, moved the same day from `bare-tree.ts` to `adapters/types.ts` beside `KEYBOARD_ROLE`, so neither ui-tree module imports the other for it); and the "text is on screen but combined into one a11y element" hint, whose advice is assert vocabulary (`match:`), moved to `verify/text-hint.ts`. Since 2026-10-08 `verdict.ts` is the leaf rule every element condition and the absent assert share — present/absent against one tree as `yes` / `no` / `unknown`, `unknown` only on a bare tree (§4, "…and a bare tree decides no condition") — and `bareTimeoutNote`, the one note their timeouts quote, its advice included; `read-tree.ts#pollOnVerdict` is the one mapping of a verdict onto a poll round (`yes` the value, `no` a miss, `unknown` `Undecided`). Since 2026-10-06 `bare-tree.ts` answers "does this tree hold anything a user could read or act on?" for `ui_snapshot`'s second text block (docs/bugs/2026-10-06-ui-snapshot-empty-right-after-launch.md: `[]` on a rendered PIN screen, and the idb tree a 0×0 Application for minutes) and, since 2026-10-07, for the flow engine's detect probe, which answers `bare` rather than "no" when every tree it read was bare (§ "…and it never wipes blind" below); `treeShape` (`7 nodes (roles: container ×6, image ×1)`, its count from `nodeCount`, which `ui_snapshot`'s note shares) names such a tree in both — it and the role summary under it moved 2026-10-07 from `mcp/tool-text.ts`, which the flow engine may not import: a heuristic by role and size — any non-structural role counts, `image`/`progress` only when labelled (an identified, unlabeled image is the measured RN splash logo), `container`/`other` only with a label or value AND under 90 % of the tree's largest rect (`SCREEN_SIZED_FRACTION`), nothing structural in a tree with no geometry at all. Also accepted: a loaded screen whose only non-wrapper nodes are identified-but-unlabeled icons (icon-only controls without an accessibility label) is called bare — rare; in `ui_snapshot` a wrong ⚠ only sends the agent to a screenshot, but since the ladder asks too it costs a refusal: such a screen cannot reach a DESTRUCTIVE rung through `ensure_state` (refused, never wiped; `run_flow` of the rung still runs it). Accepted costs, written on the function: a labelled full-screen RN root alone reads as bare (the wrong direction — that shape cannot be checked from the tree anyway, and the note says to compare with a screenshot), a small labelled overlay during load reads as content (the safe one for a presence check — but since 2026-10-08 the unsafe one for `absent:`: a labelled loading overlay makes the tree decide, so an absence can pass before the screen exists; measured on the iOS dev-client build, whose expo "Downloading 100%…" banner over the splash let an absent-`login_username` wait pass ~1.6 s after a cold launch in 3 of 5 launches — a development-build artefact, no release build shows it, and a release splash stays bare). `rectArea` is its one piece of arithmetic — defined beside `Rect` in `adapters/types.ts` since 2026-10-06 (the idb source's empty-tree check needs it and may not import upward) and re-exported by `geometry.ts`. Since 2026-10-07 `soft-keyboard.ts` answers "what does this tree say about the soft keyboard?": `keyboardInTree` gives a `SoftKeyboard` — `shown` with the band of the first `KEYBOARD_ROLE` node (the role `adapters/types.ts` defines and the WDA source writes, §3), else `unknown` (never `hidden`: an idb tree carries no band whatever the screen shows, and the tree cannot say which source it came from); `partOfKeyboard` says whether a node is the keyboard's own UI (it or an ancestor carries `UiNode.ofKeyboard`, the mark the WDA source puts on the keyboard-side Windows — a key, the toolbar's Done, the Passwords bar are never "under" the keyboard); and `readSoftKeyboard(adapter, tree, subject)` is THE one switch between the two models for READING the keyboard for a subject (the pixel poll's round and the guard's every look; the ACTING half's one switch over the same fact is `interact/keyboard.ts#keyboardModel`, §8 — one per half because `verify/` may not import `interact/`; the post-fill dismissal has no subject and each model's `dismiss` reads its own source, the oracle's `state()` or the tree's band) — the adapter's oracle `state()` when it has one, else the tree, `unknown` for a keyboard-side subject, with the `KeyboardRemedy` riding along — `dismissal: DismissalMeans` (`'back' | 'none'`: what the ADAPTER has to hide a keyboard with, a capability fixed per adapter; `interact/keyboard-window.ts#dismissal`'s `'back' | 'nothing'` is the other question, what one post-fill call DECIDES, and keeps its own literals) and the adapter's `keyboardAdvice` — so the tap guard and the pixel poll read one reading off the tree they already hold, with the same geometry as the Android oracle's answer, and neither spells the switch itself. Like `read-tree.ts#pollTree`, it takes the adapter and calls its interface, never a platform command.
- **Flow Engine** (`flow/`) — interprets `averi.yaml` descriptors (login, navigation recipes), maintains a state model of "where the app is". Its `tap:`/`fill:`/`scroll_until:`/`swipe:` steps are one-line callers of the interaction module; it converts the YAML vocabulary (`timeout: 2s`) before calling and owns the trace wording. Three modules since 2026-10-04 (five now — `flow/tool-config.ts` below, and since 2026-10-08 `flow/condition.ts`, everything asked of a `Condition`: its three-valued evaluation against one tree, its trace name and the states it names, § "…and a bare tree decides no condition"): `flow/config.ts` is the schema, the types and the pure walks over them (reference validation — names that exist, and since 2026-10-08 no cycle among states' `detect`s, through any depth of `any:`/`all:`: such a cycle never finished at run time (a stack overflow, or a microtask loop until the heap was gone) and is now `Invalid averi.yaml` naming the whole path, `states.a → states.b → states.a` — the container and destructive-flow rules, the launch-activity rule — parsing a payload loads no I/O); `flow/load.ts` is everything that touches the file system (which averi.yaml, where its build paths point, what the sibling `.env.averi` contributes) and returns `{ cfg, env }`; `flow/credentials.ts` turns config + env + the requested environment name into frozen credentials with the lazy `$name`/`${VAR}` expansion — and, since 2026-10-08, owns "a secret is never empty" whichever path made it: an unset or empty `${VAR}` and a credential declared as `""` are refused at the step that uses them (the adapters type "" as a no-op, so either used to pass as `***` and be rejected a screen later), while a plain `""` step value — a clear — is no secret and passes; `type_pin` refuses the PIN-specific half, a value with no digits, before its first key. Since 2026-10-08 a fourth, `flow/tool-config.ts`, is the config policy of the MCP tools: the policy vocabulary (none / optional / required, `.env.averi` or not), `loadForCall`, the one read a policy drives — at most once per call, handed down as a value — and `iosToolSettings` over what was read. Which tool gets which policy (§5, "Which tools read averi.yaml") is keyed by MCP tool names, so that mapping is the MCP layer's (`mcp/config-policy.ts#TOOL_CONFIG`). Until that date credential values travelled through `process.env`: the loader wrote `.env.averi` into it (with module-level state to refresh what it had written), the resolver read `AVERI_ENV` out of it and the engine read every `${VAR}` out of it at step time — three modules on one hidden global, and `FlowEngine`'s interface silently included "construct me only after `loadProjectConfig`". Now, under `flow/`, `process.env` is read in one function (`loadProjectConfig`) and written nowhere in `src/` (the adapters still read it for the toolchain — `xcode-env.ts`'s `DEVELOPER_DIR`, and the child-process environment `exec.ts` and `wda.ts` hand to adb, xcrun and xcodebuild); `EngineOptions.env` is required, so the ordering is a parameter. Because the file is no longer written into the process environment it no longer reaches child processes either: adb, xcrun and xcodebuild used to inherit the credentials; now they inherit the shell's environment only — and a name removed from `.env.averi` is gone on the next load (a removed `AVERI_ENV` used to keep running the old backend for the server's life), and one project's values no longer leak into another project loaded by the same server. The same day `stepsAreDestructive`'s safe-leaf list became a `satisfies` over every non-container, non-launch kind of `Step`: a new step kind missing from it fails `tsc` instead of silently costing a skipped recovery. Since 2026-10-07 one tool call is one engine run: `FlowEngine` has a single entry, the static `FlowEngine.run(cfg, adapter, opts, { state?, flow? })` — the state ensured first, then the flow; the request type needs at least one — which builds a fresh engine for the call and owns one trace, one environment line, one `FlowError` guard and one recovery budget. The constructor is private, so nothing outside can keep an engine and run it twice: the rule is the shape. Until then there were two entries, `ensureState` and `runFlow`, each of which reset the trace and the recovery budget and logged the environment, under an unwritten "one instance, one entry" rule that `verify` broke by calling both: a flow failing after its state was ensured threw a `FlowError` holding the flow's steps only, so the leg's FAILED section lost the `state … already active` line (and, after a ladder, the `⚠ clearState` wipe the call had paid for), the environment line printed twice, and "one recovery pass per call" held twice. The same day the `⚠ clearState` line's "N this session" count stopped being a module global with a test-only reset: it lives on an `EngineSession` the caller hands in (`EngineOptions.session`, as `env` is), and the MCP server makes one per server and passes it to every tool that runs the engine (both `verify` legs share it) — so a second server in one process starts at 1. It is required at every layer — `EngineOptions.session` and the run layer's requests, which share it with `environment` as one `EngineContext` — because an optional one, forgotten, would silently reset the count per call; the session counts through `recordClearState()`, never a field the engine bumps. The MCP layer gets the class from `run/commands.ts`, its documented delegate, not from `flow/`. When a second ladder in the run (a flow's `requires:` after the state) misses with the recovery pass already spent, the trace says so: `↻ no recovery <state>: … the run's one recovery pass was already spent on <state>`.
- **Interaction** (`interact/`) — since 2026-10-03, what it takes to ACT on an element, written once for the flow engine's steps and the MCP tools: ONE resolution policy (`resolve.ts`: zero-area nodes are never targets, a sole interactive match wins among several with a note, an optional rect-stable wait with a plain-ms budget, and a one-shot mode for the fill's value poller; since 2026-10-08 the wait says which way it failed — `ElementNotFoundError`, "…to appear", only when no round resolved the target and the last read succeeded (`scroll_until`'s "element never appeared in the tree" likewise), a plain Error "…to hold still (found, but …)" when it was found but never settled — and `resolvePresent` is the appear-only check the flow's optional tap budgets, so the one fact "was the element there" has one owner and the engine's `optional:` reads it instead of deducing it), tap, fill (focus delay, verified typing, the masked-value length rule; the post-fill keyboard dismissal is `keyboard.ts`'s), the soft-keyboard guard every tap on a resolved node goes through (`keyboard.ts`, same day; §8 — since 2026-10-07 the guard and the dismissal are one skeleton over the model seam `keyboard-model.ts`, with the window model in `keyboard-window.ts` and the in-tree model in `keyboard-in-tree.ts`, chosen once from whether the adapter has the keyboard oracle), scroll-until-visible with its clipped report, and the swipe vectors with the finger-vs-content meaning spelled out. Plain-ms options, no config or MCP type. The `ambiguous` mode is required on every resolution — the engine picks first (`FLOW_AMBIGUITY`), the MCP tap/type_text tools refuse with the candidate list — so the one place a policy could silently loosen is a type error. Before it, the engine held these as private methods and exported free functions, `ui-tree/tap-element.ts` held the tap, and the MCP tap/type_text tools used a second resolution policy (`resolveOne`: no zero-area filter, no wait, throw on ambiguity) for the same user operation.
- **Verification Engine** (`verify/`) — asserts, the layout contract, rect/color/text parity, OCR, screenshot diffing. `verify/capture.ts` is the one owner of three facts every pixel reading rests on: that the frame is SETTLED (two identical consecutive captures, one budget for the `screenshot` and `ensure_state` tools, the color, ocr and — since 2026-10-04 — screenshot-baseline asserts, and each `verify` leg); the png scale — derived once per frame, from the device screen first, and carried as one value with one failure wording to the color and text comparators, which keep their own fallback policy (color fails closed, text drops to the tree with a note); since 2026-10-07 the rect denominator too — `verify/scale.ts` is the ONE owner of trusting a screen width and answers two questions with the same tree-side refusals (those of the tree-only png scale — with a device screen `pngScale` scales by the device and only notes a content-width tree, where `windowWidth` refuses it, because there the tree's width is the denominator): `pngScale` and `windowWidth`, the window's width for the rect table and the `rect` assert (still the TREE's window — docs/bugs/2026-08-26-png-scale-needs-out-of-tree-screen-size.md's decision stands — with the device screen only witnessing it: a 0-wide tree and a CONTENT width are refused in the png scale's own words — an Android letterboxed or freeform window among them, with an Android remedy beside the iOS one — a window wider than the screen side it faces is refused (the side picked by the window rect's own aspect; a walked width, which has no orientation, is bounded by the longer side; before that refusal the screen is re-read once, bypassing the adapter's memo — `capture.ts#ScreenWitness`, through `viewport({ fresh: true })` — so a screen changed since the memoized read, e.g. an unfold or `wm size`, is judged as it is now instead of refusing until the server restarts, and a surviving refusal says what the re-read found), one agreeing with either side is measured silently, a narrower one with a note, an unwitnessed one says so; an Android landscape window laid out beside a side nav bar or a display cutout (`DeviceScreen.windowsBesideSystemBars`, Android only; landscape-shaped, the full short side tall, each gap to the screen edge at most 10 % of the long side — `scale.ts#besideSystemBars`) is measured — one that starts inset at its own width with `left` carried so every `x` is measured from it, one short of the long side silently rather than as "split view?" — while an iOS inset rect stays a content width; device reads go through `capture.ts#witnessScreen`, the one place a failed read degrades to "no witness", and `viewport()` keeps a success but no longer a failed read). The tree is walked once per frame (`inferScreenSize`), and that one size feeds the scale, the window and the region check's per-pair scale. Each tree-bearing frame carries it as `window`, derived beside the scale and BEFORE the png decode (the rect table runs on an undecoded frame), the table reads it off the frame and fails WHOLE on a refusal, and the `rect` assert asks it per round against the adapter's memoized `viewport()` (re-read fresh at most once per assert, as above) and fails through `failClosed`. Until then both read `ui-tree/geometry.ts` directly and kept its `reliable` flag as a remark — the table printed "every delta below is scaled wrong" above a WITHIN TOLERANCE verdict and the assert passed with "(UNRELIABLE …)" while `pngScale` refused the same width (the 2026-10-07 parity review, P1; reproduced as a -4.2 % `w` defect that read +0.06 %). The scale's plausibility note ([0.5, 4], formerly color-parity.ts's `SCALE_SANE_*`) moved onto `pngScale`'s own note the same day; the device-unverified limits of the witness rule are on `windowWidth`. And the rect→png crop, one mapping with the clipped fraction beside it (the inset is the color sampler's option). Before 2026-10-02 the wait had two owners, the legs took a bare screenshot, and the scale was derived at four call sites; the screenshot-baseline assert was the one pixel reading that change missed — it took a bare screenshot until 2026-10-04, so the baseline it wrote and the frame it diffed could both be mid-animation (re-baseline any screenshot assert that was flaky under it). The pure tail of the capture — tree + png + device screen → the one measured frame — is exported as `measuredFrameFor`, and the comparator tests build their fixtures through it rather than re-spelling the scale derivation, so a change to what the capture feeds the scale cannot leave those tests green against stale fixtures. Each parity comparator's inputs are measured below the run layer — rect reads the tree and the frame's `window`, color the frame `capture.ts` measured, and text, since 2026-10-04, its own leg measurement: `verify/text-parity.ts#textMeasurement` decides the recognizer once per run and owns BOTH halves of the table's policy on an absent one — the one caveat the section prints, and the per-leg `measure` that then stands on tree evidence without a note of its own (since 2026-10-05 one value; until then a `textRecognizer` produced the caveat and `measureTextLeg` took the engine as a bare argument, returning tree-only silently and trusting the caller to have printed it). `measure` recognizes one leg's text anchors on that leg's own bytes and hands back the capture with its caveats — the png width travelling WITH the OCR results it normalizes (`TextOcr`), so a capture cannot carry one without the other — and `verify/ocr.ts#ocrEngineFor` is the one rule deciding whether a recognizer exists here, quoted by both the `ocr` assert and the text table. Since 2026-10-08 a `verify` run asks it ONCE (`run/verify.ts`, review 2026-10-07 assert-capture-ocr C1) and hands that one choice to the text table and to every leg's Verifier (`VerifierOptions.ocr`): until then only the table got the run's engine, so a run-level fake never reached the `ocr` asserts and a two-platform run built up to three `VisionOcr`s, each probing `swiftc --version` before its binary cache; a flow's own `assert:` steps still build their Verifier in the engine. The same day the `ocr` assert's measurement moved beside the verdict as `verify/text-parity.ts#measureOcrAssert` (C2) — crop → recognize → the region's error → `evaluateOcrAssert` — the shape `color-parity.ts#evaluateColorAssert` has for colour, and every "not read" in it ends with `failClosed` (a region error used to come back raw, a recognizer throw as a bare `OCR failed: …`, and two sentences hand-wrote "failing closed"); a recognizer throw is a miss the poll reads past, except an `OcrUnavailableError` (no Vision, no `swiftc`, a recognizer that did not compile — `VisionOcr` memoizes its build, failures included), which comes back as a verdict marked `final` (`poll-verdict.ts#PollVerdict`) that the pixel poll — the one place that turns it into control flow — ends the assert on at once, the exit a refused capture takes (a `swiftc --version` probe that timed out or hit EAGAIN is a plain error the engine forgets, so the next read probes again); a throw from the measurement's own code propagates rather than being worded as an OCR failure. The colour table and the colour assert sample through one `color-parity.ts#sampleFill` since that day too (parity review 2026-10-07 P3), each wording an absent sample its own way. Until 2026-10-04 that measurement phase sat in `run/verify.ts` as a 50-line `runOcr` (the one measurement the run layer did itself, so it had to know OCR is keyed by anchor id and that the width is the ink normalizer, which the type did not enforce), and the engine-selection rule was written twice.
- **Orchestration** (`run/`) — composes the two engines into one `verify` run: per-platform legs, error containment, the parity tables. It is its own layer precisely because it needs BOTH engines and neither may depend on the other. Since 2026-10-03 `run/commands.ts` holds the single-platform tool compositions beside it — what one `ensure_state`, `run_flow` or `assert` call does (ONE engine run — `{ state }` or `{ flow }`, the same `FlowEngine.run` a `verify` leg calls with both — trace, health line, settled frame) — each taking a resolved adapter or an adapter-resolving callback, never the registry, and since 2026-10-08 the config its handler already read, never a path to read again (the launch-activity lookup that lived here was deleted that day: with the read moved up it was `resolveLaunchActivity(cfg, call)` under another name); and `runVerification` reads, parses and validates the layout contract itself from the path, before it resolves any adapter. Since 2026-10-05 an `environment` averi.yaml does not declare gets the same pre-flight (`run/preflight.ts#refuseUnknownEnvironment`, called by `runVerification` and by the shared ensure_state/run_flow sequence): refused before any adapter is resolved, where the engine's constructor used to find it per leg after `resolveAdapter`; and the first trace line's overridden credential names come from `Credentials.overriddenNames`, so the engine no longer re-derives the layering from `cfg.environments`. Since 2026-10-04 the three parity tables are produced the same way — one `paritySection` call each — and since 2026-10-05 the fact table (`DIMENSIONS`) holds only the facts asked at two moments and that must agree between them (title, whether this contract produces the table, its validator — since 2026-10-08 three: the comparator's options left the record when the rect and text comparators lost their test-only tolerance overrides, which production never passed, and the colour table's one real option, the theme, is the single `COLOR_OPTIONS` handed to its validator and its comparator; every tolerance is read from the contract, the one way in for tests too); what one leg contributes (a one-line collector — the tree, the measured frame, or the text capture via `textMeasurement(...).measure`), what the section says when no leg could, and what the run decided before any leg (the text table's one OCR-unavailable caveat) are handed to `paritySection` at the call that builds the table. For one day those hooks sat in the record too, with a run-context object only the text collector read; they had one or two users each, so they went back to the call sites — comparing and formatting stay hand-written per dimension, and the record is a fact table again, not a reporting framework. A collector that throws costs its leg a note, never the run; per-leg notes print in platform order after the run-level ones (before 2026-10-04 the text table's OCR notes came first, in completion order). Every table starts from the leg's frame narrowed to one that carries a tree — `verify/capture.ts#TreeFrame`, derived from the frame type so `stability` and whatever the frame says next reach the tables without an edit.
- **MCP layer** (`mcp/`) — thin: tool schemas, descriptions, and one-line delegations. No logic. What a handler holds, as of 2026-10-03: its zod schema (including parsing the assert specs), its description, resolving the platform to an adapter through the registry (this layer's own state), one delegation — to an adapter method, `interact/`, `run/commands.ts` or `run/verify.ts`, with `flow/` answering the config questions (which build, which iOS tree source, which activity, where averi.yaml is) — and the response, worded by `mcp/tool-text.ts` or the callee. Since 2026-10-08 a handler that reads averi.yaml does it in one line, first, `loadForCall(TOOL_CONFIG.<tool>(…), configPath)` — the policy looked up in `mcp/config-policy.ts`, the read done by `flow/tool-config.ts` — and hands the result down. The `verify` handler is the widest: it loads the config, parses the specs and delegates. Until that date the handlers also wrote out the ensure_state/run_flow sequence, the assert health line, the contract file read and the install/launch config lookups. Since 2026-10-03 tool registration is a side-effect-free module (`mcp/tools.ts`: `createAveriServer({ registry, version })` builds the server and connects nothing), tested through the SDK's in-memory transport with a real client over a fake-adapter registry (`tests/mcp/tools.test.ts`); `mcp/server.ts` is the stdio entry only — real registry, shutdown handlers, connect — and is tested as a spawned process (`tests/mcp/server.test.ts`: version, tool count, exit 0 on SIGTERM). Before that the registrations sat beside a top-level `await server.connect(stdio)`, so no handler could be imported by a test. A number a description quotes as a default — the settle budget, the assert budgets, scroll_until's swipe and time bounds, ensure_state's second look, get_logs' line budget, verify's contract tolerances (`DEFAULT_TOLERANCE_DE`, `CONTRACT_TOL_FACTOR`, `DEFAULT_SIZE_TOLERANCE_PCT`, derived since they were added) — is built from the constant that owns it (`DEFAULT_SETTLE_TIMEOUT_MS`, `ASSERT_TIMEOUT_MS`/`PIXEL_ASSERT_TIMEOUT_MS`, `DEFAULT_MAX_SWIPES`/`DEFAULT_SCROLL_TIMEOUT_MS`, `DEFAULT_ENSURE_TIMEOUT_MS`, `run/verify.ts#LOG_MAX_LINES` — also `formatLogExcerpt`'s own default, which until then was 2000 against the tool's 400 — the times through `util/duration.ts#formatSeconds`), never restated as a literal, and `tests/mcp/tool-descriptions.test.ts` pins each description against its constant (2026-10-08; until then half were literals — "3 s" in three places — that a changed default would have left stale). The prose docs (this file, SETUP.md, skill/SKILL.md) still quote the numbers.

**The rule that keeps this honest: dependencies point one way only** — `mcp → run → flow → interact → verify → ui-tree → adapters`, with `util/` a leaf. (`interact/` imports `ui-tree`, `adapters` and `util` only; it sits above `verify` in the order because `verify` must stay reachable from both engines without knowing how an element is acted on — the absent-in-viewport rule both need lives in `ui-tree/geometry.ts` for that reason.) Nothing below a layer may import from above it. That is checkable in one command, and it is what makes each layer independently testable:

```sh
grep -rn "from '\.\./" src | sed "s|:.*from '\.\./|  ->  |"
```

The rule earned its keep: the platform layer once imported the selector layer (for a `tapElement` that contained no platform code), and `flow/config.ts` had become the de-facto home of vocabulary — `ElementSpec`, `ElementAssert`, `parseDuration` — that neither flow nor config owns. Both inversions were invisible until the arrows were drawn.

Runs entirely locally on the dev machine (device access requires it); nothing talks to the cloud.

## 3. Device Adapter layer (raw adb + simctl/idb)

One interface, e.g.:

```
interface DeviceAdapter {           // bound to ONE device: the constructor requires the serial / UDID
    install(appPath): void          // reinstall triggers login requirement
    launch(bundleId, clearState?): void
    terminate(bundleId): void
    screenshot(): Png
    uiTree(opts?: {settle?}): UiNode // normalized accessibility tree; `settle` = one-shot caller may wait out a "no window yet" transient (Android only; iOS ignores it)
    tap(x, y): void
    longPress, swipe(direction|coords), typeText, pressKey(back/home/enter)
    keyboard?: KeyboardOracle       // OPTIONAL capability (since 2026-10-04): present where the keyboard is a separate window `back` hides — Android; absent on iOS, where it is part of the tree. Presence asserts the window model (hide key `back`, witness-vetoed); absence asserts the in-tree model (nothing to query; since stage B 2026-10-07 the post-fill dismissal taps a CONFIGURED element when the tree shows a band and presses nothing otherwise — until then a blind `enter`, measured to submit the form). When absent, nothing is queried and the tap guard reads the keyboard from the TREE that resolved the target (the `KEYBOARD_ROLE` band the WDA source marks, since 2026-10-07; a covered point is hidden first by a configured dismissal tap — `app.ios.keyboardDismiss`, §8 — or refused on a second look, nothing pressed — before that date taps were unguarded there).
    keyboardAdvice?: string          // OPTIONAL (2026-10-07, review): the in-tree model's one sentence — why THIS adapter cannot hide a covering keyboard and what was measured to work instead (`IosAdapter`: no back key, return submits, WDA keyboard/dismiss fails, a swipe does nothing; a tap on a neutral element hid it; a hardware keyboard keeps it from showing). Quoted verbatim by the refusals in interact/ and verify/, which own no platform fact.
      state(): shown{frame} | hidden | unknown   // Android: one `dumpsys window displays`. Never throws.
      witness(): shown | hidden | unknown        // independent second opinion, asked only right before a keyboard `back`: one device-side filtered `dumpsys input_method` (the command is `INPUT_SHOWN_COMMAND` in `adapters/android.ts`). Never throws.
    treeSourceKind: 'idb' | 'wda' | undefined  // REQUIRED, diagnostic only (since 2026-10-06): which backend `uiTree()` really reads with — the adapter, not `averi.yaml`, is the source of truth (the registry resolves the config INTO the adapter; a layer above that re-derived it from the config agreed only while every FlowEngine came from the registry). The iOS adapter reports its injected source's kind (always one: since 2026-10-08 there is no unbound probe adapter); undefined on Android (one tree). Nothing dispatches on it — the flow engine's wait timeout reads it to say "no tree read contained this id" only under idb. Required rather than optional like `keyboard?` because nothing asserts a model by its absence here: a wrapper that forgot it would not fail a test, it would silently lose the hint — so it fails to compile instead.
    openDeepLink(url)
    logs(since): string[]           // logcat / os_log for crash detection
}
```

Device discovery is NOT on this interface either (2026-10-08, the iOS adapter
stack review's candidate 1): which devices a platform has is a question about the
platform, answered by `adapters/discovery.ts` (`listAndroidDevices`: `adb devices -l`
plus one `adb -s <id> shell getprop` per online device, its argv `adb-shell.ts#adbShellArgv`'s;
`listIosDevices`: `simctl list devices --json` through `xcode-env.ts#simctl`, the one
simctl call `IosAdapter` makes too). The registry takes it as its second dependency beside the adapter
factory (`DeviceDiscovery`, `mcp/registry.ts` — both injected or neither, so a test
with a fake factory cannot list the host's real devices) and asks it on every
`get()`, as it asked a probe adapter before. Until then `listDevices()` was an adapter
member, so both adapters carried an unbound mode the registry used for nothing else —
an `IosAdapter` without a UDID (simctl's `booted` alias, a lazily resolved UDID for
idb, a `uiTree()` that refused) and an `AndroidAdapter` without a serial (adb without
`-s`, "the default adb device", a "more than one device" diagnosis). The serial / UDID
(and on iOS the tree source) is now a constructor invariant, and that mode is gone.
`setClipboard` went the same day: an interface member with no caller, which Android
only threw for; a first caller (pasting an OTP) would bring it back as an optional
capability, like `keyboard?`.

Selector-based tapping is deliberately NOT on this interface: `tapElement(adapter,
selector)` (`interact/tap.ts`, formerly `ui-tree/tap-element.ts`) resolves the selector against the normalized
tree and calls `tap(x, y)`. Nothing in it is platform-specific, and both adapters
had implemented it identically — which forced the platform layer to import the
selector layer above it, inverting exactly the direction this section describes.

**Android implementation** — pure `adb`:
- screenshot: `adb exec-out screencap -p` — since 2026-10-08 the bytes are judged in the adapter (`adapters/screenshot-bytes.ts`, shared with iOS): exec-out exits 0 with whatever the guest wrote, so an empty or non-PNG capture (`Killed` on a dying emulator) is a transport error naming the device and the command. Until then it was returned unchecked, and two empty captures are `Buffer.equals`, so the stability wait called a dead device's 0-byte frame SETTLED and the `screenshot` tool returned it with no note; `verify/capture.ts` keeps a length floor under that contract (`screenshotOf`), and its decode failure no longer names adb or simctl commands. A refused capture throws, and each caller contains it: inside a color, ocr or screenshot-baseline assert it ends THAT assert after one capture, rather than polling a dead device to the deadline, as a fail-closed failure quoting the adapter's first line (`screenshot failed: …; failing closed, color unchecked`), and `assertAll` goes on to the next assert (`verify/pixel-poll.ts`'s header; since the same day an `ocr` assert's measurement takes the same exit for an OCR engine that will never read, by marking its verdict `final`, and `failClosed` itself drops the reason's trailing full stop; flow `assert:` steps take element asserts only, so they never capture); as the final capture of a `verify` leg or `ensure_state` it is caught (`run/verify.ts#finalFrame`) so the trace, asserts and health line stand, with one `⚠ screenshot:` line and no image.

- input: `adb shell input tap/swipe/text/keyevent`
- install/launch: `adb install -r`, `adb shell am start` / `pm clear`. A launch names its entry point one of three ways: nothing (`monkey -c LAUNCHER`), an activity (`am start -n pkg/activity`, with the intent if one is given), or an intent alone (`am start -p pkg -a …` — scoped to the package, Android resolves the activity; since 2026-10-03). Whether a start started anything has ONE owner, `runStart` in `adapters/android-start.ts` (2026-10-07; the 2026-10-04 review's C10 had left this code in place until openDeepLink could share it): it reads the `am start` of a launch and of `openDeepLink`, and the `monkey` launch, into `started` or `refused` with the command's own lines, and throws anything else (adb failure, timeout) as it came. `am start` refuses in its output — an `Error` line or a Java exception, at exit 0 too — and monkey by its exit status, with its `** ` reason on stdout, which the ExecError message dropped. The callers word the refusal: the launch names `activity:` / `app.android.activity`, the deep link its url. A deliberate exception to "adapters speak platform only" (since 2026-10-03, extended to the monkey launch 2026-10-07): the Android launch refusals, from `am start` and from `monkey`, name config keys (`app.android.activity` in averi.yaml), the flow step's `activity:` and the `launch_app` tool, because the reader's next move is in the config or the call, not in adb; a typed error translated by the two callers (run/ for `launch_app`, flow/ for the launch step) would have been one message with two translation sites that must agree. Only words cross the layer, no import (`launchRefused` in `adapters/android.ts`). A deep link nothing handles therefore throws (until then `open_deep_link` answered "Opened"). What is unmeasured there is written once, in that module's header.
- logs: `adb logcat`
- what the device's shell receives: ONE owner, `adapters/adb-shell.ts` (2026-10-07). adb joins everything after `shell` with a space, unescaped, and the device's `sh -c` splits it again, so an unquoted `&`, space, `;`, `$` or backtick in a value was interpreted on the device (measured that day: a deep link cut at its `&`, an extra split at a space, `$HOME;id` executed). Every device command in `AndroidAdapter` goes through `shell(argv)`, which quotes each word (`shellQuote`), `execOut(argv)`, which does not — for `exec-out` the adb client escapes the words itself (`escape_arg`) — or `rawShell(line)`, the named exception for a pipe or `|| true`, with any user word quoted into it by `shellCommandLine`. `shell(argv)` and `listAndroidDevices`' getprop (`adapters/discovery.ts`) both build their argv with `adbShellArgv(serial, argv)`, so the `adb -s <serial> shell` + quoting is spelled once. Pinned through a real sh standing in for the device (`tests/helpers/device-sh.ts`). What this changed for `typeText` (a newline, return or tab is refused — `pressKey('enter')` is the route; since the code review the same day the refusal is `interact/type-text.ts`'s, the one statement of what text averi types: every C0 control character and DEL, on both platforms, before any device call — `fillField` checks before its keyboard guard, focus tap and clear, the type_text tool without a selector and the flow's `type:` step type through `typeIntoFocused`; iOS used to type a `\n` — with the adapter's check kept as a defensive assert) and `isAppRunning`, and what is UNVERIFIED on a device, is written once, in the header of `adb-shell.ts`.

**iOS implementation** — `xcrun simctl` + one helper:

Per-node normalization (role map by own key, empty→null, rect rounding, zero rect) has one owner, `normalizeIosElement` (`ios-node.ts`), that both adapters call and one test table pins through both; before, each kept its own copy and each test file pinned its own. Input and lifecycle stayed idb/simctl, and nothing above the adapter changed.
  - **Shutdown contract (0.8.1; one hop longer since 2026-10-02):** the child WDA is owned by `WdaServer`, `WdaServer` by `WdaTreeSource`, the tree source by `IosAdapter`, adapters by `AdapterRegistry`, the process by `mcp/lifecycle.ts` — and disposal runs down that chain, never across it. `lifecycle.ts` handles SIGTERM/SIGINT/SIGHUP (Node runs no `exit` hook for a signal) and awaits `registry.shutdown()` within a 1.5 s budget; `IosAdapter.dispose` returns its tree source's `dispose()`, which for the WDA source is `WdaServer.shutdown()`: it stops the child and waits for the port to go quiet, killing the listener if xcodebuild's teardown did not reach the runner (it lives under `launchd_sim`, outside our process group). **Normalized UI tree** is the key abstraction: `{role, label, identifier, value, rect, children}` identical on both platforms. Selectors like `id:login_pin_field`, `text:"Continue"`, `role:button label~"Pay.*"` resolve against it on either OS. This is what makes flow descriptors cross-platform.

## 4. Flow descriptors (`averi.yaml`)

Checked into the app repo. Describes app states and how to reach them. Every path it contains — the build paths below, the sibling `.env.averi`, the `.averi/baselines/` directory — resolves relative to **the descriptor's own location**, so the file is portable across working directories (nested repos, monorepos) and absolute paths stay untouched. Example for a PIN-login banking app:

```yaml
app:
  android: { package: md.victoriabank.myvb.dev, apk: app/build/outputs/apk/dev/debug/app-dev-debug.apk }
  ios:
    bundleId: md.victoriabank.myvb.dev
    app: build/Debug-iphonesimulator/MyVB.app
    # treeSource: wda                 # optional: RN / SwiftUI container ids (§3); keyboardDismiss needs it
    keyboardDismiss:                  # optional, ordered (§8): how to hide the soft keyboard when it covers a tap target —
      - tap: { id: login_title }      #   a NON-interactive element (a title, a label) whose tap hides it without submitting,
      - accessory: true               #   or the input-accessory toolbar's trailing button (the "Done" above a number pad)

credentials:              # values come from env / OS keychain, never from YAML
  username: ${AVERI_USER}
  password: ${AVERI_PASSWORD}
  pin:      ${AVERI_PIN}
# Values resolve from the environment the load assembles: the real one, over
# a `.env.averi` file next to averi.yaml (gitignore it) — existing env vars
# take precedence, so the project is self-contained and CI can still inject
# via real env. The file is re-read on every tool call and never written into
# process.env (since 2026-10-04 it is a value the loader returns beside the
# config, flow/load.ts).

environments:             # optional: per-backend credential overrides
  dev:
    credentials:
      username: ${AVERI_DEV_USER}
  staging:
    credentials:
      username: ${AVERI_STAGING_USER}
# Layered ON TOP of `credentials:` per key, so shared secrets are declared once.
# Selected by the tool's `environment` argument, else $AVERI_ENV, else
# `defaultEnvironment:`. Resolved once per engine, so one run can never mix one
# environment's username with another's password; an unknown name is refused
# by the run layer's pre-flight before any device is touched (2026-10-05). The
# active environment is the first trace line:
# a wrong login name is rejected one screen AFTER it is typed, so without that
# provenance an environment mix-up is indistinguishable from a bad credential.

states:
  logged_in:
    detect:                       # how to recognize we're already there
      any:
        - element: { id: dashboard_root }
        - element: { text: "Accounts" }
    reach: [login]                # flows that get us there, cheapest first

flows:
  login:
    steps:
      - launch: { clearState: false }
      - branch:
          - when: { element: { id: pin_keyboard } }     # returning user → PIN
            do:
              # keypad matches per-digit keys by resource-id or, for keypads
              # without ids (common in Compose), by visible text:
              #   keypad: { text_pattern: "{digit}" }
              - type_pin: { value: $pin, keypad: { id_pattern: "pin_key_{digit}" } }
          - when: { element: { id: username_field } }   # fresh install → full login
            do:
              - tap:  { id: username_field }
              - type: { value: $username }
              - tap:  { id: password_field }
              - type: { value: $password }
              - tap:  { text: "Log in" }
              - wait: { element: { id: pin_setup_screen }, timeout: 15s }
              - type_pin: { value: $pin, twice: true }   # set + confirm
      - optional:                                        # dismissable interstitials
          - tap: { text: "Not now" }        # biometrics prompt
          - tap: { id: promo_close }        # marketing popup
      - wait: { state: logged_in, timeout: 20s }

  goto_transfers:
    requires: logged_in
    steps:
      - tap:  { id: tab_payments }
      - tap:  { text: "New transfer" }
      - wait: { element: { id: transfer_form } }
```

Design points:

- **State detection before action.** `ensure_state` first checks `detect`; login runs only when needed. Handles the "reinstall wipes the session" case automatically, and is idempotent.
- **`reach:` is an escalation ladder, not a script.** `detect` is re-checked after *each* flow in the list and the rest are skipped once it is satisfied, so `reach: [dismiss_post_login_prompts, login]` means "try the cheap idempotent one; escalate only if it did not work". "Did not work" covers both ways a rung can fail to deliver: completing without reaching the state, and *throwing* — a cheap prelude typically fails by timing out on a `tap:` for an interstitial that was not there, and aborting the ladder on that would leave the prelude working only on the runs that did not need it. A thrown rung is never swallowed: it is logged as `⚠ reach <flow>` with the reason, and the last rung's failure still fails the call — after the recovery pass below. This is load-bearing, not a nicety: before it, listing a cheap flow ahead of a destructive one *guaranteed* the destructive one also ran — a `launch { clearState: true }` login burning a device registration on a session that was already alive, because one post-login interstitial defeated `detect` for a single probe (2026-08-26). Order the list cheapest-first.
- **…and it gets one pass backwards.** The mirror of the same finding, measured the same day: the ladder is one-shot and forward-only, so the LAST rung's aftermath can produce a screen an EARLIER rung exists to clear — login finishes, the biometrics interstitial arrives a network round-trip later, after that login's `optional:` windows closed — and nothing re-runs the cure. One `ensure_state` failed where an immediately repeated, identical one passed, because the second restarted the ladder from rung 1; the engine already held the cure and never applied it inside one call, which is not what "idempotent — call it freely" promises. So reaching the end of the ladder short of the state triggers at most one recovery pass per tool call — per engine run, so nested `requires:` and a `verify` leg's state-then-flow share it (since 2026-10-07; the leg used to get one for each) — (`↻ recovery` in the trace) over the earlier rungs, re-checking `detect` after each, then fails with the original error. "Reaching the end" covers both ways it happens: the final wait timing out, and the LAST RUNG THROWING. The second is the shape production configs actually have — a login flow's success criterion is written as the flow's own trailing `wait: { state: logged_in }`, so a late interstitial makes the rung throw and the final wait, where the pass would arm, is never reached. Covering only the first left the motivating incident failing exactly as it had before the fix (measured on device, `docs/bugs/2026-08-26-recovery-pass-skips-throwing-last-rung.md`). A throwing last rung also has its own `detect` to re-check — the one the ladder gives every other failed rung, for the flow that reaches the state and then dies on a later step. Both run before the throw is rethrown, and the caller still sees the ORIGINAL error; the pass is safe on a throw for the reason it is safe on a timeout, since what it re-runs is bounded by the two rules below rather than by why the ladder ended. Two bounds keep it from re-opening the hole above: the last rung is never re-run — it is the anchor the ladder climbs *to* — and every candidate must be provably non-destructive. "Provably" is a static walk (`flowIsDestructive`): `launch { clearState: true }` anywhere in a flow's steps including inside `branch`/`optional`/platform overrides, anything reachable through its `requires:`, an explicit `destructive: true`, an unknown flow, or a `requires` cycle. Every default in that walk points at "destructive", because being wrong there costs a second wipe while being wrong the other way only costs the latency this fix was already spending. The ladder's pre-flight "this rung is DESTRUCTIVE" line is a different question and uses a different, non-transitive predicate (`flowItselfIsDestructive`: the rung's own steps and `destructive: true`, `requires` not followed): it is printed as a fact before `requires` has been checked, and with the transitive walk every navigation flow requiring a logged-in state warned on every call, one line before "already active" (2026-10-05, `docs/bugs/2026-10-06-destructive-rung-warning-false-positive.md`). An escalating `requires` loses nothing — the nested ladder warns on the rung that actually wipes.
- **…and it never wipes blind.** A destructive rung (`flowItselfIsDestructive`) whose immediately preceding probe never read a RENDERED tree is REFUSED: the probe before rung 0 is the entry detect, before any later rung that rung's predecessor's re-check. A probe is `unknown` when every one of its reads failed (`pollTree`'s `treesRead === 0`), and — since 2026-10-07 — `bare` when every tree it read was bare (`ui-tree/bare-tree.ts#isBareTree`: only wrappers and unlabeled decoration, a launch's decor or splash); one rendered read in a window makes it a real "no". Such a probe first gets ONE second look over `ensureTimeoutMs` (20 s by default — the budget that already means "how long a state may take to appear"; the final wait after the ladder uses it too): the entry probe is a single read, so the warm path stays one read, and a cold launch is unreadable or bare for a while — agents hit it by calling `ensure_state` right after `launch_app`. Measured 2026-10-06 on an RN debug build on an Android 13 emulator: null root to ~+3 s, the decor alone (`android:id/content`, `action_bar_root`) +5.3…+13.8 s, `login_screen` at +18.3 s; through WDA the 7-node splash is read at +0.3 s. Until 2026-10-07 the second look was the 5 s settle budget (`tapTimeoutMs`) and only an `unknown` probe got it, and a bare tree counted as "no": the look ended on the decor and `ensure_state logged_out` wiped an app that was already logged out, three runs of three; under WDA the ENTRY probe read the splash as "no" and the wipe ran with no second look at all (docs/bugs/2026-10-06-second-look-reads-android-decor-as-not-in-state.md). The second look is one poll with one deadline, so null root → decor → rendered is ridden out as one transient. A second look that reads the state ends the call ("already active", or "reached after" the previous rung); one whose window held a rendered tree outside it runs the rung, warning as usual — after polling to its deadline, as every detect window does, so a cold launch onto a screen genuinely outside the state pays up to 20 s before the wipe; only a second look that still reads nothing rendered refuses. Then the ladder logs `⛔ reach <flow>` in place of the DESTRUCTIVE warning and throws `UnreadTreeRefusal`, whose cause (`UnreadCause`) is what the probe before the rung and its second look learned TOGETHER: `unknown` with the last read error only when neither read any tree; `bare` with the last bare tree's shape (`7 nodes (roles: container ×6, image ×1)`) when the second look read one; `bare-then-failed` — that shape AND the last read error — when only the probe before it did. Until the 2026-10-07 review the cause was the second look alone, so a bare entry read followed by failed reads said "never read a UI tree", and a failed entry read followed by bare ones said "every read was bare". One clause (`describeUnreadCause`) words it for the `⚠ detect` line, the refusal and the no-reach `SetupError`. Measured 2026-10-06: idb returned a 0×0 tree for minutes on a rendered PIN screen, every probe read "not in state", and mp-native's `logged_in.reach: [dismiss_post_login_prompts, login_registered, login]` would have wiped a registered app. Cheap rungs still run at once on an unknown probe, with no second look (they are how a ladder gets a readable tree; a device that cannot be read is not a screen still drawing); on a BARE probe, since 2026-10-08, they get the same second look first — see "…and a bare tree decides no condition" — and run if it still reads nothing rendered. The look and the refusal are one check at the top of the ladder loop. The bare rule's known miss — a LOADED screen whose only non-wrapper nodes are identified-but-unlabeled icons is called bare — therefore now costs a refusal there: such a screen cannot reach a destructive rung through `ensure_state` (`run_flow` of the rung still runs it). The refusal is terminal like a `SetupError` (`isTerminal`, asked by the ladder's catch; the final wait never enters a ladder, so its catch still asks only for a `SetupError`): an outer ladder whose rung's `requires:` refused must not escalate past it into its own next rung. Salvage runs no rung and the recovery pass never runs a destructive one, so neither needs the check; `run_flow` never refuses the flow's own body (the caller's decision), though a `requires:` inside it runs a ladder that applies the rule. The cost: a transient that outlasts the second look is refused too, and the call is retried (or the rung run deliberately with `run_flow`) — a retry is cheap, a wipe on an unread screen is not. This resolves the 2026-10-03 follow-up the detect probe carried since its read error stopped being swallowed.
- **…and a bare tree decides no condition** (since 2026-10-08, flow-engine review candidate 2). `flow/condition.ts` is the one module asked about a `Condition` — `evaluateCondition` (one condition against one tree), `describeCondition` (its name in the trace) and `conditionStateRefs` (the states it names, which `config.ts`'s existence and cycle checks read) — and its answer is three-valued: `yes`, `no`, or `unknown`, "this tree is BARE and cannot decide it". The leaf rule is `ui-tree/verdict.ts` (there, not in `flow/`, because the absent assert asks it too and `verify/` may not import `flow/`): a present element is `yes` when found whatever the tree holds, else `no` on a rendered tree and `unknown` on a bare one; an `absent: true` element is `no` when a match is visible whatever the tree holds, else `yes` on a rendered tree and `unknown` on a bare one — so a rendered tree never yields `unknown` and every screen an app has drawn answers exactly as before. `any:` and `all:` combine in Kleene's logic (any: `yes` if some arm is, else `unknown` if some arm is, else `no`; all: `no` if some arm is, else `unknown` if some arm is, else `yes`), stopping at the deciding arm in written order as before; `{ state: x }` is `x`'s detect with the same semantics. Each caller keeps its own policy, and none reads `unknown` as `yes`: the detect probe counts any round that is not `yes` on a bare tree as bare (its 2026-10-07 rule, unchanged), so the ladder's unread handling above — the second look, the never-wipes-blind refusal, "could not be checked" — now covers an absent detect too, and a BARE probe gets the second look (over `ensureTimeoutMs`) before ANY rung, not only a destructive one: with an absence undecided on the decor, `no_prompt: { detect: { id: prompt, absent: true }, reach: [dismiss] }` — "already active" there before — would otherwise run `dismiss` at once and fail on its tap of `later` once the decor outlasted `tapTimeoutMs`; now a rendered, detected screen ends the call, a rendered screen outside the state runs the rung on a tree that means something, and one still bare runs a cheap rung as before (a destructive one is refused). An `unknown` probe — every read failed — keeps running a cheap rung at once. The cost: a screen that is bare by the accepted miss (a map, a camera, an identified-only icon screen) delays a cheap rung by up to `ensureTimeoutMs` — and a whole ladder by up to N × `ensureTimeoutMs` for N rungs on a screen that never renders, before its ⛔ or its final wait's timeout, since each cheap rung may have relaunched the app and restarted the cold-launch clock, so each probe after it gets its own look (measured by the review: mp-native's three-rung ladder reaches ⛔ in about 60 s, where it took about 20 s before); `wait:` and `branch:` keep polling on `unknown` as on `no` — a `branch:` takes arm i only when every arm before it is `no`, so an earlier arm that is `unknown` holds the round undecided even when a later arm is `yes` on the same tree (an arm on the decor's own `content` is), since that earlier arm might win once the app renders and written order is the priority — and a timeout whose LAST tree was undecided says so beneath its headline (`the last UI tree read was bare, <shape> of only wrappers and unlabeled decoration, so it could not decide this — the screen had not rendered by the deadline; compare with screenshot, and a longer timeout may be all it needs`, in place of the idb container-id hint; dropped, like that hint, when the last read failed); the `absent` assert keeps polling on a bare tree and fails as `could not verify within Nms (the last UI tree read was bare, …)` with the same note, the wording an unreadable tree already had. Until then the evaluation was the engine's private `matches`, a boolean whose `absent` was `absentFromViewport` alone: nothing in a cold launch's decor or WDA's splash matches any selector, so a state detected by an absence was "already active" before the app had drawn anything, a `wait:` on it passed at once, a `branch:` arm on it was taken, and the absent assert PASSED — the bare rule lived only in the detect probe, and only for a tree that MISSED. The cost, the bare rule's known miss again: on a loaded screen whose only non-wrapper nodes are identified-but-unlabeled icons an absent condition can no longer pass (a wait or branch on it times out with the bare note, the assert fails as could-not-verify).
- **…and a loop through `requires:` fails its rung, never the call's chance to escalate** (since 2026-10-08). A reach rung's `requires:` leading back to the state being ensured is not a config error (only a `detect` cycle is — the mutual login/logout shape works from either state on the loop), so the engine refuses it at run time: a state re-entered while its own ensure is still on the stack, and not detected on that entry, throws a `ReentryError` naming the loop (`states.logged_in → flows.login → states.login_screen → flows.logout → states.logged_in`) where the call used to hang. It fails the rung whose `requires:` closed the loop and is deliberately NOT terminal: the ladder escalates to its next rung as for any failed rung, so a declared fallback (`reach: [login, hard_login]`) still runs and a destructive one still meets the never-wipes-blind check; with no rung left the call fails with that error. Each state is on the stack at most once, so it terminates, but the bound is the product of the loop's rung counts, not their sum (n states each with two rungs requiring the next: 2^(n+1)−3 reads, 253 at n = 6); no step runs in a re-entry subtree, so it costs reads only, never a tap. A state re-entered and detected by then answers "already active" as any ensure does — whose cost is the outer entry's stale read: the loop unwinds through rungs the app did not need, a spurious logout and login, or a wipe when the unwinding rung is destructive (identical on fb171ef). Right after `launch_app` this shape now fails fast with the unread cause ("none of this loop's states could be read on this probe (…)") where it used to ping-pong login/logout taps (7 taps measured on fb171ef) — retry once the screen renders, as with an `UnreadTreeRefusal`.
- **Failures carry their trace.** A flow that throws attaches the steps that already ran to the error message (`FlowError`). A bare "Timed out after 20000ms waiting for state logged_in" cannot tell you which reach flow ran, how far it got, or what it cost; the trace can, and it exists either way. The trace is the whole RUN's: a `verify` leg with a state and a flow is one run since 2026-10-07, so a failing flow carries the state's lines (and any wipe) before its own.
- **`branch` + `optional`** absorb the two realities of real apps: different login paths (fresh vs. returning) and random interstitials (rating prompts, promos, biometric sheets). An `optional:` step never fails the flow on what the screen did — a config refusal (an empty or undeclared credential, an unset `${VAR}`, a `type_pin` value with no digits: the engine's `isTerminal` set) fails it even inside `optional:` (since 2026-10-08), with the ✗ on the step that raised it, because skipping it would run on with the login half-typed; otherwise its trace line says why it was skipped — `(not present)` only when the interaction module reports the element was never found on a screen it could read (`ElementNotFoundError`, since 2026-10-08 — an optional tap's presence check, a nested fill's or tap's settle wait, a `scroll_until` that never matched; an optional tap the presence check DID sight quotes its tap's own timeout if the element then leaves, since a failure after finding is never absence), otherwise the failure's own headline (a field found but whose text did not land, a value refused before anything was tapped, a keyboard that would not hide, a `wait:`/`branch:` that timed out), with the read-error line joined on when the last tree read failed, so a dead device never reads as an absent interstitial. Until that date the engine guessed, and a found field whose fill failed read `(not present)`.
- **Secrets** are referenced (`${ENV}` or `keychain:` URIs), never stored. Server redacts them from logs and from anything echoed back to the agent — the agent never sees the actual PIN, it just calls the flow.
- Platform overrides per step where needed: `ios: { tap: {...} }`.
- Same file doubles as documentation of the app's navigation for humans.

## 5. MCP tool surface

Small, high-level surface — agents perform better with fewer, smarter tools:

| Tool | Purpose |
|---|---|
| `list_devices()` | Booted simulators/emulators, platform, OS version; `active` marks the current target |
| `select_device(platform, device)` | Pin the device the platform's tools target (default: first booted). A pinned device going offline is an error, never a silent fallback |
| `install_app(platform, path?)` | Uses `averi.yaml` defaults (what each tool reads of averi.yaml: "Which tools read averi.yaml", below) |
| `ensure_state(state, platform)` | The killer tool: detect → run flows → confirm. Returns final screenshot |
| `run_flow(flow, params?)` | Any named flow |
| `screenshot(platform, label?)` | PNG returned as MCP image content (agent's vision verifies it) |
| `ui_snapshot(platform, filter?)` | Normalized AX tree as JSON — cheap, text-based verification. Since 2026-10-06 a filter that matches nothing returns `[]` plus a second text block: the unfiltered tree's size and roles, or a `⚠ … bare` that the tree is empty or unrendered (still loading, or the tree source stuck on a rendered screen — compare with `screenshot`, do not read the element as absent). The array itself is unchanged |
| `tap / swipe / type_text / press_key` | Low-level escape hatch for ad-hoc exploration. Since 2026-10-03 `tap` and `type_text` resolve a selector exactly as a flow step does: they wait up to the settle budget for the element to appear and hold still, so a selector matching nothing is a timeout, not an immediate "No element matches"; ambiguous matches are refused with the list; and a `type_text` whose tree cannot be re-read after typing fails rather than reporting an unverified fill |
| `assert(spec)` | Declarative check: element exists/absent, text matches, rect geometry vs Figma-frame values (`rect` spec — deltas in % of the window width, `y` measured but never failed; fails closed on a width `verify/scale.ts#windowWidth` refuses), fill color vs an expected hex (`color` spec — CIEDE2000 over the element's sampled region, default dE 8; hex only, token names resolve upstream), screenshot-diff vs. baseline < threshold |
| `verify(platforms?, state?, flow?, asserts, contract?)` | Runs the same sequence on the requested platforms (default: iOS **and** Android; legs always android-then-ios), returns per-platform screenshots + assert results; `contract` (layout-contract JSON) appends a per-anchor `## rect parity` geometry table, anchors carrying `bg`/`bg_dark`/`sample` add a `## color parity` table sampled from the legs' own screenshots (CIEDE2000: android-vs-ios primary at `tolerance_de` 8, vs-contract at 1.5×), and anchors carrying `text`/`text_dynamic` add a `## text parity` table reading the RENDERED copy and ink height back off those same screenshots with OCR (`tolerance_size_pct` 10) — numbers over impressions; since 2026-10-03 a contract field one of those tables could not read (bad `bg`, `sample`, `text`, `text_dynamic` or `tolerance_*`) refuses the call before any leg starts, listing every such field, where it used to run both legs and print `FAILED:` in that table |
| `get_logs(platform, since, grep?, maxLines?)` | Crash/exception scan (logcat, os_log). Returns the last `maxLines` matching lines (default 400), headed by how many the grep matched and how many are shown — a `grep` alone is not a token budget |
| `record_flow(name)` *(v2)* | Watch manual/agent interaction, emit a draft flow YAML |

### Which tools read averi.yaml

Declared once per tool, in `mcp/config-policy.ts#TOOL_CONFIG`, and carried out by `flow/tool-config.ts#loadForCall` — at most one read of averi.yaml (and of `.env.averi`, where marked) per call, handed down as a value. Since 2026-10-08; until then each handler picked one of four loaders, an iOS `assert` read the file twice under two policies, and `assert` on Android and `launch_app` swallowed a broken file in a catch-all.

| Tool | Android | iOS | `.env.averi` |
|---|---|---|---|
| `install_app` | required — only without `path` (\*) | required — only without `path` (\*) | no |
| `launch_app` | optional — only with neither `activity` nor `intent` (the `app.android.activity` fallback) | none | no |
| `ui_snapshot`, `tap`, `type_text`, `scroll_until` | none | optional (tree source; dismissals for `tap`/`type_text`) | no |
| `assert` | optional (health line) | optional (tree source, health line) | no |
| `ensure_state`, `run_flow`, `verify` | required | required | yes |
| every other tool | none | none | no |

(\*) The table entry is plain `required` and does not look at `path`, by design: the handler's `path ?? appBuildPath(…)` short-circuits before the read, so a call with a path reads nothing, and the entry keeps `cfg` typed non-optional where `appBuildPath` needs it. `launch_app` is the one entry that takes the call's arguments.

- **none** — the file is not read; a broken one beside the call is not its business, because the call uses no value from it.
- **optional** — a MISSING file is no config and the call proceeds on the defaults (no health line, the idb tree source, no dismissals, the launcher's activity).
- **required** — a missing file fails the call.
- Under **optional** and **required** alike, a present-but-INVALID file fails the call, naming the file, before any device is bound. Android and iOS differ only where the tool uses different values on them — never in how a broken file is judged. Two calls that passed before 2026-10-08 now fail on a broken averi.yaml: an Android `assert` (it silently lost the health line) and an Android `launch_app` naming neither activity nor intent (it silently lost `app.android.activity` — the LeakCanary case its description warns about); the same two calls also stop passing over a read error other than a missing file (a directory at the path: EISDIR). A health check that throws outside `appHealth`'s own guard still only omits `assert`'s health line, as before: the guard around it was narrowed to the health check alone, not removed.

Verification philosophy: three tiers, cheapest first — (1) AX-tree asserts (fast, deterministic), (2) screenshot to the agent's own vision (semantic judgment), (3) pixel-diff vs. stored baseline (regression). The tool provides all three; the skill teaches when to use which.

## 7. The skill

Ships with the package (`averi` skill — copy into the app repo). SKILL.md teaches the agent the workflow, not the plumbing:

1. **Golden path**: build app → `install_app` → `ensure_state("logged_in")` → `run_flow`/low-level navigation to the changed screen → `screenshot` + `assert` → report with paired iOS/Android images.
2. **Rules**: always `ensure_state` instead of manual login; prefer `ui_snapshot` asserts over screenshots for text checks; use `verify` (default: both platforms) before declaring a cross-platform task done; on unexpected screen, take screenshot + `ui_snapshot`, try `optional` dismissals, else surface to the human; never ask the user for credentials — if a `${VAR}` is missing, tell them which env var to set.
3. **Recipes**: "verify a UI change", "reproduce a bug report", "check a flow after refactor", "update `averi.yaml` when navigation changes" (the agent maintains the descriptor as part of feature work — self-healing config).
4. Reference of tool signatures + `averi.yaml` schema.

## 8. Reliability details that make or break this

- **Waits, not sleeps**: every action polls the AX tree for the expected postcondition (configurable timeout); screen-stability heuristic (two identical consecutive screenshots, up to 5 re-captures 300 ms apart) before any frame is measured or returned — owned by `verify/capture.ts`, applied by the `screenshot` and `ensure_state` tools, the color, ocr and screenshot-baseline asserts, and the final frame of every `verify` leg, so a mid-animation frame is never the verdict (the legs took a bare screenshot until 2026-10-02, the screenshot-baseline assert until 2026-10-04 — that assert now pays the stability budget documented on `capture.ts`'s `STABILITY_*` constants where it took one capture). Since 2026-10-05 that budget has ONE owner and the frame SAYS whether it settled: `pollMs` is a poll interval and nothing else — until then the Verifier forwarded it to the capture as the delay between stability captures, so an assert inside a flow (engine default 500) waited 500 ms where the MCP `assert` tool waited 300, and "the same budget for every consumer" was false in production; `Frame.stability` (settled / moving / unjudged — decided once in capture.ts, never re-derived from the count) and `Frame.captures` report the wait's outcome; the color and ocr asserts treat a moving frame as a miss (the deadline, not a moving frame, decides, and the timeout says the frame never settled), the screenshot-baseline assert refuses to CREATE from one (it used to store the last of six differing frames as the ground truth) and still diffs against an existing baseline with a `⚠ frame:` note on the result, and the `verify` legs and the `screenshot`/`ensure_state` tools return the best frame with that note. Since 2026-10-06 the color and ocr asserts judge stability over the element's own region, through the pixel poll (`verify/pixel-poll.ts` hands the capture the matched rect; a status-bar clock or a caret elsewhere no longer keeps their frame moving, and a region the capture cannot scale or land falls back to the whole screen); the frame says whether it settled over the `screen` or only the `region`, and a region-only frame is measured only when two consecutive tree reads put the element at the same rect — the crop sits at a rect read before the captures, so without that check a sliding element's static old area would pass (cost: one extra round, about one tree read, only when the whole screen is not still; residuals recorded on `capture.ts`: a tree that already reports the element's final rect during an entrance or fade-in, and movement after the confirming snapshot); baselines, the `verify` legs and the tools still judge the whole screen. The capture takes the poll's deadline and stops short of it; the poll loop's own rule is unchanged (checked after each round, never before a read, so a late element is still found by the read that starts inside the deadline) — the measured before/after figures are on `Verifier.poll` in `verify/assert.ts`. The same day the flow engine stopped passing its poll interval as `scroll_until`'s post-swipe pause (interact/scroll.ts's own 400 ms applies; it was 500 ms in flows) — a production timing change not yet measured on a device. The same module derives the png scale once per settled frame. The tree-side wait has one owner too, since 2026-10-03: `ui-tree/read-tree.ts#pollTree` — one read per round, a failed read is a miss whose error the timeout quotes, a `PollMiss` keeps the last thing a round saw, the predicate's own errors propagate, and (since 2026-10-06) a timeout counts the rounds that read a tree (`treesRead`), so the detect probe can tell "never matched" from "never read" (`unknown`, which the ladder refuses a destructive rung on). `Verifier.poll`, `FlowEngine.pollUntil`, the state-detect probe and `interact/resolve.ts#resolveSettled` (the settle wait the flow steps and the MCP tap/type_text tools share) are its callers and own only their wording; `verify/pixel-poll.ts#pollPixels` (since 2026-10-06, the color and ocr asserts' round) is its one caller that owns more — the round's order, the stability and decode gates before any measurement, and the timeout wording those asserts share; before that they were three copies of the loop, and the probe's copy swallowed the read error, so a dead adb read as "not in state". Since 2026-10-06 the color and ocr asserts that name no `timeout` default to 12 s, the tree asserts to 3 s (`verify/assert.ts` `PIXEL_ASSERT_TIMEOUT_MS`): one pixel round on the Android emulator is a 2.7 s read plus a settled pair of captures, ~4.3 s, and a region-only settle needs a second; the shared 3 s only ever fitted because the capture overran it, which 4954ab4 stopped (docs/bugs/2026-10-06-pixel-assert-default-timeout-fits-no-round-on-device.md). ## 10. Risks

- **Compose/SwiftUI semantics gaps** → AX tree may be sparse; mitigation: coordinate-tap fallback + a lint tool that reports missing `testTag`/`accessibilityIdentifier` (also a selling point: it pushes teams toward accessible apps).
- **idb maintenance risk** (Meta's investment fluctuates) → the tree read sits behind the `IosTreeSource` seam with two adapters, idb and WDA (§3). Exercised 2026-08-12 behind a flag; a seam since 2026-10-02 — changing the default tree backend is one constant, `DEFAULT_IOS_TREE_SOURCE` in `adapters/ios-node.ts`, not an edit to `IosAdapter` or the registry. Input (`idb ui tap/swipe/text`) is NOT behind it: a full idb exit still needs a WDA input path, which drags in session management (plan, decision 4).
- **Overlap with mobile-mcp** → averi's value over raw taps is the flow-descriptor layer, cross-platform parity, and the maintained skill.
- **Secrets in a banking context** → local-only processing, redaction, and keychain integration must be in v1, not later.
